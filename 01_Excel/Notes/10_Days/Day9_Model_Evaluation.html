🧠 Key Concepts Deep Dive
✂️ Train / Test Split — Why It's Non-Negotiable CORE PRINCIPLE
Evaluating a model on the same data it trained on is like giving students the exam questions in advance. They'll score 100% — but that proves nothing about what they actually learned. Train/test split holds back 20% of data so the model is always evaluated on data it has never seen.
// Step 1: Add a random number column =RAND() → random number 0–1, recalculates on every change // Step 2: Freeze the random values (critical!) // Select random column → Copy → Paste Special → Values Only // Without freezing, RAND() regenerates every time you edit anything // Step 3: Assign Train/Test label =IF([@Random] <= 0.8, "Train", "Test") // 80% Train, 20% Test — industry standard for small datasets // Step 4: Count each split Train_count = COUNTIF(Split_col, "Train") Test_count = COUNTIF(Split_col, "Test") // Step 5: NEVER touch test data until final evaluation // Build model on Train rows only → evaluate on Test rows only // If RMSE_Train = 4.2 but RMSE_Test = 9.8 → model is OVERFITTING
📏 Error Metrics — MAE, RMSE & MAPE KNOW ALL THREE
Three metrics, three different questions. Use MAE for easy interpretation ("off by X units on average"). Use RMSE when big errors matter more than small ones. Use MAPE for percentage-based communication with non-technical stakeholders.
MAE
AVERAGE(ABS(actual-pred))
Mean Absolute Error. Average of all errors, ignoring sign. Easy to explain.
Best for: explaining error to stakeholders
RMSE
SQRT(AVERAGE((actual-pred)²))
Root Mean Squared Error. Punishes big errors more than small ones.
Best for: when large errors are very costly
MAPE
AVERAGE(ABS((actual-pred)/actual))×100
Mean Absolute Percentage Error. Scale-free, expressed as %.
Best for: comparing models across different scales
// Calculate all three on TEST set only MAE = AVERAGEIF(Split,"Test",ABS_Error_col) = AVERAGE(ABS(actual_test - pred_test)) RMSE = SQRT(AVERAGEIF(Split,"Test", Squared_Error_col)) = SQRT(AVERAGE((actual_test - pred_test)^2)) MAPE = AVERAGE(ABS((actual_test-pred_test)/actual_test)) * 100 // MAPE of 8.3% means: on average predictions are off by 8.3% of the true value // RMSE always ≥ MAE (because squaring amplifies larger errors) // If RMSE >> MAE → you have occasional large errors (outlier predictions) // If RMSE ≈ MAE → errors are consistently small (good model behaviour)
⚖️ Bias-Variance Tradeoff — The Fundamental ML Tension CORE THEORY
Every ML model sits on a spectrum between two failure modes. Understanding this tradeoff explains why adding more features sometimes hurts, and why a "perfect" training score is actually a warning sign.
🎯 High Bias (Underfitting)
Model is too simple. Misses real patterns.

Signs: Train RMSE is HIGH. Test RMSE is also HIGH. Both bad.

Fix: Add more features. Use a more complex model. Reduce regularization.

Example: Fitting a flat line to clearly curved data.
🎭 High Variance (Overfitting)
Model memorised training data. Fails on new data.

Signs: Train RMSE is VERY LOW. Test RMSE is HIGH. Big gap.

Fix: Remove weak features. Get more training data. Simplify model.

Example: A model that perfectly fits 80 training points but fails on any new student.
// Detecting overfitting with the Train vs Test gap RMSE_Train = SQRT(AVERAGEIF(Split, "Train", Squared_Error_col)) RMSE_Test = SQRT(AVERAGEIF(Split, "Test", Squared_Error_col)) Gap = RMSE_Test - RMSE_Train // Interpreting the gap: // Gap < 10% of RMSE_Train → well generalised model ✓ // Gap 10–30% → slight overfitting — worth investigating // Gap > 30% → significant overfitting → remove features or get more data // RMSE_Train ≈ RMSE_Test and both HIGH → underfitting → add features

✂️ Train / Test Split — The Right Way
Create a reproducible 80/20 split using RAND() and frozen values
Practice
▼
The single most important habit in ML is evaluating your model on data it has never seen. Without a proper train/test split, every metric you calculate is optimistically biased — your model looks better than it really is. This task builds that habit into your workflow permanently.
1
Open your Day6_Complete.xlsx (regression model) or create Day9_Evaluation.xlsx with a fresh 80-row dataset: StudentID, Score (target), StudyHours, Attendance, Is_Eng, Is_Mkt. Convert to Table named EvalData.
2
Add a "Random" column: =RAND(). Notice it changes whenever you press Enter anywhere — that's the problem. We must freeze it immediately.
3
Freeze the random values: Select the Random column → Ctrl+C → right-click same column → Paste Special → Values → OK. Verify: clicking elsewhere no longer changes the numbers. Now they're frozen seeds for your split.
4
Add "Split" column: =IF([@Random]<=0.8,"Train","Test"). Count each:
=COUNTIF(EvalData[Split],"Train") → should be ~64
=COUNTIF(EvalData[Split],"Test") → should be ~16
Verify both sum to 80.
5
Build regression on Train only: Run ToolPak Regression (Data → Data Analysis → Regression). For Y and X ranges, use the full columns — but in the Output, add a note that says "Trained on Train rows only." Record the coefficients: β₀ (intercept), β₁ (StudyHours), β₂ (Attendance).
6
Add "Predicted_Score" column using your trained coefficients:
=Intercept + β₁*[@StudyHours] + β₂*[@Attendance]
This applies to ALL rows (train and test). In the next task you'll calculate error metrics separately for each split.
// Step 1: Random column =RAND() // Step 2: FREEZE immediately (paste as values) // Select column → Ctrl+C → Paste Special → Values → OK // Step 3: Train/Test label =IF([@Random]<=0.8, "Train", "Test") // Step 4: Verify counts =COUNTIF(EvalData[Split], "Train") → ~64 =COUNTIF(EvalData[Split], "Test") → ~16 // Step 5: Apply trained model to ALL rows =Intercept + β₁*[@StudyHours] + β₂*[@Attendance] // Step 6: Absolute error per row =ABS([@Score] - [@Predicted_Score]) // Step 7: Squared error per row =([@Score] - [@Predicted_Score])^2
🚨
Critical rule — never break this: Once you've done your train/test split, the test set is locked. You cannot use test data to make any modeling decisions — not feature selection, not threshold tuning, not anything. The moment you look at test performance and adjust your model, the test set is "contaminated" and no longer measures true generalisation.

Split column: Train/Test
Counts sum to 80
Coefficients recorded

📏 Error Metrics Dashboard — MAE, RMSE, MAPE
Calculate all three metrics separately for Train and Test — then diagnose your model
Practice
▼
Three metrics answer three different questions: MAE asks "how far off are we on average?", RMSE asks "do we make any catastrophically bad predictions?", and MAPE asks "what % of the actual value are we typically off by?" Together they give a complete picture of model health that no single metric can provide.
1
Create sheet "MetricsDashboard". Build a 2×4 grid: rows = Train / Test, columns = MAE / RMSE / MAPE / R². This is your Model Performance Scorecard.
2
MAE — Train and Test:
Train MAE: =AVERAGEIF(EvalData[Split],"Train",EvalData[Abs_Error])
Test MAE: =AVERAGEIF(EvalData[Split],"Test",EvalData[Abs_Error])
Format as "X.X score points". Read as: "On average, predictions are off by X points."
3
RMSE — Train and Test:
Train RMSE: =SQRT(AVERAGEIF(EvalData[Split],"Train",EvalData[Sq_Error]))
Test RMSE: =SQRT(AVERAGEIF(EvalData[Split],"Test",EvalData[Sq_Error]))
RMSE ≥ MAE always. Large gap means occasional big errors.
4
MAPE — Train and Test:
Add a "MAPE_Error" column to EvalData: =ABS(([@Score]-[@Predicted_Score])/[@Score])
Train MAPE: =AVERAGEIF(EvalData[Split],"Train",EvalData[MAPE_Error])*100
Test MAPE: =AVERAGEIF(EvalData[Split],"Test",EvalData[MAPE_Error])*100
Format as percentage. Read as: "Predictions are typically off by X% of the true score."
5
Overfitting diagnosis:
Gap = Test RMSE − Train RMSE
Gap % = Gap / Train RMSE × 100
Add a "Diagnosis" cell: =IF((Test_RMSE-Train_RMSE)/Train_RMSE<0.1,"✓ Well Generalised",IF((Test_RMSE-Train_RMSE)/Train_RMSE<0.3,"⚠ Slight Overfitting","✗ Overfitting"))
6
Baseline comparison: Calculate a "Dumb Model" baseline — always predict the mean score. =ABS([@Score]-AVERAGEIF(EvalData[Split],"Train",EvalData[Score])). Calculate MAE for this baseline. Your real model MUST beat the baseline — otherwise it has no value over simply predicting the average for everyone.
// MAE (Mean Absolute Error) Train_MAE = AVERAGEIF(Split_col, "Train", Abs_Error_col) Test_MAE = AVERAGEIF(Split_col, "Test", Abs_Error_col) // RMSE (Root Mean Squared Error) Train_RMSE = SQRT(AVERAGEIF(Split_col, "Train", Sq_Error_col)) Test_RMSE = SQRT(AVERAGEIF(Split_col, "Test", Sq_Error_col)) // MAPE per row (add as column) =ABS(([@Score]-[@Predicted_Score])/[@Score]) // MAPE metric Train_MAPE = AVERAGEIF(Split_col, "Train", MAPE_col) * 100 // Gap and overfitting diagnosis Gap_pct = (Test_RMSE - Train_RMSE) / Train_RMSE * 100 // Baseline: always predict mean — your model must beat this Baseline_MAE = AVERAGEIF(Split_col, "Train", Baseline_Abs_Error_col)
💡
Reading the scorecard: Good model = Test MAE close to Train MAE, RMSE only slightly above MAE, MAPE under 10%, and both metrics clearly better than the baseline. If any of these fail, you have a specific, diagnosable problem — not a vague "bad model."
MAE (Train + Test) calculated
RMSE (Train + Test) calculated
MAPE column + metric done
Gap% calculated
Diagnosis formula added

🎛 Data Table Hyperparameter Sweep
Automate sensitivity testing — find the feature count that minimises test RMSE
Tuning
▼
Data Tables let you run "what if X changes?" automatically across a range of values. Applied to model tuning, you can sweep the number of features from 1 to 6 and record test RMSE for each — finding the sweet spot between underfitting (too few features) and overfitting (too many). This is hyperparameter tuning in Excel.
1
Create sheet "FeatureSweep". Build 6 regression models sequentially — each adding one more feature:
Model 1: StudyHours only
Model 2: + Attendance
Model 3: + Is_Eng
Model 4: + Is_Mkt
Model 5: + Income
Model 6: + Tenure_Days
For each model, run ToolPak Regression on Train rows only. Record Test RMSE.
2
Build the comparison table: Number of Features (1–6) | Train RMSE | Test RMSE | Adj R² | Gap %. Fill in all values from your 6 model runs.
3
Alternative — 1-Variable Data Table: Set up a single prediction formula referencing a "Number of Features" cell (K1). In column A, list values 1–6. In the cell to the right of row 1's blank, put your Test RMSE formula. Select A1:B7 → Data → What-If Analysis → Data Table → Column input cell = K1. Excel calculates Test RMSE for each feature count automatically.
4
Chart the results: Insert a line chart with Number of Features (X) vs both Train RMSE and Test RMSE (two lines). The Train RMSE should decrease or stay flat as features increase. Test RMSE should first decrease (underfitting → better) then increase (overfitting → worse). The minimum of Test RMSE = optimal feature count.
5
Find the optimal feature count: =INDEX(Features_col, MATCH(MIN(TestRMSE_col), TestRMSE_col, 0)). Add a callout box on the chart pointing to the minimum Test RMSE: "✓ Optimal Model — [N] features".
6
Bias-Variance visual: Add a third calculated column: Gap = Test_RMSE − Train_RMSE. Plot as a bar chart alongside the line chart. Low gap = well-generalised. High gap = overfitting. This visual makes the bias-variance tradeoff visible and explainable to any stakeholder.
// 1-Variable Data Table setup: // Column A: 1,2,3,4,5,6 (number of features) // Cell B1: your Test RMSE formula referencing K1 (feature count variable) // Select A1:B7 → Data → What-If Analysis → Data Table // Column input cell: K1 → OK // Excel fills B2:B7 automatically — one RMSE per feature count // Find optimal feature count (minimum Test RMSE) =INDEX(A2:A7, MATCH(MIN(B2:B7), B2:B7, 0)) // Gap between test and train RMSE per model =Test_RMSE - Train_RMSE // % gap (overfitting indicator) =(Test_RMSE - Train_RMSE) / Train_RMSE * 100 // < 10% → well generalised ✓ // > 30% → overfitting → reduce features
🎯
This IS hyperparameter tuning. In sklearn you'd use GridSearchCV to sweep parameters and plot a validation curve — that's exactly what you just built manually in Excel. The Data Table is your GridSearchCV. The Test RMSE vs features chart is your validation curve. The minimum Test RMSE point is your optimal hyperparameter.

🔍 Goal Seek + Scenario Manager
Work backwards from a target — and compare best/base/worst case models
Practice
▼
Goal Seek answers the question "what input produces this exact output?" — it's reverse prediction. Scenario Manager lets you store multiple model configurations and compare them side-by-side. Together they answer the two most common stakeholder questions: "What does a student need to do to pass?" and "How does our model perform under different assumptions?"
1
Goal Seek — what study hours guarantee a 70 score?
In a clean area of your sheet, set up your regression formula:
Input cell (yellow): B2 = StudyHours (start with 4)
Attendance fixed at B3 = 80
Prediction: B4 = =Intercept + β₁*B2 + β₂*B3
Currently B4 shows the predicted score for 4 hours.
2
Run Goal Seek: Data → What-If Analysis → Goal Seek:
Set cell: B4 (the prediction)
To value: 70 (the target score)
By changing cell: B2 (study hours)
Click OK. Excel solves backwards: "What study hours makes the prediction = 70?"
3
Record the answer. Then run Goal Seek again for target = 80 and target = 90. Build a table: Target Score | Required Study Hours. This is your "study plan calculator" — a direct, actionable output from your regression model.
4
Scenario Manager: Data → What-If Analysis → Scenario Manager → Add.
Scenario 1 "Best Case": set β₁=5.5, β₂=0.4 (stronger feature effects)
Scenario 2 "Base Case": your actual trained coefficients
Scenario 3 "Worst Case": β₁=2.8, β₂=0.15 (weaker effects)
Name each scenario and save the changing cells.
5
Click "Summary" in Scenario Manager → select your Test RMSE cell as the result cell → OK. Excel generates a Scenario Summary table showing Test RMSE under each scenario. This is your model sensitivity analysis — how much does performance vary with different assumptions?
6
Add a "Sensitivity" interpretation: if Best Case RMSE and Worst Case RMSE are close → model is robust. If they're far apart → model is highly sensitive to the coefficient values and needs more training data for stability.
// Goal Seek — reverse prediction setup // B2 = Study Hours (variable cell) // B3 = Attendance (fixed at 80) // B4 = prediction formula Prediction = Intercept + β₁*B2 + β₂*B3 // Goal Seek: Data → What-If Analysis → Goal Seek // Set cell: B4 | To value: 70 | By changing: B2 // Result: B2 = hours needed to achieve 70 points // Build the "study plan" table: // Target 60 → Run Goal Seek → Record hours // Target 70 → Run Goal Seek → Record hours // Target 80 → Run Goal Seek → Record hours // Target 90 → Run Goal Seek → Record hours // Scenario Manager summary shows: // Scenario | β₁ | β₂ | Test_RMSE // Best | 5.5| 0.4| 3.8 // Base | 4.2| 0.3| 5.1 // Worst | 2.8|0.15| 7.4
🧠
Goal Seek is deployed ML. When a bank's loan model predicts rejection, they use Goal Seek logic to calculate: "What income level would this applicant need to qualify?" When a student performance model flags risk, Goal Seek calculates: "How many more hours of study would change the prediction to Pass?" This is model outputs made actionable.

Section 4 — Model Health Checklist: A checklist of 8 items, each with a ✓ or ✗:

☐ Test RMSE within 30% of Train RMSE (no overfitting)

Day 9 Pro Tip — Test RMSE is the Only Number That Matters
Your training RMSE is what your model achieves in its comfort zone. Your test RMSE is what it achieves in the real world. Every optimisation decision — feature selection, model complexity, threshold tuning — must be validated against test RMSE, never training RMSE. A model that improves training RMSE but worsens test RMSE is moving in the wrong direction. Always keep your eyes on the test set. It is the only honest judge of whether your model will work when deployed.
