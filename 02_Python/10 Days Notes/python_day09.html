The GIL — Python's Global Interpreter Lock

Why "concurrency" in Python is more nuanced than you'd expect

The GIL ensures only ONE thread executes Python bytecode at a time, even on a multi-core machine. This is the single most important concept for understanding WHY Python offers 3 different concurrency tools instead of one.

🔒 The GIL's Practical Impact
CPU-bound work (heavy computation) → threading does NOT speed this up (GIL blocks true parallelism)
I/O-bound work (waiting on network/disk) → threading DOES help (GIL is released during I/O waits)
Need TRUE parallel CPU work? → use multiprocessing (separate processes, separate GILs)
This single distinction — I/O-bound vs CPU-bound — determines which of today's three tools you should reach for.
💡 I/O-Bound vs CPU-Bound — The Key Question
Ask: "Is my program mostly WAITING (for a network response, disk read, user input) or mostly CALCULATING (crunching numbers, image processing)?" Waiting → threading/asyncio. Calculating → multiprocessing.
🧵

threading — Concurrent I/O-Bound Work

Multiple threads sharing memory, useful when waiting on I/O

PYTHON
import threading
import time

def download_file(name, delay):
    print(f"Starting {name}...")
    time.sleep(delay)   # simulates waiting on a network request
    print(f"Finished {name}")

# Sequential — takes 3+2+1 = 6 seconds total
start = time.time()
download_file("A", 3); download_file("B", 2); download_file("C", 1)
print(f"Sequential took {time.time()-start:.1f}s")

# Threaded — all three run CONCURRENTLY, total ≈ 3 seconds (the longest one)
start = time.time()
threads = [
    threading.Thread(target=download_file, args=("A", 3)),
    threading.Thread(target=download_file, args=("B", 2)),
    threading.Thread(target=download_file, args=("C", 1)),
]
for t in threads: t.start()
for t in threads: t.join()   # wait for ALL threads to finish
print(f"Threaded took {time.time()-start:.1f}s")

# Race conditions — when threads modify SHARED data unsafely
counter = 0
lock = threading.Lock()

def increment():
    global counter
    with lock:              # ensures only ONE thread modifies counter at a time
        counter += 1
⚠️ Race Conditions Are Real, Even With the GIL
The GIL prevents two threads from running Python bytecode SIMULTANEOUSLY, but operations like counter += 1 actually involve MULTIPLE bytecode steps — a thread can be interrupted mid-operation, causing lost updates. Always use a threading.Lock() when multiple threads modify shared state.
⚙️

multiprocessing — True Parallel CPU Work

Separate processes, separate memory, separate GILs

PYTHON
from multiprocessing import Process, Pool
import time

def cpu_heavy_task(n):
    return sum(i*i for i in range(n))   # genuinely CPU-intensive work

if __name__ == "__main__":   # REQUIRED guard for multiprocessing on Windows/macOS

    # Manual Process approach
    p1 = Process(target=cpu_heavy_task, args=(10_000_000,))
    p2 = Process(target=cpu_heavy_task, args=(10_000_000,))
    p1.start(); p2.start()
    p1.join(); p2.join()   # these TRULY run in parallel on separate CPU cores

    # Pool — easier way to parallelize the SAME function over many inputs
    with Pool(processes=4) as pool:
        results = pool.map(cpu_heavy_task, [1_000_000]*8)   # 8 tasks across 4 processes
        print(results)
Featurethreadingmultiprocessing
True CPU parallelism?❌ No (blocked by GIL)✅ Yes (separate processes)
MemoryShared between threadsSeparate per process (more overhead)
Best forI/O-bound (network, disk, waiting)CPU-bound (heavy computation)
Startup costLightweightHeavier (new process/interpreter)
⚠️ The if __name__ == "__main__" Guard is Mandatory
On Windows (and sometimes macOS), multiprocessing RE-IMPORTS your script in each new process. Without the guard, this causes infinite recursive process spawning. ALWAYS wrap multiprocessing code that starts new processes in this guard.

asyncio — Cooperative Concurrency

Handling thousands of I/O tasks in a single thread

asyncio uses a single thread but switches between many tasks COOPERATIVELY — each task voluntarily yields control (via await) whenever it's waiting, letting other tasks run. Ideal for thousands of concurrent network requests.

PYTHON
import asyncio

async def download_file(name, delay):
    print(f"Starting {name}...")
    await asyncio.sleep(delay)   # non-blocking "wait" — lets OTHER tasks run meanwhile
    print(f"Finished {name}")
    return f"{name} done"

async def main():
    # asyncio.gather runs multiple coroutines CONCURRENTLY
    results = await asyncio.gather(
        download_file("A", 3),
        download_file("B", 2),
        download_file("C", 1),
    )
    print(results)   # total time ≈ 3s, not 6s — same concurrency benefit as threading, single thread

asyncio.run(main())   # the entry point that starts the event loop
⚡ async/await Vocabulary
async def → defines a COROUTINE function (doesn't run immediately when called)
await → pauses THIS coroutine, letting other tasks run, until the awaited thing completes
asyncio.run() → the top-level entry point that starts the event loop
asyncio.gather() → runs multiple coroutines concurrently, waits for all to finish
💡 threading vs asyncio for I/O-Bound Work
Both achieve similar concurrency for I/O-bound tasks. asyncio uses a SINGLE thread with cooperative task-switching (lower overhead, scales to THOUSANDS of tasks, but requires "async-aware" libraries). threading uses OS-level threads (works with any existing blocking code, but has more per-thread overhead and only scales to hundreds, not thousands).

concurrent.futures — A Unified, Simpler Interface

ThreadPoolExecutor and ProcessPoolExecutor

PYTHON
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def fetch_url(url):
    # simulate a network call
    import time; time.sleep(1)
    return f"Fetched {url}"

urls = ["site1.com", "site2.com", "site3.com", "site4.com"]

# ThreadPoolExecutor — for I/O-bound tasks, higher-level than manual threading.Thread
with ThreadPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(fetch_url, urls))
    print(results)   # all 4 urls "fetched" concurrently, ~1s total instead of 4s

# ProcessPoolExecutor — for CPU-bound tasks, same interface as ThreadPoolExecutor
def square(n):
    return n * n

if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=4) as executor:
        results = list(executor.map(square, range(10)))
        print(results)
✅ concurrent.futures is Often the Best Starting Point
It offers the SAME simple .map() and .submit() interface for BOTH threads and processes — just swap ThreadPoolExecutor for ProcessPoolExecutor depending on whether your task is I/O-bound or CPU-bound. More convenient than manually managing raw Thread/Process objects.

    return count
