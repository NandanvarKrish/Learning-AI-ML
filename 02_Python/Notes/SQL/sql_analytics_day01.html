What is SQL, and Why Analysts Use It

The idea in one minute

SQL (Structured Query Language) is the language you use to ask a database questions. You describe the result you want (for example, total revenue per station), and the database decides how to find it. That single idea is why analysts use SQL: the database holds millions of rows, and a spreadsheet cannot.

Real-world reason

The operations team exports 2 million trip records. Opened in a spreadsheet, the file crashes or takes minutes to filter. In SQL, the same question runs inside the database in seconds, and the answer is a few rows you can check and paste into a report.

This course uses MariaDB (the database inside XAMPP). MySQL uses the same syntax for everything in Day 1, so the notes apply to both.

Databases, Tables, Rows and Columns

The vocabulary you will use every day

A database is a named container for related tables. A table stores one kind of thing, with fixed columns. Each row is one record (one trip), and each column is one attribute (its fare, say), with a fixed data type.

ConceptSpreadsheet equivalentIn bike_analytics
DatabaseA workbookbike_analytics
TableA sheettrips, stations
RowA line of dataOne trip
ColumnA header with a typefee_inr, a DECIMAL(8,2)

The data types you will meet

  • INT: whole numbers, used for IDs and minutes.
  • CHAR(3): fixed-length text. Every bike ID here is exactly three characters, such as B07.
  • VARCHAR(16): variable-length text up to 16 characters, used for station names.
  • ENUM('classic','electric'): one value from a fixed list. The database rejects anything else.
  • DECIMAL(8,2): exact decimal numbers with two places. Use it for money, never FLOAT.
  • DATETIME: a date and time, such as 2026-08-07 13:29:00. DATE keeps only the date.

Keys: how tables are linked and kept clean

A primary key identifies each row uniquely and cannot be empty; trips.trip_id is the primary key. A foreign key points to another table: trips.start_station must match a name in stations, so a trip cannot start at a station that does not exist.

Your First SELECT

Columns, aliases, DISTINCT and LIMIT

A SELECT statement names the columns you want and the table they come from. Add LIMIT while exploring, so you see a sample and not two million rows.

syntax
SELECT column1, column2
FROM   table_name
LIMIT  10;

Look at the first rows

Name the columns you need. ORDER BY trip_id makes the sample repeatable: the same five rows come back every time. Sorting is covered properly on Day 3.

SQL
SELECT trip_id, bike_type, minutes, fee_inr FROM trips ORDER BY trip_id LIMIT 5

DISTINCT lists each value once. Use it to see which categories exist in a column, such as the status values, before you write filters.

Counting Rows Correctly

COUNT, COUNT(column), COUNT(DISTINCT) and NULL

Counting is the first real analysis most people do. The three forms look similar but mean different things.

ExpressionCounts
COUNT(*)every row
COUNT(column)rows where that column is not NULL
COUNT(DISTINCT column)different values in that column, ignoring NULL

Three different counts

Two numbers that should match in a clean table: all rows and unique IDs. When they differ, the table has duplicates, which is the first thing to check.

SQL
SELECT COUNT(*) AS all_rows, COUNT(DISTINCT trip_id) AS unique_trip_ids, COUNT(DISTINCT bike_id) AS bikes FROM trips
all_rowsunique_trip_idsbikes
40040012

NULL is not counted

NULLIF(a, b) returns NULL when the two values are equal. So COUNT skips every cancelled trip. This is how an analyst counts a subset before the filter topic arrives on Day 2.

SQL
SELECT COUNT(*) AS all_rows, COUNT(NULLIF(status, 'cancelled')) AS not_cancelled FROM trips
all_rowsnot_cancelled
400377

The Order Your Query Really Runs In

Why aliases and WHERE behave the way they do

A query is written in one order and runs in another. This explains most confusing error messages.

order
Written order:  SELECT  ->  FROM  ->  WHERE  ->  GROUP BY  ->  HAVING  ->  ORDER BY  ->  LIMIT
Runs in order:  FROM  ->  WHERE  ->  GROUP BY  ->  HAVING  ->  SELECT  ->  ORDER BY  ->  LIMIT
Why this matters

The database reads FROM first and only then the SELECT list. So an alias you define in SELECT does not exist yet in WHERE. That is why WHERE revenue > 5000 fails when revenue is an alias, and why you will meet this again on Days 2 and 6.

Real-World Examples

Four situations from finance, operations, data engineering and product

Scenario 1 — Finance: does the export match the ops total?

Finance asks you to reconcile the export before the board pack. Two totals, one query: the number of trips and the revenue. You compare them with the figure the ops dashboard shows. If they differ, stop and find out why before you report anything.

SQL
SELECT COUNT(*) AS trips, ROUND(SUM(fee_inr), 2) AS revenue_inr FROM trips
tripsrevenue_inr
40023476.00

Scenario 2 — Operations: how far back does the data go?

Before you say 'monthly revenue is up', confirm the data covers the months you are comparing. Here the last trip is on 28 October, so October is a partial month. A report that treats it as complete would understate the month, and Day 9 shows how to handle it.

SQL
SELECT MIN(started_at) AS first_trip, MAX(started_at) AS last_trip, COUNT(DISTINCT DATE(started_at)) AS days_with_trips FROM trips
first_triplast_tripdays_with_trips
2026-07-01 00:00:002026-10-28 23:43:00120

Scenario 3 — Data engineering: are the IDs unique after the merge?

A merge of two files can repeat IDs, and every downstream total is then inflated. Equal numbers here mean each trip appears once. If the second number is smaller, you have duplicates, and you must not sum fees until you know which copy is right.

SQL
SELECT COUNT(*) AS rows_in_table, COUNT(DISTINCT trip_id) AS unique_ids FROM trips
rows_in_tableunique_ids
400400

Scenario 4 — Product: what stations does the directory list?

A station directory is a reference table. Before you join trips to it, look at it: a station missing from this list will silently drop its trips from any join you write on Day 5.

Common Mistakes

Fix these before they reach a board pack

MistakeWhat goes wrongFix
Trusting SELECT * in a reportA new column changes the report's shape without warningName the columns you need
Counting without checking duplicatesTotals are inflated when IDs repeatCompare COUNT(*) with COUNT(DISTINCT id) first
Forgetting the end of a dayA DATETIME range ending at midnight drops the last dayCheck the time part of every range (Day 2)
Using an alias in WHEREError: unknown column, because WHERE runs before SELECTRepeat the expression, or use a subquery (Day 6)
Assuming the table is completePartial months and missing days look like falling demandRun the coverage check before any trend
Ignoring NULL in averages and countsCOUNT(column) and AVG silently skip NULL valuesCount NULL separately with IS NULL (Day 2)

Capstone: The First Audit

The real-world task for Day 1

Capstone: The First Audit

The board meets on Friday and the operations director wants one page of numbers. Before anyone builds a chart, you must prove the data is complete and consistent. Your audit decides what can be published.

5 phases10 queries1 audit note
1

Set up and map the tables

30 min▼

Load 00_seed.sql. Then run SHOW TABLES and DESCRIBE on both tables. Write down, for each table, the primary key and every column that is NOT NULL.

  • Both tables appear in SHOW TABLES
  • You can name the primary key of each table
  • You can list the NOT NULL columns of trips
2

Answer the ten audit questions

60 min▼

Answer each question with one query, and write the result beside it in your notes.

  1. How many trips are in the table?
  2. How many unique trip IDs are there? (They should equal Q1.)
  3. How many bikes are in the fleet?
  4. How many stations are there?
  5. What is the first and last trip date and time?
  6. On how many different days did a trip start?
  7. What is the total revenue, to two decimal places?

Hint for Q5 and Q6: use MIN, MAX and COUNT(DISTINCT DATE(started_at)).

3

Test the owner's claim about the fleet

30 min▼

The owner says the fleet has 12 bikes. Test that claim with a query, and say in one sentence whether the data supports it. Then look at the stations table: which station opened last, and when? Check the answer against the stations listing, not from memory.

  • Bike count query written and explained
  • Claim confirmed or corrected with evidence
  • Newest station identified with its opening date
4

Write the audit note

30 min▼

Write a short audit note, five lines, for the board pack. Each line states a number, the query behind it, and whether it passed a check. Put the queries in day01_audit.sql.

Note template

Trips: __ (rows) / __ (unique IDs) — pass/fail. Coverage: __ to __, __ days with trips. Fleet: __ bikes. Revenue: Rs __. Open issues: __.

5

Stretch: find something unexpected

20 min▼

Stretch task (optional). Find one thing in the data you did not expect and explain it in one sentence. Examples to look for: a column whose values are all the same, an ID pattern, or a date gap.
