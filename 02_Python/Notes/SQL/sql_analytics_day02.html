WHERE: Keeping the Rows You Need

The filter runs before everything else

WHERE keeps only the rows for which a condition is TRUE. Rows where it is FALSE, or where the answer is unknown (NULL), are dropped. Everything you learned on Day 1 about counting still applies, but now it counts the rows that survive the filter.

syntax
SELECT columns
FROM   table
WHERE  condition        -- a row is kept only if this is TRUE
LIMIT  10;
OperatorMeaningExample

<> or !=not equalstatus <> 'cancelled'

Long completed rides

Two conditions joined by AND: both must be true. The ORDER BY and LIMIT just make the sample repeatable.

SQL
SELECT trip_id, minutes, fee_inr FROM trips WHERE status = 'completed' AND minutes > 60 ORDER BY trip_id LIMIT 8

The statement runs and returns no result set.

AND, OR and NOT: Logic and Precedence

Where most filter bugs start

AND needs both sides to be true. OR needs at least one. NOT flips a condition. The precedence rule is the trap: AND is evaluated before OR, so a query without parentheses can mean something you did not intend.

OR: cancelled or free

A cancelled ride has a zero fee, so the two groups overlap. The count is 23, not 46. Overlap is normal, and a query that adds two counts must subtract it.

SQL
SELECT COUNT(*) AS cancelled_or_zero_fee FROM trips WHERE status = 'cancelled' OR fee_inr = 0
cancelled_or_zero_fee
23

Precedence trap (no parentheses)

Read as (electric AND cancelled) OR classic. Every classic trip is included, completed or not. This returns 212 rows.

SQL
SELECT COUNT(*) AS no_parentheses FROM trips WHERE bike_type = 'electric' AND status = 'cancelled' OR bike_type = 'classic'
no_parentheses
212

Same words, with parentheses

Now it reads as: electric, AND either cancelled or classic. Only 12 rows. Put parentheses wherever you mix AND and OR, even when you think the default is right.

SQL
SELECT COUNT(*) AS with_parentheses FROM trips WHERE bike_type = 'electric' AND (status = 'cancelled' OR bike_type = 'classic')
with_parentheses
12

NOT

Gives the same result as status <> 'completed' here, because status is never NULL. The NOT form reads more naturally for some conditions.

SQL
SELECT COUNT(*) AS not_completed FROM trips WHERE NOT (status = 'completed')
not_completed
23

BETWEEN and Dates: The End-of-Day Trap

A range that silently loses a day

BETWEEN a AND b is inclusive at both ends, and it is shorthand for x >= a AND x <= b. With a DATETIME column, the end value matters: a bare date means midnight at the start of that day.

The end-of-day trap

The first number treats 31 August as midnight, so every trip after 00:00 on the 31st is dropped: 100 instead of 103. Three real trips vanish with no error message. Always end a datetime range at 23:59:59, or use < '2026-09-01'.

SQL
SELECT COUNT(*) AS wrong_end, (SELECT COUNT(*) FROM trips WHERE started_at BETWEEN '2026-08-01' AND '2026-08-31 23:59:59') AS right_end FROM trips WHERE started_at BETWEEN '2026-08-01' AND '2026-08-31'
wrong_endright_end
100103

Fare band with BETWEEN

100 and 200 are both included. For a number column, BETWEEN has no trap, so write it as the bounds you mean.

SQL
SELECT COUNT(*) AS mid_fare FROM trips WHERE status = 'completed' AND fee_inr BETWEEN 100 AND 200
mid_fare
32

IN and LIKE: Lists and Patterns

Membership and text matching

IN (...) tests membership in a list. LIKE tests a pattern: % means any run of characters, and _ means exactly one character.

A list of values

Same as zone = 'Core' OR zone = 'Campus', but shorter and easier to extend. NOT IN is the opposite.

SQL
SELECT name, zone FROM stations WHERE zone IN ('Core', 'Campus') ORDER BY name
namezone
CENTRALCore
MARKETCore
UNIVERSITYCampus

Pattern matching

_TADIUM matches any single first letter followed by TADIUM: STADIUM. H% matches any name that starts with H.

SQL
SELECT name FROM stations WHERE name LIKE '_TADIUM' OR name LIKE 'H%' ORDER BY name
name
HARBOUR
STADIUM

Searching for a half-remembered name

A leading % searches inside the name. Useful when a station name in another system is spelled differently.

SQL
SELECT name FROM stations WHERE name LIKE '%SIDE%'
name
RIVERSIDE

NULL: Unknown Is Not Zero

Why = NULL never matches

NULL means unknown, not zero and not an empty string. Comparisons with NULL are never TRUE, not even NULL = NULL. Use IS NULL and IS NOT NULL instead.

Why = NULL does not work

The first result is NULL (unknown), so a filter on it would drop every row. The second is 1 (TRUE). This is the single most common SQL bug in analyst work.

SQL
SELECT NULL = NULL AS equals_test, NULL IS NULL AS is_null_test
equals_testis_null_test
NULL1

Finding missing values

This data has no missing end stations, so the answer is 0. The check is still worth running: a zero here is a result, and a non-zero would be a finding.

SQL
SELECT COUNT(*) AS missing_end_station FROM trips WHERE end_station IS NULL
missing_end_station
0

Text Case and Collation

What counts as the same value

In MariaDB's default collation, text comparisons ignore case: 'COMPLETED' matches 'completed'. Other databases and collations behave differently, so do not rely on it when you move to a different system.

Case-insensitive match

Returns 377, the same as the lowercase search. Your notes should say which collation you assumed when you wrote a filter.

SQL
SELECT COUNT(*) AS upper_case_search FROM trips WHERE status = 'COMPLETED'
upper_case_search
377

Real-World Examples

Four filters from operations, pricing, marketing and data quality

Scenario 1 — Operations: is the electric fleet cancelling more?

The operations lead sees electric bikes cancelled more often in the news. Count the cancellations for one bike type first, then compare with the other type on the next line. A single count is a starting point, not a conclusion: you still need the total for each type.

SQL
SELECT COUNT(*) AS electric_cancelled FROM trips WHERE bike_type = 'electric' AND status = 'cancelled'
electric_cancelled
12

Scenario 2 — Pricing review: how many rides sit in the mid band?

The pricing team wants to know how many completed rides fall between Rs 100 and Rs 200. The filter answers the question directly, and the boundaries are stated in the query so the team can change them.

SQL
SELECT COUNT(*) AS mid_band_rides FROM trips WHERE status = 'completed' AND fee_inr BETWEEN 100 AND 200
mid_band_rides
32

Scenario 3 — Marketing: September rides from two waterfront stations

A campaign report for September. The end date is 23:59:59 on purpose: the trips on 30 September evening belong in September. A wrong end date would under-report the campaign.

SQL
SELECT COUNT(*) AS sept_waterfront_departures FROM trips WHERE start_station IN ('HARBOUR', 'RIVERSIDE') AND started_at BETWEEN '2026-09-01' AND '2026-09-30 23:59:59'
sept_waterfront_departures
32

Scenario 4 — Data quality: are there impossible rows?

A completed ride with zero minutes is a data error. Check it with a filter: the expected answer is 0. Pair it with a second rule, cancelled rides with a fee, which is also 0 here.

SQL
SELECT COUNT(*) AS completed_zero_minutes FROM trips WHERE status = 'completed' AND minutes = 0
completed_zero_minutes
0
