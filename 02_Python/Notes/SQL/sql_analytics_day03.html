Sort, Rank and Page

ORDER BY: Sorting the Result

Where the sort sits in a query

ORDER BY sorts the result. It runs after WHERE has filtered the rows and after the columns are chosen, and before LIMIT cuts the result down. Ascending is the default; DESC puts the largest first.

syntax
SELECT columns
FROM   table
WHERE  condition
ORDER BY column1 [ASC|DESC], column2 [ASC|DESC]
LIMIT  n [OFFSET m];

Highest fares first

Sorted by fare, largest first. The second key, trip_id, is the tie-breaker. The top fare is 123.00, and 32 completed trips share it, so without the tie-breaker these five rows would be an arbitrary choice from those 32.

SQL
SELECT trip_id, fee_inr FROM trips WHERE status = 'completed' ORDER BY fee_inr DESC, trip_id LIMIT 5

Sorting by an alias

MariaDB lets ORDER BY use a name from the SELECT list. Other databases may not, so repeat the expression if you need portability.

SQL
SELECT trip_id, fee_inr AS fee FROM trips WHERE status = 'completed' ORDER BY fee DESC, trip_id LIMIT 3

Tie-Breakers: Making Order Stable

Equal values need a unique last key

A sort key with ties returns equal rows in an order the database does not promise. Run the same query twice on a busy system and the middle of the list can change. Add a unique column as the last key, and the order is fixed.

Ties are common

This counts start times that are shared by more than one trip: 120 of them. Sorting by started_at alone is not enough for a page of results. (GROUP BY and HAVING come on Day 4; this is a preview.)

SQL
SELECT COUNT(*) AS trips_sharing_a_start_time FROM (SELECT started_at FROM trips GROUP BY started_at HAVING COUNT(*) > 1) t
trips_sharing_a_start_time
120

LIMIT and OFFSET: Top N and Paging

Taking the first rows, then the next

LIMIT n returns at most n rows. LIMIT n OFFSET m skips m rows first. A page of size 10 for page p is LIMIT 10 OFFSET (p - 1) * 10. Without ORDER BY, LIMIT returns some rows, but the database does not say which.

Page 2 of trips by start time

Page 1 is rows 1 to 10, page 2 is rows 11 to 20. The offset is (2 - 1) × 10 = 10. Always page with the same sort key, or the pages will overlap.

SQL
SELECT trip_id, started_at FROM trips ORDER BY started_at, trip_id LIMIT 10 OFFSET 10

NULL in Sorting

Where unknown values land

NULL is unknown, so the database must decide where it goes. In MariaDB an ascending sort puts NULL first, and a descending sort puts it last. A query for the 'cheapest' item can return a NULL row first unless you guard against it.

NULL sorts first in ascending order

The NULL row comes first. Here it is a toy table; on the trips table, a missing fee would behave the same way.

SQL
SELECT x FROM (SELECT NULL AS x UNION ALL SELECT 1 UNION ALL SELECT 2) t ORDER BY x
x
NULL
1
2

Cheapest completed electric ride

The IS NOT NULL guard from Day 2 makes the 'cheapest' answer mean a real fee. Trip 8, at 21.00, is the cheapest completed electric ride.

SQL
SELECT trip_id, fee_inr FROM trips WHERE status = 'completed' AND bike_type = 'electric' AND fee_inr IS NOT NULL ORDER BY fee_inr, trip_id LIMIT 1
trip_idfee_inr
821.00

Text Sorts Differently from Numbers

A common reason for a wrong top list

Sorting compares characters when the column holds text. Digits are compared one character at a time, so '100' sorts before '9'. Store numbers as numbers, or compare them as numbers, and this problem goes away.

Text numbers sort as text

The order is 10, 100, 9. Nothing is wrong with the database here; the values are text, so the sort is alphabetical.

SQL
SELECT x FROM (SELECT '9' AS x UNION ALL SELECT '10' UNION ALL SELECT '100') t ORDER BY x
x
10
100
9

Common Mistakes

Fix these before they reach a report

MistakeWhat goes wrongFix
LIMIT without ORDER BYReturns some rows, but which ones is not definedAlways sort before you limit
ORDER BY with ties and no unique keyThe same report can change between runs; pages can repeat or skip rowsAdd trip_id as the last key
Cheapest or lowest with NULL presentA NULL row is returned first in an ascending sortAdd AND fee_inr IS NOT NULL
OFFSET for a deep page on a big tableThe database reads and discards all earlier rows, so it gets slower with each pageNote it; keyset paging is a later topic
Numbers stored as text'9' sorts after '100'Store numbers as numbers
Sorting by a column you did not selectWorks in most systems, but the output can look unsorted to a readerSelect the column you sort by, or say so in the notes
Assuming DESC puts NULL firstIn MariaDB, NULLs come last in DESC orderGuard with IS NOT NULL to be sure
