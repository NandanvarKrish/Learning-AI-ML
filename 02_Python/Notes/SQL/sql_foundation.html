Change the Data and the Structure

Insert, update and delete rows safely, group changes into transactions, alter tables that already hold data, and drop what you no longer need. Every statement runs on the server, and every refusal shows its real error.

Every result on this page was produced by the server. The dangerous statements are shown on copies, so the lesson never damages the practice data.

Customers, products, orders and order lines

SQL
CREATE TABLE customers (
    customer_id INT AUTO_INCREMENT PRIMARY KEY,
    email       VARCHAR(100) NOT NULL UNIQUE,
    full_name   VARCHAR(60)  NOT NULL,
    city        VARCHAR(40)  NULL,
    joined_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE products (
    sku          CHAR(6)       PRIMARY KEY,
    product_name VARCHAR(80)   NOT NULL,
    price        DECIMAL(8,2)  NOT NULL CHECK (price >= 0),
    stock        INT           NOT NULL DEFAULT 0 CHECK (stock >= 0)
);
CREATE TABLE orders (
    order_id    INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL,
    placed_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    status      ENUM('pending','paid','shipped','cancelled') NOT NULL DEFAULT 'pending',
    CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
CREATE TABLE order_items (
    order_id   INT NOT NULL,
    sku        CHAR(6) NOT NULL,
    qty        INT NOT NULL CHECK (qty > 0),
    unit_price DECIMAL(8,2) NOT NULL,
    PRIMARY KEY (order_id, sku),
    CONSTRAINT fk_items_order   FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE CASCADE,
    CONSTRAINT fk_items_product FOREIGN KEY (sku) REFERENCES products(sku)
);

Runs without a result set.

Inserting Rows

Defaults, copies and INSERT ... SELECT

A row with some columns left to their defaults

Columns you leave out take their defaults. stock has DEFAULT 0, so the new product starts with no stock.

SQL
INSERT INTO products (sku, product_name, price) VALUES ('P005', 'Stapler', 120.00);

Runs without a result set.

Check the new row

Stock is 0, from the default.

SQL
SELECT sku, stock FROM products WHERE sku = 'P005'
skustock
P0050

Copy the structure of a table, with no rows

CREATE TABLE ... AS SELECT makes a table from a query's result. WHERE 1 = 0 returns no rows, so the new table is empty.

SQL
CREATE TABLE order_archive AS SELECT * FROM orders WHERE 1 = 0;

Runs without a result set.

The copy has no primary key

The columns came across, but the PRI key did not. A copy made this way loses its keys and rules, so add them yourself if you need them.

SQL

FieldTypeNullKeyDefaultExtra
order_idint(11)NO0
customer_idint(11)NONULL
placed_atdatetimeNOcurrent_timestamp()
statusenum('pending','paid','shipped','cancelled')NOpending

Insert the shipped orders from a query

INSERT ... SELECT copies rows that a query returns. Here, one shipped order.

SQL
INSERT INTO order_archive SELECT * FROM orders WHERE status = 'shipped';

The archived rows

Order 3 is in the archive.

Updating Rows

WHERE decides which rows change

Update the rows that match a WHERE

UPDATE changes the rows its WHERE selects, and only those. SET computes the new value from the old one.

SQL
UPDATE products SET stock = stock - 2 WHERE sku = 'P001';

Runs without a result set.

Check the stock levels

Only P001 moved, from 20 to 18.

SQL
SELECT sku, stock FROM products ORDER BY sku

Change an order's status

Order 2 moves from pending to paid.

SQL
UPDATE orders SET status = 'paid' WHERE order_id = 2;

Runs without a result set.

A status outside the ENUM is refused on update too

The same ENUM rule applies to updates. Nothing changes.

SQL
UPDATE orders SET status = 'refunded' WHERE order_id = 2;
Server response
ERROR 1265 (01000) at line 1: Data truncated for column 'status' at row 1

A copy, to try the dangerous form safely

Practise risky statements on a copy, never on the only copy of the data.

SQL
CREATE TABLE stock_copy AS SELECT * FROM products;

Runs without a result set.

UPDATE with no WHERE changes every row

There is no WHERE, so every row matches. The server does not ask for confirmation. This is the most common data-loss mistake in SQL.

SQL
UPDATE stock_copy SET stock = 0;

Runs without a result set.

Every row was changed

Every product now shows stock 0, including P001 and P002 which should have kept their stock.

SQL
SELECT sku, stock FROM stock_copy ORDER BY sku
skustock
P0010
P0020
P0030
P0050

Remove the copy

The copy is no longer needed. The real products table was never touched.

SQL
DROP TABLE stock_copy;

Runs without a result set.

Deleting Rows and Emptying Tables

DELETE, TRUNCATE and DROP are three different things

Order 3 and its lines before the delete

One order and one line for it.

SQL
SELECT (SELECT COUNT(*) FROM orders WHERE order_id = 3) AS order_count, (SELECT COUNT(*) FROM order_items WHERE order_id = 3) AS line_count
order_countline_count
11

Delete an order

The order is removed. Its order lines are removed too, because of ON DELETE CASCADE from Day 0.

SQL
DELETE FROM orders WHERE order_id = 3;

Runs without a result set.

The lines went with the order

Both counts are zero. The archive copy still holds order 3, because it is a separate table with no foreign key.

SQL
SELECT (SELECT COUNT(*) FROM orders WHERE order_id = 3) AS order_count, (SELECT COUNT(*) FROM order_items WHERE order_id = 3) AS line_count
order_countline_count
00

A copy of order lines, to compare the three ways to empty a table

Use a copy again, so the real lines stay safe.

SQL
CREATE TABLE lines_copy AS SELECT * FROM order_items;

Runs without a result set.

TRUNCATE empties the table and keeps its structure

TRUNCATE removes all rows quickly and keeps the table. It cannot be rolled back and resets auto-numbering.

SQL
TRUNCATE TABLE lines_copy;

Runs without a result set.

The table is empty but still exists

Zero rows, and the table is still there.

SQL
SELECT COUNT(*) FROM lines_copy
COUNT(*)
0

DROP removes the table itself

DROP deletes the structure and the data. Nothing can read the table afterwards.

SQL
DROP TABLE lines_copy;

Runs without a result set.

Reading a dropped table fails

The server cannot find the table, so it refuses the query.

SQL
SELECT * FROM lines_copy;
Server response
ERROR 1146 (42S02) at line 1: Table 'learn_sql.lines_copy' doesn't exist

Insert or Update in One Step

ON DUPLICATE KEY UPDATE

Insert, or add to the stock if the product already exists

P001 already exists, so the duplicate-key rule would normally refuse this. ON DUPLICATE KEY UPDATE changes the existing row instead, adding 5 to its stock.

SQL
INSERT INTO products (sku, product_name, price, stock) VALUES ('P001', 'Notebook A5', 49.50, 5)
ON DUPLICATE KEY UPDATE stock = stock + VALUES(stock);

Runs without a result set.

P001 now has 23

18 plus 5 is 23.

SQL
SELECT sku, stock FROM products WHERE sku = 'P001'
skustock
P00123

Transactions: All or Nothing

ROLLBACK, COMMIT and a failure midway

Stock before the attempt

150 pens in stock.

SQL
SELECT sku, stock FROM products WHERE sku = 'P002'
skustock
P002150

A change that is rolled back

A transaction groups statements so they succeed or fail together. ROLLBACK undoes everything since START TRANSACTION. These three statements run in one session.

SQL
START TRANSACTION;
UPDATE products SET stock = stock - 5 WHERE sku = 'P002';
ROLLBACK;

Runs without a result set.

After the rollback, nothing changed

Still 150. The rollback worked.

SQL
SELECT sku, stock FROM products WHERE sku = 'P002'
skustock
P002150

A sale that is committed

COMMIT makes the order and the stock change permanent. Both happen, or neither does.

SQL
START TRANSACTION;
INSERT INTO orders (customer_id, status) VALUES (1, 'pending');
UPDATE products SET stock = stock - 5 WHERE sku = 'P002';
COMMIT;

Runs without a result set.

The committed change is visible

Now 145.

SQL
SELECT sku, stock FROM products WHERE sku = 'P002'
skustock
P002145

A failing step inside a transaction undoes the rest

Taking 1000 units of a product with 0 in stock breaks the CHECK (stock >= 0) rule. The session stops before COMMIT, so the open change is discarded.

SQL
START TRANSACTION;
UPDATE products SET stock = stock - 1000 WHERE sku = 'P003';
COMMIT;
Server response
ERROR 4025 (23000) at line 2: CONSTRAINT `products.stock` failed for `learn_sql`.`products`

Stock for P003 is still zero

The refused change never happened.

SQL
SELECT sku, stock FROM products WHERE sku = 'P003'
skustock
P0030

Changing a Table's Structure

ALTER TABLE: add, change, rename, drop, add a rule

Add a column

ALTER TABLE changes a table that already exists. The new column is empty for existing rows.

SQL
ALTER TABLE customers ADD COLUMN phone VARCHAR(15) NULL AFTER city;

Runs without a result set.

Change a column's size and rule

MODIFY changes the type or rules, keeping the name. Existing values must still fit.

SQL
ALTER TABLE customers MODIFY COLUMN full_name VARCHAR(100) NOT NULL;

Runs without a result set.

Rename a column

CHANGE renames and redefines in one step. It works on every MariaDB version, including the XAMPP 10.4 you may use. RENAME COLUMN needs 10.5.2 or later.

SQL
ALTER TABLE customers CHANGE COLUMN city town VARCHAR(40) NULL;

Runs without a result set.

The structure now

phone is there and town replaces city.

SQL
DESCRIBE customers
FieldTypeNullKeyDefaultExtra
customer_idint(11)NOPRINULLauto_increment
emailvarchar(100)NOUNINULL
full_namevarchar(100)NONULL
townvarchar(40)YESNULL
phonevarchar(15)YESNULL
joined_atdatetimeNOcurrent_timestamp()

Add a rule to an existing table

Existing rows already pass, so the rule is added. New rows must pass it too.

SQL
ALTER TABLE products ADD CONSTRAINT chk_name_len CHECK (CHAR_LENGTH(product_name) >= 2);

Runs without a result set.

The new rule refuses a one-letter name

The rule applies to new data from now on.

SQL
INSERT INTO products (sku, product_name, price) VALUES ('P009', 'X', 1.00);
Server response
ERROR 4025 (23000) at line 1: CONSTRAINT `chk_name_len` failed for `learn_sql`.`products`

Remove the column again

DROP COLUMN deletes the column and its values. Check first that nothing uses it.

SQL
ALTER TABLE customers DROP COLUMN phone;

Runs without a result set.

Indexes

Faster lookups, and their cost

Create an index on a column you often filter by

An index is a sorted lookup structure. It speeds up searches on that column and costs some space and some time on every write.

SQL
CREATE INDEX idx_orders_status ON orders (status);

Runs without a result set.

The indexes on the orders table

The primary key, the new index, and the index MariaDB created for the foreign key automatically.

SQL
SELECT INDEX_NAME, COLUMN_NAME FROM information_schema.STATISTICS WHERE TABLE_SCHEMA = 'learn_sql' AND TABLE_NAME = 'orders' ORDER BY INDEX_NAME

idx_orders_statusstatus

Remove the index

Dropping an index does not touch the data, only the lookup structure.

SQL
DROP INDEX idx_orders_status ON orders;

Runs without a result set.

Renaming and Dropping Tables

Permanent, so be sure first

Rename a table

The rows and structure stay the same. Only the name changes.

SQL
RENAME TABLE order_archive TO archived_orders;

Runs without a result set.

Find it by its new name

Found under the new name.

SQL
SHOW TABLES LIKE 'archived%'
Tables_in_learn_sql (archived%)
archived_orders

Drop a table you no longer need

Dropping is permanent. DROP TABLE IF EXISTS does the same without an error when the table is already gone.

SQL
DROP TABLE archived_orders;

Runs without a result set.

The dropped table is gone

The table no longer exists.

SQL
SELECT * FROM archived_orders;

Real-World: Changing a Live Database Safely

The habits that prevent data loss

SituationSafe approachWhy
An UPDATE or DELETE on productionRun a SELECT with the same WHERE first, check the count, then changeYou see exactly which rows will change
Several statements that must agreeSTART TRANSACTION, then COMMIT or ROLLBACKPartial changes never remain
A risky schema changeTest it on a copy first, then apply itA mistake stays in the copy
Removing old dataCopy to an archive table, check it, then deleteThe data survives a wrong delete
A new rule on existing dataCheck the existing rows against the rule with a SELECT firstAdding the rule fails if any row breaks it

Take a backup before any change to a database you cannot rebuild. mysqldump writes the structure and data to a file you can restore.

Common Mistakes

The ones that lose or corrupt data

MistakeWhat goes wrongFix
UPDATE or DELETE without WHEREEvery row changes or disappears, with no warningSELECT with the same WHERE first
Expecting TRUNCATE to be undoableIt cannot be rolled backUse DELETE inside a transaction if you need to undo
Changing data outside a transaction when several tables must agreeA crash between statements leaves them out of stepWrap them in START TRANSACTION ... COMMIT
Copying a table with CREATE ... AS SELECT and assuming the keys came tooThe copy has no primary key or foreign keyAdd the keys with ALTER TABLE
Adding a rule to a table with bad rowsThe ALTER fails, or the data is left inconsistentCheck the rule with a SELECT first
Using RENAME COLUMN on XAMPP 10.4Syntax error: the feature needs 10.5.2 or laterUse CHANGE COLUMN
Indexing every columnWrites slow down and space is wastedIndex the columns you filter and join on
