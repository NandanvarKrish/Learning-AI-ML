Exception Handling

~2 hours · try/except — handling errors gracefully instead of crashing

01 Why this matters for AI/ML

Real data is messy — missing files, malformed numbers, unexpected blank fields. A robust data pipeline can't just crash the moment it hits one bad row out of a million; it needs to handle the problem gracefully and keep going. try/except is exactly how you build that resilience.

02 Basic try/except

try: result = 10 / 0 print(result) except ZeroDivisionError: print("Can't divide by zero!")

Python attempts everything inside try:. If an error occurs, it immediately jumps to the matching except block instead of crashing the whole program — the rest of the try block is skipped, and execution continues after the except block.

03 Common exception types

ValueError
Wrong value for a conversion, e.g. int("abc")
TypeError
Wrong type used in an operation
IndexError
List index out of range
KeyError
Dictionary key doesn't exist
ZeroDivisionError
Dividing by zero
FileNotFoundError
File doesn't exist (Day 43)

Catch the specific exception type you expect — this is why yesterday's IndexError, Day 37's KeyError, and Day 43's FileNotFoundError all matter by name, not just as generic "errors."

04 else and finally

try: age = int("25") except ValueError: print("Invalid number") else: print("Conversion succeeded: " + str(age)) finally: print("This always runs, error or not")

else runs ONLY if no exception occurred. finally runs ALWAYS — whether there was an error or not — commonly used for cleanup work (like closing a file) that must happen regardless of what went wrong.

05 Real-world example (safely reading a file)

Directly resolves yesterday's FileNotFoundError

try: with open("sales_data.txt", "r") as file: content = file.read() print(content) except FileNotFoundError: print("File not found — using default empty dataset instead") content = ""

Instead of the whole program crashing the moment a file is missing, it now handles the situation gracefully and can fall back to a sensible default — exactly what a real, production-quality data pipeline needs to do.

06 Second example (safely parsing messy data)

Skipping bad rows instead of crashing the whole pipeline

raw_scores = ["85", "92", "N/A", "78", "corrupted", "95"] valid_scores = [] for i in range(len(raw_scores)): try: score = int(raw_scores[i]) valid_scores.append(score) except ValueError: print("Skipping invalid entry: " + raw_scores[i]) print(valid_scores) # [85, 92, 78, 95]

Without try/except, hitting "N/A" would crash the ENTIRE loop, losing every score that came after it too. With it, one bad entry is skipped and processing continues — genuinely essential behavior for real, messy datasets.

07 Common mistakes to avoid

Mistake 1 — Using a bare `except:` that catches everything. This silently swallows ALL errors, including genuine bugs in your own code (typos, logic mistakes) — making them very hard to notice or debug. Always catch the SPECIFIC exception type you expect.

Mistake 2 — Catching too broadly "just to be safe." If you catch Exception generically when you only expected a ValueError, you might accidentally hide a completely unrelated bug that should have crashed loudly and been fixed.

Mistake 3 — Using try/except for normal control flow. Exceptions are for genuinely exceptional, unexpected situations — using them as a substitute for a simple if check (when you easily could have checked in advance) makes code harder to follow.

Mistake 4 — Forgetting that code after the error point in the try block never runs. The moment an exception occurs, Python jumps straight to except — any remaining lines in that try block are skipped entirely for that pass.
