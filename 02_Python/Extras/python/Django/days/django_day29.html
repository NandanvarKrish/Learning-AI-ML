Lesson 1: Knowing When Something Breaks

A shipped app needs three kinds of visibility: it should tell you it's alive, tell you when code fails, and tell you when it gets slow. Yesterday's container runs, but you still need to know how it behaves.

Analogy: A car dashboard shows the engine is running (health), warning lights tell you about faults (errors), and the fuel and speed gauges show how hard it's working (performance).

Lesson 2: A Health Check Endpoint

Load balancers and container platforms call a simple URL to decide whether to send traffic to a server. The check should be cheap and should also confirm the database answers:

# blog/views.py
from django.db import connection
from django.http import JsonResponse

def health(request):
    try:
        with connection.cursor() as cursor:
            cursor.execute("SELECT 1")
        return JsonResponse({"status": "ok", "database": "ok"})
    except Exception:
        return JsonResponse({"status": "error", "database": "down"}, status=503)
# config/urls.py
urlpatterns = [
    path("health/", health, name="health"),
    # ...other routes...
]
$ curl -i http://localhost:8000/health/ HTTP/1.1 200 OK {"status": "ok", "database": "ok"}
Keep it public but quiet: The health endpoint should reveal nothing sensitive. Don't include version numbers, settings, or user data. Also keep it out of the login requirement and out of throttling so the platform can always reach it.

Lesson 3: Error Tracking

Day 12 taught you to read tracebacks and write logs. In production, nobody watches the log file all day, so an error tracker such as Sentry collects exceptions, groups them, and alerts you. The Python SDK connects with a few lines:

# config/settings/prod.py
import os
import sentry_sdk

sentry_sdk.init(
    dsn=os.environ.get("SENTRY_DSN", ""),
    traces_sample_rate=0.1,        # sample 10% of requests for performance data
    send_default_pii=False,        # don't send personal details by default
)
Environment variable for the DSN: The DSN is a project address that is safe to keep out of Git. Setting it empty in development turns reporting off, so local errors stay local.
Privacy first: Error reports can include request data. Leave personal-data sending off unless you have a clear reason and a privacy policy that covers it.

Lesson 4: Finding Slow Queries

The most common slow page is one that runs many queries, as you saw with N+1 problems on Day 9. Django can count them for you. The test below fails if a view runs more queries than you expect:

from django.test import TestCase
from django.urls import reverse

class PostListQueryTests(TestCase):
    def test_list_page_uses_few_queries(self):
        with self.assertNumQueries(3):
            self.client.get(reverse("post-list"))

When a count changes, you can print the actual queries with the CaptureQueriesContext helper:

from django.db import connection
from django.test.utils import CaptureQueriesContext

with CaptureQueriesContext(connection) as ctx:
    self.client.get(reverse("post-list"))
for q in ctx.captured_queries:
    print(q["sql"][:80])
Fix with Day 9 tools: Repeated queries usually disappear with select_related for foreign keys and prefetch_related for many-to-many relations.

Lesson 5: The Debug Toolbar (Development Only)

django-debug-toolbar shows every query, its time, and its source on each page. It is for development only, so add it to the development settings:

# config/settings/dev.py
INSTALLED_APPS += ["debug_toolbar"]
MIDDLEWARE.insert(0, "debug_toolbar.middleware.DebugToolbarMiddleware")
INTERNAL_IPS = ["127.0.0.1"]
# config/urls.py  (only when DEBUG is True)
from django.conf import settings
if settings.DEBUG:
    import debug_toolbar
    urlpatterns += [path("__debug__/", include(debug_toolbar.urls))]
Never in production: The toolbar reveals SQL and internals. Keep it out of prod.py entirely, not merely hidden behind DEBUG.

Lesson 6: Database Indexes

An index lets the database find rows without scanning the whole table, like an index at the back of a book. Add one to fields you filter or sort by often:

class Post(models.Model):
    title = models.CharField(max_length=200)
    is_published = models.BooleanField(default=False)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["-created_at"]
        indexes = [
            models.Index(fields=["is_published", "-created_at"], name="published_recent_idx"),
        ]
python manage.py makemigrations
python manage.py migrate
Add an index when...Skip it when...
A field is used often in filter() or order_by()The table is tiny
A foreign key is queried often (Django adds one automatically)Most queries read the whole table anyway
A query is slow in the logs or toolbarThe field changes on almost every write
Indexes cost something: Every index is updated on every insert and update. Add them where reads are common and writes are modest, and measure before and after.

Lesson 7: Caching Recap

Day 20's cache is the most effective performance tool for pages that many visitors read but few people change. Combine it with the health and query checks above to confirm it helps:

from django.core.cache import cache

def popular_posts():
    posts = cache.get("popular_posts")
    if posts is None:
        posts = list(Post.objects.filter(is_published=True).order_by("-views")[:10])
        cache.set("popular_posts", posts, timeout=300)   # five minutes
    return posts
Measure, then cache: Caching a fast page adds complexity for no benefit. Use assertNumQueries and the toolbar to find the real bottleneck first.

Lesson 8: A CI Pipeline with GitHub Actions

Continuous integration (CI) runs your checks automatically whenever code is pushed. A GitHub Actions workflow file lives in your repository:

# .github/workflows/ci.yml
name: CI

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_DB: blog_test
          POSTGRES_USER: blog
          POSTGRES_PASSWORD: ci-only-password
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready --health-interval 5s
          --health-timeout 3s --health-retries 10

    env:
      DJANGO_SECRET_KEY: ci-only-not-secret
      DJANGO_SETTINGS_MODULE: config.settings.dev
      POSTGRES_HOST: localhost
      POSTGRES_DB: blog_test
      POSTGRES_USER: blog
      POSTGRES_PASSWORD: ci-only-password

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements.txt
      - run: python manage.py check
      - run: python manage.py makemigrations --check --dry-run
      - run: python manage.py test
Run python manage.py test Found 42 test(s). .................................... Ran 42 tests in 6.318s OK
StepWhat it catches
checkBroken settings and misconfigured apps
makemigrations --checkModel changes that have no migration file yet
testBehaviour that broke since the last push
Secrets in CI: The values above are throwaway test values, so they're safe in the file. Real deployment secrets belong in GitHub's encrypted secrets, read as ${{ secrets.NAME }}.
A red build is a feature: If the pipeline fails, don't merge. Fix the test or the code first, because a passing pipeline is what makes it safe to deploy.

Common Mistakes on Day 29

  1. Making the health check login-only or throttled: the platform can't reach it, and it looks like the app is down.
  2. Sending personal data to error trackers by default: keep send_default_pii off unless you need it.
  3. Shipping the debug toolbar: keep it in development settings only.
  4. Adding indexes without measuring: they slow down writes, so check the query first.
  5. Forgetting makemigrations --check in CI: a model change without a migration only fails in production.
  6. Ignoring a failing pipeline: a failing build means the last change is not safe.

Practical 2: Count Queries

Practical 3: Add an Index

Add the published_recent_idx index, run the migration, and confirm showmigrations lists it as applied.

Practical 4: CI Pipeline

Create .github/workflows/ci.yml from Lesson 8, push to a GitHub repository, and watch the Actions tab. Fix any step that fails.

Practical 5: Break It on Purpose

Change a model field without creating a migration, push, and confirm the makemigrations --check step fails. Then create the migration and confirm the build passes.
