Docker for Django

Estimated time: about 1.5 hours · Packaging the app in a container, running Gunicorn and Postgres together with Compose, and keeping secrets out of the image

Lesson 1: The "Works on My Machine" Problem

Your project depends on a Python version, installed packages, system libraries, and settings. Moving it to a server means recreating all of that by hand, and small differences cause bugs.

Analogy: A shipping container holds the goods and everything they need to travel. It doesn't matter which ship or truck carries it, because the container looks the same everywhere. A Docker image is that container for your app.
TermMeaning
ImageA read-only snapshot: OS layer, Python, packages, and your code
ContainerA running copy of an image
DockerfileThe recipe that builds the image, step by step
ComposeA file that runs several containers together, such as web and database

Lesson 2: The Dockerfile

Each instruction in a Dockerfile adds a layer. Put the things that change least near the top, so Docker can reuse cached layers:

# Dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# Install dependencies first, so this layer is cached until requirements change
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Then copy the code, which changes often
COPY . .

# Collect static files at build time, using a throwaway key that never ships
RUN DJANGO_SECRET_KEY=build-only-not-secret \
    DJANGO_SETTINGS_MODULE=config.settings.prod \
    python manage.py collectstatic --noinput

RUN useradd --create-home appuser
USER appuser

EXPOSE 8000
CMD ["gunicorn", "config.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "3"]
Why the order matters: If you copy all the code before installing requirements, every small code change forces a full reinstall. Copying requirements.txt first keeps rebuilds fast.
Build-time key only: The collectstatic step needs a secret key to load settings, but that key is baked into an image layer. Use a clearly fake value like the one above, and never a real secret.

Lesson 3: .dockerignore

Without a .dockerignore file, Docker copies everything in the folder into the image, including local virtual environments, Git history, and your .env file with real secrets:

# .dockerignore
.git
.venv
__pycache__/
*.pyc
.env
db.sqlite3
media/
staticfiles/
Secrets never go in the image: Anyone who can pull the image can read every file in it. Pass secrets at run time instead, as shown in Lesson 5.

Lesson 4: Building and Running One Container

Build the image, then run it. The -e flags inject settings at run time:

docker build -t mini-blog:1.0 .

docker run --rm -p 8000:8000 \
  -e DJANGO_SECRET_KEY="a-long-random-value-you-generated" \
  -e DJANGO_ALLOWED_HOSTS="localhost,127.0.0.1" \
  mini-blog:1.0
[INFO] Starting gunicorn 22.0.0 [INFO] Listening at: http://0.0.0.0:8000 (1) [INFO] Booting worker with pid: 7

Open http://localhost:8000 in your browser. The app runs inside the container, and the port mapping 8000:8000 sends your browser's traffic to it.

Generate a real key: Create one with python -c "import secrets; print(secrets.token_urlsafe(50))", then keep it in a password manager or your server's secret store.

Lesson 5: Environment Variables and Settings

The settings you built on Day 21 read from the environment. Inside a container, that's the only way to change them, which fits well:

# config/settings/prod.py
import os

SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]          # fails loudly if missing
DEBUG = False
ALLOWED_HOSTS = os.environ["DJANGO_ALLOWED_HOSTS"].split(",")

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ["POSTGRES_DB"],
        "USER": os.environ["POSTGRES_USER"],
        "PASSWORD": os.environ["POSTGRES_PASSWORD"],
        "HOST": os.environ.get("POSTGRES_HOST", "db"),
        "PORT": "5432",
    }
}

Keep the variables in an env file that is never committed, and load it with --env-file:

# .env.prod   (listed in .gitignore and .dockerignore)
DJANGO_SECRET_KEY=replace-me
DJANGO_ALLOWED_HOSTS=example.com
POSTGRES_DB=blog
POSTGRES_USER=blog
POSTGRES_PASSWORD=replace-me

docker run --rm -p 8000:8000 --env-file .env.prod mini-blog:1.0
Local Postgres password: The sample values are placeholders. Choose your own passwords, and never reuse them on a public server.

Lesson 6: Compose with Web and Database

Compose runs the app and Postgres together, on a private network where the app reaches the database by its service name db:

# docker-compose.yml
services:
  db:
    image: postgres:16
    env_file: .env.prod
    volumes:
      - pgdata:/var/lib/postgresql/data

  web:
    build: .
    env_file: .env.prod
    command: >
      sh -c "python manage.py migrate --noinput &&
             gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 3"
    ports:
      - "8000:8000"
    depends_on:
      - db
    volumes:
      - media:/app/media

volumes:
  pgdata:
  media:
docker compose up --build -d
docker compose exec web python manage.py createsuperuser
docker compose logs -f web
[+] Running 3/3 ✔ Network mini-blog_default Created ✔ Container mini-blog-db-1 Started ✔ Container mini-blog-web-1 Started
Named volumes keep data: pgdata stores the database files and media stores uploads (Day 5). Removing the containers with docker compose down keeps them. Only down -v deletes them.
depends_on is not "ready": It only waits for the container to start, not for Postgres to accept connections. For a first run, retry the migration, or add a healthcheck to db and use condition: service_healthy.

Lesson 7: Static Files and Uploads in Containers

Gunicorn doesn't serve static files well (Day 5). In production, put Nginx in front (Day 22), or use a package such as WhiteNoise to serve the collectstatic output from the app itself:

# settings/prod.py
MIDDLEWARE.insert(1, "whitenoise.middleware.WhiteNoiseMiddleware")
STATIC_ROOT = BASE_DIR / "staticfiles"
STORAGES = {
    "staticfiles": {"BACKEND": "whitenoise.storage.CompressedManifestStaticFilesStorage"},
}
Uploads need a volume: Files saved to media/ live inside the container. Without a volume, they vanish when the container is replaced. Mount one, as Compose does above.

Lesson 8: Checking the Container

Before calling the deployment done, run the checks you learned on Day 21 and Day 22 inside the container:

docker compose exec web python manage.py check --deploy
docker compose exec web python manage.py showmigrations
docker compose ps
CommandWhat it tells you
check --deploySecurity settings still missing or weak
showmigrationsWhether every migration was applied
compose psWhether each service is running or restarting
Restart policy: Add restart: unless-stopped to both services so they come back after a server reboot.

Common Mistakes on Day 28

  1. Copying .env or secrets into the image: add them to .dockerignore and pass them at run time.
  2. Running as root: create an unprivileged user and switch to it with USER.
  3. Forgetting the volume for Postgres or media: data is lost when the container is removed.
  4. Using DEBUG = True in the image: the production settings module must set it to False.
  5. Connecting to localhost for the database: inside a container, localhost means the container itself. Use the service name db.
  6. Putting the source copy before requirements: every code change then reinstalls all packages.

Practicals

Use your mini-blog project from the last few days.

Practical 1: Write the Dockerfile

Create the Dockerfile and .dockerignore from Lessons 2 and 3. Build the image with docker build -t mini-blog:1.0 .

Practical 2: Run One Container

Run the image with a generated secret key and DJANGO_ALLOWED_HOSTS=localhost. Open the site in your browser. Note that it cannot reach a database yet, which is the next step.

Practical 3: Compose Stack

Write docker-compose.yml with db and web, plus a .env.prod file. Run docker compose up --build -d, then migrate and createsuperuser inside the container.

Practical 4: Persistence Test

Create a post in the admin, run docker compose down, then docker compose up -d. Confirm the post is still there. Then confirm down -v would remove it.

Practical 5: Check the Container

Run check --deploy inside the web container and fix at least one warning that is relevant to your setup.
