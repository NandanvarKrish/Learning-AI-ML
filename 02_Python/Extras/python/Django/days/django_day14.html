Relationships in Practice

Estimated time: about 1.5 hours · OneToOneField, managing ManyToMany with add, remove, set, and clear, extra data with a through model, and querying across relationships

Lesson 1: Recap and the Three Relationship Types

On Day 3 you met ForeignKey and ManyToManyField. Today you'll use all three relationship types together:

TypeMeaningExample
ForeignKeyMany rows point to one rowMany posts, one author
OneToOneFieldOne row points to exactly one rowOne author, one profile
ManyToManyFieldMany rows relate to many rowsMany posts, many tags
Analogy: ForeignKey is a family where many children share one surname. OneToOne is a passport: each person has exactly one. ManyToMany is a club: members can belong to many clubs, and each club has many members.

Lesson 2: OneToOneField

Suppose each author has one profile with a biography and avatar. A OneToOneField guarantees that no author can have two profiles:

# blog/models.py
class Profile(models.Model):
    author = models.OneToOneField(
        Author,
        on_delete=models.CASCADE,
        related_name="profile",
    )
    bio = models.TextField(blank=True)
    website = models.URLField(blank=True)

    def __str__(self):
        return f"Profile of {self.author.name}"

Both directions work with a single attribute, and the reverse side is always one object, not a list:

>>> asha = Author.objects.get(name="Asha")
>>> Profile.objects.create(author=asha, bio="Writes about Django.")
>>> asha.profile.bio
>>> Profile.objects.get(author__name="Asha").website
'Writes about Django.' ''
Missing profiles: An author with no profile makes asha.profile raise Author.profile.RelatedObjectDoesNotExist. Check with hasattr(author, "profile"), or use a try/except around the lookup.

Lesson 3: Managing ManyToMany Relations

The related manager on a ManyToMany field gives you four methods for changing the links. Use the Tag model from Day 3 with the tags field on Post:

>>> post = Post.objects.get(title="Model tips")
>>> python = Tag.objects.create(name="python")
>>> web = Tag.objects.create(name="web")
>>> django_tag = Tag.objects.create(name="django")

>>> post.tags.add(python, web)
>>> post.tags.count()
>>> post.tags.remove(web)
>>> post.tags.count()
>>> post.tags.set([web, django_tag])
>>> post.tags.all().order_by("name")
>>> post.tags.clear()
>>> post.tags.count()
2 1 <QuerySet [<Tag: django>, <Tag: web>]> 0
MethodEffect on the links
add(...)Adds links; existing ones are kept, duplicates are ignored
remove(...)Removes only those links; the Tag objects remain
set([...])Makes the list exactly these links, adding and removing as needed
clear()Removes every link; the Tag objects remain
Remember: Removing a tag from a post never deletes the tag itself. The tag can still be used by other posts. Deleting a Tag object, however, removes all its links.

Lesson 4: Querying Across Relationships

Use double underscores to follow a relation, then use distinct() when a join can return the same row more than once:

>>> Post.objects.filter(tags__name="python").order_by("title")
>>> Tag.objects.filter(posts__author__name="Asha").distinct().order_by("name")
>>> Post.objects.filter(author__profile__website__contains="example")

The second query walks three relations: Tag to Post, then Post to Author. Each tag appears once, even if several of Asha's posts use it.

Duplicates: Filtering on a ManyToMany field can return a row once for each matching tag. Add .distinct() when you need each object only once. Note that distinct() can be slower on large tables, so use it only when needed.

Use related_query_name to choose a name for reverse filters. Without it, the reverse filter name is the model name in lowercase, such as post, rather than the plural posts.

Lesson 5: Extra Data with a Through Model

Sometimes the link itself has information, such as a student's grade in a course. A plain ManyToMany can't store it, so use an explicit through model:

# school/models.py
class Student(models.Model):
    name = models.CharField(max_length=100)

class Course(models.Model):
    title = models.CharField(max_length=100)
    students = models.ManyToManyField(Student, through="Enrollment", related_name="courses")

class Enrollment(models.Model):
    student = models.ForeignKey(Student, on_delete=models.CASCADE)
    course = models.ForeignKey(Course, on_delete=models.CASCADE)
    grade = models.CharField(max_length=2, blank=True)
    enrolled_on = models.DateField(auto_now_add=True)

    class Meta:
        unique_together = ("student", "course")

With a through model, add(), set(), and clear() are no longer available on the relation. Create the links explicitly, which lets you set the extra fields:

>>> ravi = Student.objects.create(name="Ravi")
>>> django101 = Course.objects.create(title="Django 101")
>>> Enrollment.objects.create(student=ravi, course=django101, grade="A")
>>> ravi.courses.all()
>>> Enrollment.objects.get(student=ravi, course=django101).grade
<QuerySet [<Course: Django 101>]> 'A'
When to choose a through model: Use it as soon as the link needs data of its own, such as a date, role, score, or status. Keep a plain ManyToMany when the link has no extra information.

Lesson 6: Prefetching Filtered Relations

Suppose you want each author with only their published posts, loaded efficiently. Prefetch lets you filter the related objects and store them under a new name:

from django.db.models import Prefetch

>>> authors = Author.objects.prefetch_related(
...     Prefetch(
...         "posts",
...         queryset=Post.objects.filter(is_published=True).order_by("title"),
...         to_attr="published_posts",
...     )
... ).order_by("name")
>>> for a in authors:
...     print(a.name, [p.title for p in a.published_posts])
Asha ['Model tips', 'Views explained'] Ravi []

The two queries are: one for the authors, and one for their published posts. Without Prefetch, filtering inside the loop would run a separate query for every author.

Naming: to_attr stores the result in a plain list, not a queryset. This is handy when you want the list ready for a template.

Lesson 7: Deletion and Related Data

Recall the on_delete rules from Day 3, and check them as you add relations:

SituationResult
Delete an Author with CASCADE postsTheir posts are deleted too
Delete a ProfileThe Author remains, with no profile
Delete a TagThe Tag and its links are removed; posts remain
Delete an EnrollmentThe student and course remain
Plan deletions before building: Ask "what should happen to the children?" for every ForeignKey. A wrong choice here can delete far more data than you intended.

Common Mistakes on Day 14

  1. Forgetting distinct() on a ManyToMany filter: the same object can appear more than once.
  2. Expecting remove() to delete the tag: it only removes the link.
  3. Using add() on a through-model relation: create the through objects explicitly.
  4. Accessing a missing OneToOne reverse: it raises an exception, so check first.
  5. Filtering inside a loop instead of using Prefetch: this causes an extra query for each object.
