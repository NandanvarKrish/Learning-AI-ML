DJANGO DAY 11 of 30

Sessions, Cookies, and Messages

Estimated time: about 1.5 hours · How Django remembers visitors between requests, storing data in cookies and sessions, and showing one-time messages to users

Lesson 1: The Problem: HTTP Forgets

HTTP is stateless. Each request stands alone, and the server doesn't remember the previous one. Yet sites remember logged-in users, shopping carts, and preferences. The solution is to send a small piece of information with each request so the server can recognise the visitor.

Analogy: A coat-check ticket. You hand over your coat and get a numbered ticket. Each time you return, you show the ticket, and the staff find your coat. The ticket is not the coat; it is just a key to what is stored.

Django gives you two tools for this: cookies, which the browser stores, and sessions, which keep the data on the server and use a cookie only as a key.

Lesson 2: Cookies

A cookie is a small piece of text the server asks the browser to keep. The browser sends it back with every later request to that site.

# blog/views.py
from django.http import HttpResponse

def set_theme(request):
    response = HttpResponse("Theme saved")
    response.set_cookie("theme", "dark", max_age=60 * 60 * 24 * 30)  # 30 days in seconds
    return response

def show_theme(request):
    theme = request.COOKIES.get("theme", "light")   # default if no cookie exists
    return HttpResponse(f"Theme: {theme}")
Visit /theme/set/ → Theme saved Visit /theme/show/ → Theme: dark

To remove a cookie, use response.delete_cookie("theme").

Never trust cookies: The browser can edit any cookie. Store preferences such as a theme in cookies, but never store anything that grants access, such as "is_admin=True". Put that kind of data on the server, where the visitor can't change it.

Lesson 3: Sessions

A session stores data on the server. The browser holds only a random session ID in a cookie, and Django looks up the matching data on each request. The request.session object behaves like a dictionary:

# blog/views.py
from django.http import HttpResponse

def visit_counter(request):
    count = request.session.get("visits", 0) + 1
    request.session["visits"] = count
    return HttpResponse(f"You have visited this page {count} time(s).")
First visit: You have visited this page 1 time(s). Second visit: You have visited this page 2 time(s). Third visit: You have visited this page 3 time(s).

Each visit increases the count because the browser sends the same session cookie back. Open a private window and the count starts again at 1, because that browser has no session cookie.

CommandWhat it does
request.session["key"] = valueStores a value; Django saves the session automatically
request.session.get("key", default)Reads a value safely
del request.session["key"]Removes one value
request.session.flush()Deletes all session data and the session itself (used at logout)
request.session.set_expiry(300)Ends the session after 300 seconds of inactivity
Where sessions live: By default, Django stores sessions in the database, in the django_session table. That is why django.contrib.sessions appears in INSTALLED_APPS and why migrate creates the table.

Lesson 4: Session Settings and Security

A few settings in settings.py control how sessions behave:

# mysite/settings.py
SESSION_COOKIE_AGE = 60 * 60 * 24 * 14     # two weeks (the default)
SESSION_EXPIRE_AT_BROWSER_CLOSE = False     # True keeps the session only until the browser closes
SESSION_COOKIE_SECURE = True                # only send the cookie over HTTPS (use in production)
SESSION_COOKIE_HTTPONLY = True              # JavaScript cannot read the cookie (default)
SettingWhy it matters
SESSION_COOKIE_HTTPONLYProtects the session ID from being stolen by injected JavaScript (default True)
SESSION_COOKIE_SECUREStops the cookie from travelling over unencrypted connections (set True on a live HTTPS site)
SESSION_COOKIE_SAMESITELimits cookies sent from other websites, reducing CSRF risk (default "Lax")
SESSION_COOKIE_AGEHow long a session stays valid, in seconds
Security reminder: Setting SESSION_COOKIE_SECURE = True on a local runserver (plain HTTP) stops the cookie from working, so sessions appear broken. Enable it only once the site runs over HTTPS.

Lesson 5: Messages Framework

After a form is saved, you usually want to show a short confirmation, such as "Post created." Because you redirect after a POST (Day 6), the message must survive the redirect. Django's messages framework handles this: it stores the message in the session, shows it once on the next page, and then clears it.

# blog/views.py
from django.contrib import messages
from django.shortcuts import redirect

def post_create(request):
    # ...form handling as before...
    if form.is_valid():
        form.save()
        messages.success(request, "Post created.")
        return redirect("post_list")

Show the messages in the base template, so any page can display them:

# templates/base.html (inside <main>, before the content block)
{% if messages %}
  <ul class="messages">
    {% for message in messages %}
      <li class="{{ message.tags }}">{{ message }}</li>
    {% endfor %}
  </ul>
{% endif %}
<ul class="messages"> <li class="success">Post created.</li> </ul>
FunctionLevelTypical use
messages.success()SUCCESS"Post created."
messages.info()INFO"You have 2 drafts."
messages.warning()WARNING"This post has no cover image."
messages.error()ERROR"Could not save. Please try again."
Note: message.tags gives the CSS class name, such as success, so you can colour each message type in your stylesheet.

Common Mistakes on Day 11

  1. Storing secrets or permissions in cookies: the browser can edit them. Keep them in sessions or on the server.
  2. Forgetting migrate: the django_session table is missing, and sessions fail with a database error.
  3. Setting SESSION_COOKIE_SECURE on plain HTTP: the browser refuses the cookie, and the session never persists.
  4. Expecting messages to show without rendering them: add the loop to the template.
  5. Calling messages after a render instead of a redirect: the message may appear on the wrong page or be lost.
  6. Using request.session.get() without a default: a new visitor gets None, and later arithmetic fails.

Practicals

Use your mini-blog project.

Practical 1: Visit Counter

Add the visit_counter view from Lesson 3 and a URL for it. Refresh the page several times, then open a private window and confirm the count starts again.

Practical 2: Theme Cookie

Write set_theme and show_theme from Lesson 2. Set the cookie, close and reopen the tab, and confirm the theme is still "dark".

Practical 3: Inspect the Session Cookie

Open your browser's developer tools, find the sessionid cookie, and note that it is a random string. Explain in one sentence why the visit count is not stored inside that string.

Practical 4: Messages on Create and Edit

Add messages.success to the create and edit views, add the loop to base.html, and confirm the message appears once after saving and disappears on the next refresh.

Practical 5: Error Message

In the form handling, add a messages.error call for an invalid form. Submit an invalid post and confirm the error message appears along with the form errors.
