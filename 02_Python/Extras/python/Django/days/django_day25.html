Viewsets and Routers

Estimated time: about 1.5 hours · ModelViewSet, customising querysets and saving, custom actions, DefaultRouter, search, ordering, and pagination settings for APIs

Lesson 1: From Several Views to One Class

On Day 23 you wrote separate functions for listing, fetching, and creating. A viewset groups all the endpoints for one resource into a single class, and a router generates the URLs for you.

Analogy: A viewset is a service counter that handles every request about one kind of item: list, look up, order, change, or cancel. The router is the signboard that tells customers which door leads to which counter.
ApproachCode you write
Individual views (Day 23)One function or class per endpoint, plus each URL
ViewSet with a routerOne class with a serializer and queryset; URLs are generated

Lesson 2: A ModelViewSet

A ModelViewSet provides list, create, retrieve, update, partial update, and destroy. You give it a queryset and a serializer:

# blog/api_views.py
from rest_framework import viewsets
from .models import Post
from .serializers import PostSerializer

class PostViewSet(viewsets.ModelViewSet):
    queryset = Post.objects.select_related("author").prefetch_related("tags")
    serializer_class = PostSerializer
Open by default: This class lets anyone read, create, change, and delete posts, including drafts. Lessons 3 and 4 add the rules that restrict it. Until then, don't deploy it.

Lesson 3: Customising the Queryset and Saving

Override get_queryset() to decide which objects each visitor may see, and perform_create() to set values that come from the request rather than the client:

class PostViewSet(viewsets.ModelViewSet):
    serializer_class = PostSerializer

    def get_queryset(self):
        qs = Post.objects.select_related("author").prefetch_related("tags")
        if self.request.user.is_staff:
            return qs                              # staff see drafts too
        return qs.filter(is_published=True)        # everyone else sees published only

    def perform_create(self, serializer):
        serializer.save(author=self.request.user.author)   # set by the server, not the client
Filtering applies to detail views too: get_object() uses get_queryset(), so a draft requested by an anonymous visitor returns 404, as if it doesn't exist.
Never trust a client-supplied author: If the client could send author in the body, one user could post as another. Setting it in perform_create keeps ownership under server control.

Lesson 4: Permissions

Set who may do what with permission_classes. The Day 16 and Day 17 ideas apply directly:

from rest_framework import permissions

class PostViewSet(viewsets.ModelViewSet):
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]
    # ...queryset and methods as before...
Permission classEffect
AllowAnyAnyone may call every method
IsAuthenticatedOnly signed-in users may call any method
IsAuthenticatedOrReadOnlyAnyone may read; only signed-in users may write
IsAdminUserOnly staff users may call any method
Object-level checks: DRF calls has_object_permission on custom permission classes. You can write one that allows only the author to edit their own post, as you did with ownership checks on Day 17.

Lesson 5: Custom Actions

Sometimes an endpoint does more than the standard five actions. The @action decorator adds one, such as publishing a post:

from rest_framework.decorators import action
from rest_framework.response import Response

class PostViewSet(viewsets.ModelViewSet):
    # ...other code...

    @action(detail=True, methods=["post"])
    def publish(self, request, pk=None):
        post = self.get_object()
        post.publish()                     # the model method from Day 10
        return Response({"status": "published"})

detail=True means the action works on one object, and the URL includes its id: /api/posts/<id>/publish/. Use detail=False for actions on the whole collection.

Use POST for actions that change data: Publishing changes the post, so it must not be a GET. Otherwise a link in an email could publish something by accident.

Lesson 6: DefaultRouter

A router creates the URLs from the viewset automatically. Register the viewset, and include the router's URLs:

# blog/urls.py
from django.urls import include, path
from rest_framework.routers import DefaultRouter
from .api_views import PostViewSet

router = DefaultRouter()
router.register("posts", PostViewSet, basename="post")

urlpatterns = [
    path("api/", include(router.urls)),
]

The basename: The basename is used to build URL names such as post-list. Set it explicitly, so the names stay the same if the model is renamed.

DefaultRouter also adds an index view at /api/ that links to each list endpoint. The browsable API (from Day 23) uses these URLs to build its pages.

Lesson 7: Searching, Ordering, and Pagination

DRF includes filter backends that read query parameters. Add them to the viewset:

from rest_framework import filters

class PostViewSet(viewsets.ModelViewSet):
    # ...queryset, permissions, and methods...
    filter_backends = [filters.SearchFilter, filters.OrderingFilter]
    search_fields = ["title", "body"]
    ordering_fields = ["created_at", "title"]
    ordering = ["-created_at"]

Clients can now call /api/posts/?search=django&ordering=title, and the same whitelisting idea from Day 19 applies: only the listed ordering fields are accepted.

Pagination is set once for the whole project, in settings.py:

REST_FRAMEWORK = {
    "DEFAULT_PAGINATION_CLASS": "rest_framework.pagination.PageNumberPagination",
    "PAGE_SIZE": 5,
}
{ "count": 12, "next": "http://127.0.0.1:8000/api/posts/?page=2", "previous": null, "results": [ ... five posts ... ] }

The wrapper with count, next, and previous is the list shape that Day 23's {"results": [...]} was preparing for.

Lesson 8: Testing a Viewset

DRF provides APITestCase with a client that handles JSON, and force_authenticate to act as a particular user:

from django.urls import reverse
from rest_framework.test import APITestCase

class PostApiTests(APITestCase):
    def setUp(self):
        self.author = Author.objects.create(name="Asha", email="asha@example.com")
        self.user = User.objects.create_user(username="asha", password="x-pass-123")
        self.author.user = self.user
        self.author.save()

    def test_anonymous_can_list_published(self):
        response = self.client.get(reverse("post-list"))
        self.assertEqual(response.status_code, 200)

    def test_anonymous_cannot_create(self):
        response = self.client.post(reverse("post-list"), {"title": "x"}, format="json")
        self.assertIn(response.status_code, (401, 403))

    def test_signed_in_user_creates_post_for_themselves(self):
        self.client.force_authenticate(user=self.user)
        response = self.client.post(reverse("post-list"),
                                    {"title": "Made via API", "body": "Hi", "is_published": True},
                                    format="json")
        self.assertEqual(response.status_code, 201)
        self.assertEqual(response.data["author"], self.author.pk)
Why 401 or 403: Which code you get depends on the authentication classes configured. Both mean the request was refused, so the test accepts either.

Common Mistakes on Day 25

  1. Shipping a ModelViewSet with no permissions: anyone can change or delete data.
  2. Letting the client set the author: set ownership in perform_create.
  3. Using GET for actions that change data: use POST, as the publish action does.
  4. Forgetting basename when the queryset is customised: the router cannot infer names from a queryset that is set in get_queryset.
  5. Forgetting the search and ordering whitelist: clients can sort by fields you meant to hide.
  6. Testing only the success path: check anonymous and wrong-user access as well.

Practicals

Use your mini-blog project with Django REST framework installed.

Practical 1: Build the Viewset

Create PostViewSet with get_queryset and perform_create. Register it with a DefaultRouter and visit /api/posts/ in the browser.

Practical 2: Permissions

Add IsAuthenticatedOrReadOnly. Confirm anonymous visitors can read but not create, and that a signed-in user can create.

Practical 3: Publish Action

Add the publish action. Create a draft through the API, call the publish URL with POST, and confirm the post is now published.

Practical 4: Search and Pagination

Add the search and ordering backends, set PAGE_SIZE to 2, and create at least three posts. Confirm ?search= and the Next link work.

Practical 5: Test the Rules

Write the three tests from Lesson 8 and add one that a draft is not returned to an anonymous visitor. Run python manage.py test.
