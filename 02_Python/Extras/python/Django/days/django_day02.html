Models and the ORM

Estimated time: about 1.5 hours · Defining models, field types, migrations, saving and querying data, and the ORM without writing SQL

Lesson 1: What Is a Model?

A model is a Python class that describes one kind of data your site stores. Each model becomes a database table, and each attribute becomes a column.

Analogy: A model is a form template. The template says what boxes exist (title, date, body) and what kind of answer each box accepts. Each saved form is one row in the table.

Django's ORM (Object-Relational Mapper) translates Python into SQL for you. Instead of writing INSERT INTO blog_post ..., you write Post.objects.create(...).

Lesson 2: Writing Your First Model

Open blog/models.py from Day 1 and define a Post class:

# blog/models.py
from django.db import models

class Post(models.Model):
    title = models.CharField(max_length=200)
    body = models.TextField()
    created_at = models.DateTimeField(auto_now_add=True)
    is_published = models.BooleanField(default=False)

    class Meta:
        ordering = ["-created_at"]     # newest first by default

    def __str__(self):
        return self.title

Why __str__? It controls how an object appears in the admin panel, in the shell, and in error messages. Always define it. This is the same __str__ method from the Python classes lesson on Day 16.

Lesson 3: Migrations

A model is only a plan. A migration is the step that turns the plan into real database tables. Django does this in two commands:

  1. makemigrations reads your models and writes a migration file describing the change.
  2. migrate applies the migration files to the database.
python manage.py makemigrations blog
python manage.py migrate
Migrations for 'blog': blog/migrations/0001_initial.py + Create model Post
python manage.py migrate blog
Operations to perform: Apply all migrations: blog Running migrations: Applying blog.0001_initial... OK
Rule: Whenever you change a model, run makemigrations and then migrate. Django does not update the database automatically. If you skip this step, you'll see errors such as "no such column".

The file blog/migrations/0001_initial.py is part of your code. Commit it to Git, so anyone who clones the project can recreate the same tables.

Lesson 4: Creating and Saving Objects

Open the Django shell, which loads your project so you can experiment with real data:

python manage.py shell
>>> from blog.models import Post
>>> p = Post.objects.create(title="Hello Django", body="My first post.")
>>> p
<Post: Hello Django>
<Post: Hello Django>

There are two common ways to save:

>>> p2 = Post(title="Second post", body="Built with save()")
>>> p2.save()          # writes the row to the database
>>> p2.id
2
2

create() builds and saves in one step. Creating the object with Post(...) and then calling save() does the same thing in two steps, which is useful when you want to change the object first.

Note: id is added automatically as the primary key. The number you see depends on how many rows already exist in your database.

Lesson 5: Querying with the ORM

Every model has a objects manager, which is your gateway to the database.

>>> Post.objects.all()
<QuerySet [<Post: Second post>, <Post: Hello Django>]>
>>> Post.objects.count()
2
>>> Post.objects.get(id=1)
<Post: Hello Django>
<QuerySet [<Post: Second post>, <Post: Hello Django>]> 2 <Post: Hello Django>

The ordering shown comes from ordering = ["-created_at"], so newer posts appear first.

Careful with get(): it raises Post.DoesNotExist when nothing matches, and MultipleObjectsReturned when several things match. Use filter() when you expect a list, and get() only when you expect exactly one row.

Filtering with lookups

Lookups use double underscores to say how to compare:

>>> Post.objects.filter(is_published=False)
>>> Post.objects.filter(title__startswith="Hello")
>>> Post.objects.filter(title__icontains="django")
>>> Post.objects.filter(id__gt=1)
>>> Post.objects.exclude(title="Second post")
>>> Post.objects.filter(is_published=False).order_by("title")
LookupMeaning
exact (the default)Exact match, case-sensitive
iexact, icontainsCase-insensitive versions
contains, startswith, endswithText matching
gt, gte, lt, lteGreater or less than
inMatches any value in a list

Querysets are lazy: filter() doesn't hit the database until you loop over the results, slice them, or call something like count(). You can chain them freely.

Lesson 6: Updating and Deleting

>>> p = Post.objects.get(id=1)
>>> p.title = "Hello, Django World"
>>> p.save()

>>> Post.objects.filter(is_published=False).update(is_published=True)
2

>>> p2 = Post.objects.get(id=2)
>>> p2.delete()
(1, {'blog.Post': 1})
2 (1, {'blog.Post': 1})

update() changes many rows in one query and returns how many rows changed. delete() returns a tuple: the total objects removed and a breakdown per model.

Destructive: Post.objects.all().delete() removes every post with no undo. Double-check your filter before running any delete().

Lesson 7: Connecting Models with Foreign Keys (Preview)

Most real data is related. A post has one author, and an author has many posts. You express that with a ForeignKey, which you'll meet in full on Day 3.

class Author(models.Model):
    name = models.CharField(max_length=100)

class Post(models.Model):
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name="posts")
    title = models.CharField(max_length=200)

Notice on_delete. It tells Django what to do when the author is deleted. CASCADE deletes the posts too. You'll learn the other options on Day 3.

Common Mistakes on Day 2

  1. Changing a model and forgetting migrations: run makemigrations and migrate after every model change.
  2. Using get() for lists: use filter() when more than one result is possible.
  3. Forgetting to save: changing an attribute on an object does nothing to the database until you call save().
  4. Editing old migration files: create a new migration instead. Old ones describe history that's already been applied.
  5. Missing max_length: CharField requires it, and makemigrations will report an error.
