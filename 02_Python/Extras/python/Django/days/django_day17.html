Permissions and Groups

Estimated time: about 1.5 hours · Model permissions, custom permissions, groups for roles, checking access in views with mixins and decorators, and object-level ownership checks

Lesson 1: Who May Do What

Yesterday you learned that a login proves identity. Permissions answer the next question: which actions may this user perform? Django's permission system works on models. For every model it creates four permissions automatically:

PermissionAllows
blog.view_postViewing posts in the admin and in code that checks it
blog.add_postCreating posts
blog.change_postEditing posts
blog.delete_postDeleting posts
Analogy: Think of a building with keycards. Each door (action) needs a specific card (permission). Groups are the job titles that come with a standard set of cards, so you don't hand out cards one at a time.

Lesson 2: Custom Permissions

Add your own permissions in the model's Meta class. Here, editors may publish posts, which is different from simply editing them:

# blog/models.py
class Post(models.Model):
    # ...fields...

    class Meta:
        ordering = ["-created_at"]
        permissions = [
            ("publish_post", "Can publish posts"),
        ]
python manage.py makemigrations blog
python manage.py migrate
Migrations for 'blog': blog/migrations/0004_alter_post_options.py ~ Alter model options for post

After migrating, list the permissions Django now knows for posts:

>>> from django.contrib.auth.models import Permission
>>> Permission.objects.filter(codename__endswith="_post").values_list("codename", flat=True).order_by("codename")
<QuerySet ['add_post', 'change_post', 'delete_post', 'publish_post', 'view_post']>
Name format: A permission is always referred to as app_label.codename, such as blog.publish_post. The codename is what you see in the database; the second text in the Meta tuple is the description shown in the admin.

Lesson 3: Groups

Assigning permissions one user at a time becomes tedious. A group holds a set of permissions, and you add users to the group:

>>> from django.contrib.auth.models import User, Group, Permission

>>> editors = Group.objects.create(name="Editors")
>>> publish = Permission.objects.get(codename="publish_post")
>>> editors.permissions.add(publish)

>>> sam = User.objects.get(username="sam")
>>> sam.groups.add(editors)
>>> sam = User.objects.get(username="sam")    # reload to clear cached permissions
>>> sam.has_perm("blog.publish_post")
True

Notice the reload. Django caches a user's permissions on the object, so after changing groups, fetch the user again before checking.

Removing access: Use sam.groups.remove(editors) to take a user out of a group. Their permissions from other groups stay in place, so check them all.

Lesson 4: Checking Permissions in Views

There are two ways to protect a view with permissions, mirroring the login tools from Day 16:

# blog/views.py
from django.contrib.auth.decorators import permission_required
from django.contrib.auth.mixins import PermissionRequiredMixin
from django.views.generic import CreateView

@permission_required("blog.publish_post", raise_exception=True)
def publish_queue(request):
    ...

class PostCreateView(PermissionRequiredMixin, CreateView):
    model = Post
    form_class = PostForm
    template_name = "blog/post_form.html"
    permission_required = "blog.add_post"
SituationResult
Anonymous visitorRedirected to the login page (with login_required style handling)
Logged in, but missing the permission403 Forbidden when raise_exception=True (or the mixin's default)
Logged in with the permissionThe view runs normally
Combine with login: PermissionRequiredMixin already requires login. Use LoginRequiredMixin only for pages that need a logged-in user but no particular permission.

Lesson 5: Checking Permissions in Templates

Templates can hide buttons the user cannot use. This is for convenience only; the view must still check:

# blog/templates/blog/post_detail.html
{% if perms.blog.change_post %}
  <a href="{% url 'post_edit' post.pk %}">Edit</a>
{% endif %}
{% if perms.blog.publish_post %}
  <button type="submit">Publish now</button>
{% endif %}

perms is available in every template and reads like perms.app_label.codename.

Lesson 6: Object-Level Ownership

Model permissions apply to the whole table. "Can change posts" lets you edit any post. Often the rule is narrower: authors may edit their own posts. Check the object in the view:

from django.core.exceptions import PermissionDenied
from django.shortcuts import get_object_or_404

def post_edit(request, pk):
    post = get_object_or_404(Post, pk=pk)
    is_owner = post.author.user == request.user
    if not (is_owner or request.user.has_perm("blog.change_post")):
        raise PermissionDenied
    ...
Owner check needs login first: An anonymous user is not equal to any author's user, so the check returns False and they get a 403. Pair this with login_required, so they are sent to log in instead.
Libraries: Projects with many object rules often use a package such as django-guardian. Start with simple owner checks like this one before adding a library.

Lesson 7: Staff and Superusers

FlagMeaning
is_activeThe account can log in at all. Deactivate instead of deleting when access should stop.
is_staffThe user may sign in to the admin site
is_superuserThe user has every permission, without needing them assigned
Be sparing with superuser: A superuser bypasses every permission check. Give staff access through groups with specific permissions, and reserve superuser for the people who manage the system.

Common Mistakes on Day 17

  1. Forgetting to migrate after adding a custom permission: the permission doesn't exist in the database yet.
  2. Using a stale user object after changing groups: reload the user before checking.
  3. Hiding buttons but not checking in the view: anyone can type the URL.
  4. Relying on model permissions for ownership rules: check the specific object too.
  5. Making everyone a superuser: it bypasses all controls and makes mistakes costly.

Practicals

Use your mini-blog project.

Practical 1: Custom Permission

Add publish_post to Post.Meta.permissions, migrate, and confirm it appears in the permission list.

Practical 2: Editors Group

Create an "Editors" group with the publish and change permissions. Add one user to it and confirm has_perm returns True for that user after reloading, and False for another user.

Practical 3: Protect a View

Protect a page with permission_required. Visit it as a logged-out user, as a logged-in user without the permission, and as a user in the group. Record each result.

Practical 4: Owner Check

Add the owner check to the edit view from Lesson 6. Confirm that an author can edit their own post, and another logged-in user gets a 403 unless they have the change permission.

Practical 5: Template Buttons

Show the Edit and Publish buttons in post_detail.html only to users with the matching permissions. Confirm the buttons change between two accounts.
