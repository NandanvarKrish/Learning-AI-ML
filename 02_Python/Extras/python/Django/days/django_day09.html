Lesson 2: Querysets Are Lazy

A queryset describes the data you want, but does not hit the database until you use the results. You can build it up step by step:

>>> qs = Post.objects.all()                 # no query yet
>>> qs = qs.filter(is_published=True)      # still no query
>>> qs = qs.order_by("title")              # still no query
>>> for post in qs:                        # the query runs here
...     print(post.title)
Model tips Views explained

A queryset caches its results after the first evaluation. Looping over it twice does not run the query twice.

Triggers evaluationDoes not trigger it
Looping, list()filter(), exclude(), order_by()
len(), bool(), print()values(), select_related()
get(), first(), exists(), count()Slicing with [:n] (until you evaluate it)
Watch out: count() asks the database to count, while len(qs) loads every row into memory and then counts them. Use count() when you only need the number.

Lesson 3: Combining Conditions with Q

Keyword arguments in filter() are combined with AND. For OR and NOT, use Q objects with |, &, and ~:

>>> from django.db.models import Q

>>> Post.objects.filter(is_published=True, views__gt=30).order_by("title")
>>> Post.objects.filter(Q(is_published=True) | Q(views__gt=20)).order_by("title")
>>> Post.objects.filter(~Q(author__name="Ravi")).order_by("title")
<QuerySet [<Post: Model tips>]> <QuerySet [<Post: Model tips>, <Post: Views explained>]> <QuerySet [<Post: Model tips>, <Post: Views explained>]>

Check each line against the data table. The first line needs both conditions: Model tips has 40 views and is published. Forms made easy is excluded by both the OR line and the NOT line.

Lesson 4: Comparing Fields with F

F refers to a field value in the database, so you can compare fields to each other or change a value without fetching it into Python first:

>>> from django.db.models import F

>>> Post.objects.filter(views__gte=F("id") * 10).order_by("title")   # compare against a calculation
>>> Post.objects.update(views=F("views") + 5)                       # safe increment in the database
3
3

After the update, the views are 45, 30, and 15. The update ran as one SQL statement, which avoids a common bug: two users increasing the same value at once, where one increment is lost.

Why F matters: Doing post.views += 1; post.save() reads the value into Python first. If two requests run at the same time, one increment can overwrite the other. F does the arithmetic inside the database.

Lesson 5: Aggregation

aggregate() computes one summary value for the whole queryset:

>>> from django.db.models import Sum, Avg, Count, Max

>>> Post.objects.aggregate(total=Sum("views"))
>>> Post.objects.aggregate(avg=Avg("views"))
>>> Post.objects.aggregate(best=Max("views"), posts=Count("id"))
{'total': 75} {'avg': 25.0} {'best': 40, 'posts': 3}

These numbers are from the original data, before the Lesson 4 update. Your results after that update will be 45, 30, and 15 instead. Check your own numbers against your data.

Here's how to count only the published posts with filter inside an aggregate:

>>> Post.objects.aggregate(published=Count("id", filter=Q(is_published=True)))
{'published': 2}

Lesson 6: Annotation: Per-Row Values

annotate() adds a calculated value to each row. The Author-to-Post relationship from Day 3 makes this useful:

>>> from django.db.models import Count, Q

>>> authors = Author.objects.annotate(
...     post_count=Count("posts"),
...     published_count=Count("posts", filter=Q(posts__is_published=True)),
... ).order_by("name")
>>> for a in authors:
...     print(a.name, a.post_count, a.published_count)
Asha 2 2 Ravi 1 0
Aggregate vs annotate: aggregate() returns one dictionary for the whole queryset. annotate() returns a queryset in which each object has an extra attribute, such as a.post_count.

Lesson 7: values and values_list

Sometimes you don't need model objects, just specific fields. values() returns dictionaries, and values_list() returns tuples:

>>> Post.objects.order_by("title").values("title", "views")
>>> Post.objects.order_by("title").values_list("title", flat=True)
>>> Post.objects.values("author__name").distinct()
<QuerySet [{'title': 'Forms made easy', 'views': 10}, {'title': 'Model tips', 'views': 40}, {'title': 'Views explained', 'views': 25}]> <QuerySet ['Forms made easy', 'Model tips', 'Views explained']> <QuerySet [{'author__name': 'Asha'}, {'author__name': 'Ravi'}]>

flat=True gives a plain list of values rather than tuples, which works only with one field. Notice author__name follows the foreign key from Day 3.

When to use values: For reports, exports, and charts, you usually don't need full objects. Requesting only the fields you need makes the query lighter.

Lesson 8: exists, first, and Slicing

>>> Post.objects.filter(views__gt=100).exists()
>>> Post.objects.order_by("title").first()
>>> Post.objects.order_by("-views")[:2]
False <Post: Forms made easy> <QuerySet [<Post: Model tips>, <Post: Views explained>]>
  • exists() is faster than count() > 0, because the database can stop at the first match.
  • first() returns None instead of raising an error when the queryset is empty. get() raises an error in that case.
  • Slicing with [:n] becomes a SQL LIMIT, so only those rows are fetched.

Lesson 9: The N+1 Query Problem

A common performance mistake is looping over objects and touching related data inside the loop:

# Slow: one query for posts, then one query per post for the author
for post in Post.objects.all():
    print(post.title, post.author.name)

# Fast: the author is fetched in the same query
for post in Post.objects.select_related("author"):
    print(post.title, post.author.name)

With three posts, the slow version runs about four queries (one for the posts plus one per author lookup). The fast version runs one query. The gap grows quickly: with a thousand posts, the slow version runs about a thousand and one queries.

MethodUse for
select_related()ForeignKey and one-to-one fields (joined in one query)
prefetch_related()ManyToMany and reverse ForeignKey fields (a second query, combined in Python)
>>> Post.objects.prefetch_related("tags")       # loads tags efficiently
>>> Author.objects.prefetch_related("posts")    # loads each author's posts
Measure, don't guess: Use Django Debug Toolbar or django.test.utils.CaptureQueriesContext to count the queries a page runs before and after changes.

Common Mistakes on Day 9

  1. Using len(qs) to count: use qs.count() to let the database count.
  2. Using | in place of , inside filter: keyword arguments are AND. Use Q objects for OR.
  3. Incrementing with Python arithmetic: use F() to avoid lost updates.
  4. Expecting get() to return None: it raises an error. Use first() when the result might be missing.
  5. Looping over related objects without select_related: this causes the N+1 problem.
  6. Forgetting order_by: results and pagination can change between requests.
