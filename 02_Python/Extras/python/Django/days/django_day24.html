Django REST Framework Serializers

Lesson 1: What a Serializer Does

On Day 23 you wrote post_to_dict by hand, and validated input with a form. A serializer in Django REST framework does both jobs in one place:

  • Output: turns a model object into a plain dictionary ready for JSON.
  • Input: checks incoming data, and turns it back into validated values that can be saved.
Analogy: A serializer is a customs officer at a border. Goods leaving the country are packed into standard crates. Goods arriving are inspected, and only the allowed items are let through.

Lesson 2: A ModelSerializer

A ModelSerializer reads the model and builds the fields automatically. List the fields you want to expose, as you did on Day 23:

# blog/serializers.py
from rest_framework import serializers
from .models import Post

class PostSerializer(serializers.ModelSerializer):
    class Meta:
        model = Post
        fields = ["id", "title", "body", "author", "is_published", "created_at"]
        read_only_fields = ["id", "created_at"]

Test it in the shell:

>>> from blog.serializers import PostSerializer
>>> from blog.models import Post

>>> post = Post.objects.get(title="Model tips")
>>> PostSerializer(post).data
{'id': 1, 'title': 'Model tips', 'body': 'Keep models small.', 'author': 1, 'is_published': True, 'created_at': '2026-10-21T07:14:00+05:30'}

Notice author shows the author's id, not their name. A ForeignKey becomes a primary key by default. The date uses the ISO format, and its exact digits depend on your data.

Explicit is safer: Listing fields is required, or you can end up exposing every column. Django REST framework will warn you if you forget it.

Lesson 3: Related Fields and Custom Values

Sometimes the default output is not what clients need. Shape the value with a field that reads a related attribute, or a method:

class PostSerializer(serializers.ModelSerializer):
    author_name = serializers.CharField(source="author.name", read_only=True)
    tags = serializers.SlugRelatedField(
        many=True, slug_field="name", queryset=Tag.objects.all(), required=False,
    )

    class Meta:
        model = Post
        fields = ["id", "title", "body", "author", "author_name", "tags", "is_published", "created_at"]
        read_only_fields = ["id", "created_at"]
{'id': 1, 'title': 'Model tips', 'body': 'Keep models small.', 'author': 1, 'author_name': 'Asha', 'tags': ['python', 'web'], 'is_published': True, 'created_at': '...'}
Field typeOutput
Default ForeignKeyThe related id, such as 1
CharField(source="author.name")A value from the related object, such as "Asha"
SlugRelatedField(many=True, slug_field="name")A list of tag names, such as ["python", "web"]
SerializerMethodFieldThe result of a method you write, for calculated values
Watch for extra queries: author.name and tags each trigger a query per object unless the view uses select_related and prefetch_related (Day 9). Add them in the queryset.

Lesson 4: Validating Input

When data arrives from a client, create the serializer with data=, then call is_valid(). Check the errors and read the clean values from validated_data:

>>> s = PostSerializer(data={"title": "Hi", "body": "Text", "author": 1})
>>> s.is_valid()
>>> s.errors
False {'title': [ErrorDetail(string='Ensure this field has at least 5 characters.', code='min_length')]}

Add rules with a method named validate_<field>, which works like clean_<field> on a form (Day 6):

class PostSerializer(serializers.ModelSerializer):
    # ...fields and Meta as before...

    def validate_title(self, value):
        value = value.strip()
        if len(value) < 5:
            raise serializers.ValidationError("Title must be at least 5 characters.")
        return value

    def validate(self, data):
        if data.get("is_published") and not data.get("body"):
            raise serializers.ValidationError("Published posts need body text.")
        return data

Use validate() for rules involving several fields, just as clean() works on forms.

Errors are structured: The API returns a dictionary keyed by field name, and each error includes a machine-readable code. Clients can show messages next to the right inputs, and translate them by code.

Lesson 5: Saving Data

After validation succeeds, save() creates or updates the object:

>>> s = PostSerializer(data={"title": "Serializers rock", "body": "Yes", "author": 1, "is_published": True})
>>> s.is_valid()
>>> post = s.save()
>>> post.title
True 'Serializers rock'

To update an existing post, pass the instance first, then the new data. Use partial=True to change only some fields:

>>> post = Post.objects.get(title="Model tips")
>>> s = PostSerializer(post, data={"title": "Model tips, revised"}, partial=True)
>>> s.is_valid()
>>> s.save()
>>> s.data["title"]
True 'Model tips, revised'
Without partial=True: Every required field must be present, so a request changing only the title is rejected. Use partial=True for PATCH-style updates.

Lesson 6: Lists and Nested Data

Pass many=True to serialise a list. Use it on the output side, and the same serializer produces a list of dictionaries:

>>> PostSerializer(Post.objects.all().order_by("title"), many=True).data
[{'id': 3, 'title': 'Forms made easy', ...}, {'id': 1, 'title': 'Model tips', ...}, ...]

For a read-only nested object, such as showing the full author instead of the id, use a second serializer:

class AuthorSerializer(serializers.ModelSerializer):
    class Meta:
        model = Author
        fields = ["id", "name"]

class PostDetailSerializer(PostSerializer):
    author = AuthorSerializer(read_only=True)
Read and write shapes can differ: A common pattern is a detailed serializer for reading and a simpler one for writing, which avoids sending nested objects back in.

Lesson 7: Plain Serializers

Not every input matches a model. A contact form posted to an API is a good example. Use serializers.Serializer and declare each field yourself:

class ContactSerializer(serializers.Serializer):
    name = serializers.CharField(max_length=50)
    email = serializers.EmailField()
    message = serializers.CharField(style={"base_template": "textarea.html"})

This works like a Django form, but produces JSON errors and expects JSON input.

Common Mistakes on Day 24

  1. Leaving out fields: list the fields you want to expose, so new model columns stay private.
  2. Forgetting is_valid() before save(): DRF raises an error if you save unvalidated data.
  3. Reading data instead of validated_data: use validated values for anything you save.
  4. Missing partial=True on updates: required fields block partial changes.
  5. Missing queries for related fields: add select_related and prefetch_related to avoid one query per object.
  6. Putting nested write logic everywhere: keep writes simple, and use read-only nested serializers for display.
