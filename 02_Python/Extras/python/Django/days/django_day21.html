DJANGO DAY 21 of 30

Settings for Development and Production

Estimated time: about 1.5 hours · Splitting settings into base, development, and production modules, reading secrets from the environment, and the security settings a live site needs

Lesson 1: One File Cannot Serve Two Worlds

Your settings.py currently mixes two very different needs. On your laptop, you want DEBUG = True, console email, and a local database. On a live site, you need DEBUG = False, strict hosts, HTTPS, and real secrets. Keeping both in one file means someone eventually ships the wrong setting.

Analogy: A pilot's flight checklist differs for a training flight and a passenger flight. The aircraft is the same, but the safety settings change with the purpose.

The fix is to share common settings in one place, and keep environment-specific settings in separate files.

Lesson 2: Splitting Settings into a Package

Turn settings.py into a package with a shared base and two environment files:

mysite/ └── settings/ ├── __init__.py # empty ├── base.py # shared settings for every environment ├── dev.py # development: DEBUG on, local conveniences └── prod.py # production: secure, reads secrets from the environment
# mysite/settings/base.py
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent.parent

INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "blog",
]

MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]

ROOT_URLCONF = "mysite.urls"
STATIC_URL = "static/"
STATIC_ROOT = BASE_DIR / "staticfiles"
MEDIA_URL = "media/"
MEDIA_ROOT = BASE_DIR / "media"
DEFAULT_AUTO_FIELD = "django.db.models.BigAutoField"
Counting the parents: base.py sits in mysite/settings/, so BASE_DIR needs three .parent steps to reach the project root. Check it with print(BASE_DIR) after the change.

Lesson 3: Development and Production Modules

Each environment file starts by importing the base, then overrides what differs:

# mysite/settings/dev.py
from .base import *

DEBUG = True
SECRET_KEY = "dev-only-insecure-key-change-me"   # fine locally, never in production
ALLOWED_HOSTS = ["127.0.0.1", "localhost"]

EMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend"

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}
# mysite/settings/prod.py
import os
from .base import *

DEBUG = False
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
ALLOWED_HOSTS = os.environ.get("DJANGO_ALLOWED_HOSTS", "").split(",")

EMAIL_BACKEND = "django.core.mail.backends.smtp.EmailBackend"
EMAIL_HOST = os.environ["EMAIL_HOST"]
EMAIL_HOST_PASSWORD = os.environ["EMAIL_HOST_PASSWORD"]
EMAIL_HOST_USER = os.environ.get("EMAIL_HOST_USER", "")
EMAIL_USE_TLS = True
EMAIL_PORT = 587
Fail loudly on missing secrets: os.environ["DJANGO_SECRET_KEY"] raises a KeyError if the variable is missing, so the site refuses to start with an unsafe default. Avoid os.environ.get("DJANGO_SECRET_KEY", "fallback") for secrets, because a missing variable would then silently use the fallback.
KeyError: 'DJANGO_SECRET_KEY'

That error is the correct behaviour: the production server will not start until the secret is set.

Lesson 4: Choosing the Settings Module

Django reads the DJANGO_SETTINGS_MODULE environment variable to decide which settings to load. manage.py sets a default, which you can override:

# manage.py (the default line, already present)
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "mysite.settings.dev")
# Development (uses the default)
python manage.py runserver

# Production (explicit)
export DJANGO_SETTINGS_MODULE=mysite.settings.prod
export DJANGO_SECRET_KEY="a-long-random-value"
export DJANGO_ALLOWED_HOSTS="example.com,www.example.com"
python manage.py check --deploy
Generate a real secret key with a short Python command, such as python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())". Store the result in your hosting platform's secret manager, not in Git.

Lesson 5: Production Security Settings

A live site needs extra protections on top of DEBUG = False:

# mysite/settings/prod.py (security section)
SECURE_SSL_REDIRECT = True             # send HTTP visitors to HTTPS
SESSION_COOKIE_SECURE = True           # session cookie only over HTTPS (Day 11)
CSRF_COOKIE_SECURE = True              # CSRF cookie only over HTTPS (Day 6)
SECURE_HSTS_SECONDS = 3600             # tell browsers to use HTTPS for an hour (raise later)
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_CONTENT_TYPE_NOSNIFF = True     # stop browsers guessing file types
X_FRAME_OPTIONS = "DENY"               # prevent the site being embedded in other sites
CSRF_TRUSTED_ORIGINS = ["https://example.com"]
SettingProtects against
SECURE_SSL_REDIRECTVisitors sending data over plain HTTP
SESSION_COOKIE_SECURE and CSRF_COOKIE_SECURECookies being read on unencrypted connections
SECURE_HSTS_SECONDSDowngrade attacks that try to switch the visitor to HTTP
X_FRAME_OPTIONSClickjacking, where your page is hidden inside another site
CSRF_TRUSTED_ORIGINSForm submissions from unexpected domains
Raise HSTS slowly: A long SECURE_HSTS_SECONDS makes browsers insist on HTTPS for that time, even if you later break HTTPS. Start with a short value, check that everything works, then increase it over several weeks.

Lesson 6: Keeping Database Settings Flexible

Development often uses SQLite, while production uses PostgreSQL. Read the production details from the environment, so the same code runs everywhere:

# mysite/settings/prod.py
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ["DB_NAME"],
        "USER": os.environ["DB_USER"],
        "PASSWORD": os.environ["DB_PASSWORD"],
        "HOST": os.environ.get("DB_HOST", "localhost"),
        "PORT": os.environ.get("DB_PORT", "5432"),
    }
}
Helper libraries: Packages such as django-environ and dj-database-url can parse a single DATABASE_URL variable. The approach here uses only the standard library, which keeps dependencies minimal.

Lesson 7: Checking Your Setup

Two commands catch most mistakes before a site goes live:

python manage.py check
python manage.py check --deploy --settings=mysite.settings.prod
?: (security.W004) You have not set a value for the SECURE_HSTS_SECONDS setting. If your entire site is served only over SSL, you may want to consider setting a value and enabling HTTP Strict Transport Security.

Each warning names a setting and explains the risk. Read them all, fix what applies, and document any you consciously accept.

Test the production settings locally: Run collectstatic and the server with the prod module, using temporary environment values. Problems such as missing static files show up here, not after deployment.

Lesson 8: Keeping Secrets Out of Git

  • Add .env files and any local secrets to .gitignore (Day 29).
  • Never hard-code secret keys, passwords, or API tokens in settings.py.
  • If a secret is ever committed, change it immediately. Deleting it from history does not make it safe, because copies may already exist.
  • Use different secret keys for each environment, so a leak in development cannot compromise production.

Common Mistakes on Day 21

  1. Leaving DEBUG = True in production: it shows code and settings to anyone who triggers an error.
  2. Using a fallback for a missing secret: the site runs with an insecure key without anyone noticing.
  3. Wrong BASE_DIR after moving settings: static files and the database go to the wrong folder.
  4. Forgetting ALLOWED_HOSTS: production refuses every request, or accepts ones meant for another domain.
  5. Enabling HSTS for a long time too early: a broken HTTPS setup then blocks visitors in their browsers.
  6. Committing the production settings values: keep them in the environment or a secret manager.

Practicals

Use your mini-blog project.

Practical 1: Split the Settings

Create the settings package with base.py, dev.py, and prod.py. Move the shared settings to base and confirm python manage.py runserver still works.

Practical 2: Check BASE_DIR

Print BASE_DIR from the dev settings and confirm it points to your project folder. Explain in one sentence why three .parent steps are needed.

Practical 3: Fail Loudly

Run DJANGO_SETTINGS_MODULE=mysite.settings.prod python manage.py check without setting DJANGO_SECRET_KEY. Record the error, then set a temporary value and confirm the check passes.

Practical 4: Deploy Check

Run check --deploy with the prod settings and list every warning. Choose three to fix and explain each in one sentence.

Practical 5: Secret Hygiene

Search your project for any password or key typed directly into a settings file. Move each one to an environment variable and add a .env entry to .gitignore.
