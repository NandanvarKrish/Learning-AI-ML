Caching Basics

Estimated time: about 1.5 hours · The cache framework, low-level get and set, cache_page for views, template fragment caching, invalidating cached data on change, and the dangers of caching personal content

Lesson 1: Why Cache?

Some work is expensive and gives the same result for many visitors: counting thousands of posts, building a sidebar of popular tags, or calling an outside service. A cache keeps the result for a while, so the next request reuses it instead of repeating the work.

Analogy: A cook who prepares a popular dish in batches and keeps a tray warm. Customers get the tray instantly, and the cook refreshes it when the ingredients change or the tray goes stale.

The hard part of caching is not storing the data. It is knowing when the stored copy is no longer correct.

Lesson 2: Configuring the Cache

Django's cache framework has a configuration in settings.py. For development, the in-memory backend is simplest:

# mysite/settings.py
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.locmem.LocMemCache",
        "LOCATION": "mini-blog",
    }
}

In production, the cache is usually shared by all server processes, so a store such as Redis is used. Django includes a Redis backend:

CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",
        "LOCATION": "redis://127.0.0.1:6379/1",
    }
}
Local memory is per process: The LocMem cache is separate for each server process. In production with several processes, one process may hold a value that another has already changed. Use a shared backend such as Redis for real sites.

Lesson 3: Low-Level Cache API

The cache object stores any picklable Python value under a key, for a number of seconds:

>>> from django.core.cache import cache

>>> cache.set("greeting", "hello", timeout=60)
>>> cache.get("greeting")
>>> cache.get("missing", "fallback")
>>> cache.delete("greeting")
>>> cache.get("greeting")
'hello' 'fallback' None

The most useful method is get_or_set. It returns the cached value, or runs the function, stores the result, and returns it:

>>> from blog.models import Post
>>> total = cache.get_or_set("total_published", lambda: Post.objects.filter(is_published=True).count(), 300)
>>> total
2

The first call runs the count. Calls in the next five minutes return the stored number without touching the database. The output shows the count from the sample data; yours will match your own posts.

MethodPurpose
set(key, value, timeout)Store a value for timeout seconds
get(key, default)Read a value, or the default when missing or expired
get_or_set(key, func, timeout)Read, or compute and store
delete(key)Remove one entry
delete_many([keys])Remove several entries at once
clear()Remove everything in the cache (use with care)
Choose timeouts deliberately: A short timeout keeps data fresh but does more work. A long timeout saves work but risks stale results. Set a timeout even when you plan to invalidate, as a safety net.

Lesson 4: Caching a Whole View

The cache_page decorator stores the entire response for a set time. The next visitor gets the saved HTML:

# blog/views.py
from django.views.decorators.cache import cache_page

@cache_page(60 * 15)          # fifteen minutes
def post_list(request):
    posts = Post.objects.filter(is_published=True)
    return render(request, "blog/post_list.html", {"posts": posts})

For class-based views, wrap the dispatch method:

from django.utils.decorators import method_decorator
from django.views.decorators.cache import cache_page

@method_decorator(cache_page(60 * 15), name="dispatch")
class PostListView(ListView):
    model = Post
    template_name = "blog/post_list.html"
Never cache personal pages this way: Your base template shows the signed-in username (Day 16). If that page is cached and served to another visitor, they see the first person's name. Per-view caching is only safe for pages that look identical to everyone.

Lesson 5: Caching a Fragment

Often only one part of a page is slow or shared, such as a list of popular tags. The cache template tag caches just that fragment:

{% load cache %}

{% cache 600 popular_tags %}
  <ul class="tags">
    {% for tag in tags %}
      <li>{{ tag.name }} ({{ tag.posts.count }})</li>
    {% endfor %}
  </ul>
{% endcache %}

The number is the timeout in seconds, and popular_tags is the fragment's name. If the fragment depends on the user, add extra values to make the cache key unique:

{% load cache %}
{% cache 600 user_menu request.user.pk %}
  <p>Hello, {{ request.user.username }}</p>
{% endcache %}
Fragments are safer than whole pages: You can cache the public tag list and leave the personal navigation outside the cache block. That keeps most of the speed without leaking personal data.

Lesson 6: Invalidating the Cache

When a post changes, cached data about posts becomes wrong. Remove those entries in a signal (Day 10), so the next request rebuilds them:

# blog/signals.py
from django.core.cache import cache
from django.db.models.signals import post_save, post_delete
from django.dispatch import receiver
from .models import Post

@receiver([post_save, post_delete], sender=Post)
def clear_post_cache(sender, **kwargs):
    cache.delete_many(["total_published", "popular_tags"])
Keep the key list in one place: Forgetting to clear one key is the most common caching bug. Define the key names as constants, and use them in both the reading code and the clearing code.

Here is the usual sequence:

  1. A visitor asks for the count. The cache is empty, so the database runs the count and stores it.
  2. An editor publishes a new post. The signal deletes total_published.
  3. The next visitor finds nothing in the cache, so the count is recalculated and includes the new post.

Lesson 7: Cache Keys and Testing

Each cache entry has a key. Keep keys descriptive and specific, such as post:42:detail rather than detail. Keys must be short, without spaces, and unique across your project.

Tests should not share cache state. Clear the cache in setUp, so one test's data doesn't affect another:

from django.core.cache import cache
from django.test import TestCase

class TotalCountTests(TestCase):
    def setUp(self):
        cache.clear()

    def test_count_is_cached(self):
        cache.set("total_published", 99, 60)
        self.assertEqual(cache.get("total_published"), 99)
Cache during tests: Use the LocMem backend in the test settings, so tests don't depend on a running Redis server.

Lesson 8: What Not to Cache

  • Personal data: carts, account details, and private drafts must never be shared between visitors.
  • Values that must always be exact: account balances or stock counts used at checkout.
  • Cheap queries: caching adds complexity and a risk of stale data, so cache only work that is measurably slow.
  • Pages with forms and CSRF tokens: the token belongs to one visitor's session.
Measure first: Use the query counts from Day 9 to find slow pages, then cache the specific part that is slow. Caching everything hides problems and creates bugs.

Common Mistakes on Day 20

  1. Caching a personal page with cache_page: the next visitor sees someone else's content.
  2. Forgetting to invalidate: visitors see old data until the timeout ends.
  3. Setting no timeout: values may stay forever, even when they become wrong.
  4. Using LocMem in production with several processes: each process keeps its own copy.
  5. Misspelling a cache key: the clearing code silently misses it, so the data stays stale.

Practicals

Use your mini-blog project.

Practical 1: Low-Level Cache

In the shell, set a value with a 60-second timeout, read it, delete it, and read again. Record the three results.

Practical 2: get_or_set

Cache the published post count with get_or_set. Add a new published post and confirm the count is still the old value until you clear the cache.

Practical 3: Invalidate on Change

Add the signal from Lesson 6. Publish a new post and confirm the cached count updates on the next read.

Practical 4: Fragment Cache

Cache a sidebar of tags with the cache tag. Add a tag to a post, and explain why the sidebar may still show the old list until the timeout ends. Then add the invalidation for it.

Practical 5: Find the Leak

Explain in one or two sentences why the base template's username display must not be inside a whole-page cache. Then wrap only the public tag list in a fragment cache instead.
