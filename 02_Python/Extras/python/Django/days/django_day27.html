API Versioning and Throttling Deep Dive

Estimated time: about 1.5 hours · Versioning strategies, serving two versions side by side, scoped throttles, custom throttle classes, and the 429 response

Lesson 1: Why Version an API?

Once mobile apps and other clients depend on your API, changing a field name breaks them. Versioning lets you release a new shape while old clients keep using the old one.

Analogy: A version is like a product edition. Owners of the old model keep their manual, and new buyers get the new one. Both still work.

The rule of thumb: add fields freely, but rename or remove them only in a new version.

Lesson 2: Choosing a Versioning Strategy

DRF offers several ways for a client to say which version it wants:

ClassHow the client asksExample
URLPathVersioningVersion in the URL path/api/v1/posts/
NamespaceVersioningURL namespace (v1, v2)/v1/posts/ via namespaces
QueryParameterVersioningQuery string parameter/api/posts/?version=2
AcceptHeaderVersioningMedia type in the Accept headerAccept: application/json; version=2.0
HostNameVersioningSubdomainv2.api.example.com
Most common choice: URLPathVersioning. The version is visible in logs, easy to test in a browser, and easy to cache.

Lesson 3: URL Path Versioning

Turn on the versioning class in settings, then give the URL a version part:

# settings.py
REST_FRAMEWORK = {
    # ...existing settings...
    "DEFAULT_VERSIONING_CLASS": "rest_framework.versioning.URLPathVersioning",
    "DEFAULT_VERSION": "1",
    "ALLOWED_VERSIONS": ["1", "2"],
}
# blog/urls.py
from django.urls import include, path
from rest_framework.routers import DefaultRouter
from .api_views import PostViewSet

router = DefaultRouter()
router.register("posts", PostViewSet, basename="post")

urlpatterns = [
    path("api//", include(router.urls)),
]

Inside a view, request.version holds the version string from the URL. A request for /api/3/posts/ is rejected because 3 isn't in ALLOWED_VERSIONS.

Check the URL pattern: The URL must contain the version segment, and its keyword must match VERSION_PARAM, which defaults to version. If it doesn't match, request.version will be None.

Lesson 4: Different Behaviour per Version

Branch on request.version inside the serializer or viewset. Keep the difference small and clear:

class PostViewSet(viewsets.ModelViewSet):
    queryset = Post.objects.all()

    def get_serializer_class(self):
        if self.request.version == "2":
            return PostSerializerV2     # renamed fields and new shape
        return PostSerializer           # the original v1 shape
GET /api/1/posts/ -> {"title": "Hello", "author": 3} GET /api/2/posts/ -> {"title": "Hello", "author": {"id": 3, "name": "Asha"}}
Two serializers, one queryset: Keeping the data access the same and changing only the serializer is the cleanest way to version. Your business logic stays in one place.
Don't let versions drift: Every fix to shared logic must reach both versions. Remove old versions on a schedule and announce the date in advance.

Lesson 5: Throttling Recap and Scoped Rates

Day 26 set global limits for anonymous and signed-in users. Often a single endpoint needs its own limit, such as a login or an expensive search. ScopedRateThrottle lets each view declare a named scope:

# settings.py
REST_FRAMEWORK = {
    # ...existing settings...
    "DEFAULT_THROTTLE_CLASSES": [
        "rest_framework.throttling.ScopedRateThrottle",
    ],
    "DEFAULT_THROTTLE_RATES": {
        "search": "30/minute",
        "uploads": "10/hour",
    },
}
from rest_framework.throttling import ScopedRateThrottle

class PostViewSet(viewsets.ModelViewSet):
    throttle_classes = [ScopedRateThrottle]
    throttle_scope = "search"
    # ...rest of the viewset...

Only views with a throttle_scope are limited, and only by that scope's rate. A view without a scope is not throttled by this class.

Rate format: Rates are number/period, where the period is second, minute, hour, or day. Examples: 100/hour, 5/second.

Lesson 6: The 429 Response

When a client goes over the limit, DRF returns 429 Too Many Requests. It also sends a Retry-After header with the number of seconds to wait:

HTTP/1.1 429 Too Many Requests Retry-After: 42 {"detail": "Request was throttled. Expected available in 42 seconds."}

A well-behaved client reads Retry-After and pauses. Your own tests can check the status code and that the header is present.

Lesson 7: A Custom Throttle

Sometimes you want to limit by something other than the IP or user, such as the API key in a header. Subclass SimpleRateThrottle and define the cache key:

# blog/throttles.py
from rest_framework.throttling import SimpleRateThrottle

class ApiKeyThrottle(SimpleRateThrottle):
    scope = "api_key"

    def get_cache_key(self, request, view):
        key = request.headers.get("X-API-Key")
        if not key:
            return None                 # None means: don't throttle this request
        return self.cache_format % {"scope": self.scope, "ident": key}
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_RATES": {
        # ...other scopes...
        "api_key": "500/day",
    },
}
Don't trust the header blindly: A client can change its X-API-Key value to escape the limit. Throttle by a value you verified (such as a token's user), or combine it with the IP address.
Returning None: If get_cache_key returns None, DRF skips throttling for that request. This is how you exempt internal calls.

Lesson 8: Testing Versions and Throttles

Throttle counts live in the cache, so tests must clear it between runs or earlier tests will affect later ones:

from django.core.cache import cache
from django.test import override_settings
from django.urls import reverse
from rest_framework import status
from rest_framework.test import APITestCase

class VersionAndThrottleTests(APITestCase):
    def setUp(self):
        cache.clear()

    def test_v1_returns_original_shape(self):
        response = self.client.get("/api/1/posts/")
        self.assertEqual(response.status_code, status.HTTP_200_OK)

    def test_unknown_version_is_rejected(self):
        response = self.client.get("/api/9/posts/")
        self.assertEqual(response.status_code, status.HTTP_404_NOT_FOUND)

    @override_settings(REST_FRAMEWORK={
        "DEFAULT_THROTTLE_CLASSES": ["rest_framework.throttling.AnonRateThrottle"],
        "DEFAULT_THROTTLE_RATES": {"anon": "2/minute"},
    })
    def test_third_anonymous_request_is_throttled(self):
        url = "/api/1/posts/"
        self.client.get(url)
        self.client.get(url)
        response = self.client.get(url)
        self.assertEqual(response.status_code, status.HTTP_429_TOO_MANY_REQUESTS)
        self.assertIn("Retry-After", response)
Why override_settings: Throttle classes read their rates when DRF loads them. Overriding the setting for one test keeps the low limit from affecting the rest of the suite.
Caching in tests: If your test settings use a cache that other tests share, cache.clear() in setUp is essential. Otherwise a test that runs later may get throttled by requests from an earlier test.

Common Mistakes on Day 27

  1. Mismatched URL keyword: the pattern must use <str:version>, or request.version is None.
  2. Forgetting ALLOWED_VERSIONS: unexpected versions can reach your code.
  3. Duplicated business logic across versions: share the queryset and service code; version only the shape.
  4. A scope with no matching rate: the throttle has nothing to enforce, so check DEFAULT_THROTTLE_RATES.
  5. Trusting client-supplied keys for throttling: verify them first.
  6. Not clearing the cache in tests: counts carry over between tests.
