Testing Your Django App

Estimated time: about 1.5 hours · Writing tests with TestCase, the test client, checking responses, redirects, templates and forms, and running the suite with manage.py test

Lesson 1: Why Test a Website?

A website changes constantly. A small edit to a model can break a page three folders away, and you may not notice until a visitor complains. Tests are automatic checks that run in seconds and tell you what broke.

Analogy: A smoke alarm. You hope never to need it, but it runs quietly in the background and warns you the moment something goes wrong.

Django's test framework builds on Python's unittest. Each test runs against a separate, temporary test database, so your real data is never touched.

Lesson 2: Test Structure

Put tests in blog/tests.py, which Django finds automatically. Each test class inherits from TestCase, and each method whose name starts with test_ is a test:

# blog/tests.py
from django.test import TestCase
from .models import Author, Post

class PostModelTests(TestCase):
    def setUp(self):
        self.author = Author.objects.create(name="Asha", email="asha@example.com")

    def test_word_count(self):
        post = Post.objects.create(author=self.author, title="Model tips",
                                   body="Keep models small.")
        self.assertEqual(post.word_count, 3)

Notice the assert methods. They are clearer than plain assert because they print helpful messages when they fail.

MethodChecks that
assertEqual(a, b)a equals b
assertTrue(x) / assertFalse(x)x is truthy or falsy
assertIn(a, b)a is in b
assertRaises(Error)the block raises the given error
Note: Each test method runs in its own transaction, which is rolled back afterwards. One test's data never leaks into another.

Lesson 3: setUp and setUpTestData

Creating the same objects in every test is slow and repetitive. Two methods help:

  • setUp() runs before every test method. Use it for objects a test might change.
  • setUpTestData() runs once for the whole class, and is faster. Use it for data that tests only read.
class PostListViewTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        author = Author.objects.create(name="Asha", email="asha@example.com")
        Post.objects.create(author=author, title="Visible post", body="Hello", is_published=True)
        Post.objects.create(author=author, title="Hidden draft", body="Secret", is_published=False)
Caution: Objects created in setUpTestData are shared across the class's tests. If one test changes them, Django protects the original for later tests, but you should still avoid modifying them.

Lesson 4: Testing Views with the Test Client

The self.client object acts like a browser. It sends requests to your URLs and gives you the response to inspect:

from django.urls import reverse

class PostListViewTests(TestCase):
    # ...setUpTestData from above...

    def test_page_loads(self):
        response = self.client.get(reverse("post_list"))
        self.assertEqual(response.status_code, 200)

    def test_only_published_posts_shown(self):
        response = self.client.get(reverse("post_list"))
        self.assertContains(response, "Visible post")
        self.assertNotContains(response, "Hidden draft")

    def test_correct_template_used(self):
        response = self.client.get(reverse("post_list"))
        self.assertTemplateUsed(response, "blog/post_list.html")
AssertionUse it to check
assertEqual(response.status_code, 200)The page returned successfully
assertContains(response, text)Text appears in the page
assertNotContains(response, text)Sensitive or hidden text does not appear
assertTemplateUsed(response, name)The right template was rendered
assertRedirects(response, url)A POST redirected to the expected page
Always use reverse(): If you hard-code /posts/ and the route changes, the test fails for the wrong reason. Using the route name keeps tests focused on behaviour.

Lesson 5: Testing Forms and POST Requests

To test a form, send the data a browser would send. Check both the successful path and the error path:

class PostCreateViewTests(TestCase):
    def setUp(self):
        self.author = Author.objects.create(name="Asha", email="asha@example.com")

    def test_valid_post_is_saved_and_redirects(self):
        response = self.client.post(reverse("post_create"), {
            "author": self.author.pk,
            "title": "A valid title",
            "body": "Body text",
            "is_published": True,
        })
        self.assertRedirects(response, reverse("post_list"))
        self.assertEqual(Post.objects.count(), 1)

    def test_short_title_is_rejected(self):
        response = self.client.post(reverse("post_create"), {
            "author": self.author.pk,
            "title": "Hi",
            "body": "Body text",
        })
        self.assertEqual(response.status_code, 200)
        self.assertContains(response, "at least 5 characters")
        self.assertEqual(Post.objects.count(), 0)
Test client and CSRF: The test client skips CSRF checks by default, so your POST tests don't need the token. Real browsers still need it; test the token separately if the protection is important to you.

Checking Post.objects.count() proves the database changed, not just that the page looked right. Test both.

Lesson 6: Testing Deletion

class PostDeleteViewTests(TestCase):
    def setUp(self):
        author = Author.objects.create(name="Asha", email="asha@example.com")
        self.post = Post.objects.create(author=author, title="To remove", body="Bye")

    def test_post_request_deletes_post(self):
        response = self.client.post(reverse("post_delete", args=[self.post.pk]))
        self.assertRedirects(response, reverse("post_list"))
        self.assertFalse(Post.objects.filter(pk=self.post.pk).exists())

A test like this protects a dangerous action. If someone later changes the view to delete on GET, the test shows the mistake quickly, because the post would be removed by a plain page visit.

Lesson 7: Running the Tests

python manage.py test
python manage.py test blog
python manage.py test blog.tests.PostListViewTests.test_only_published_posts_shown

A successful run looks like this. Timings vary on your machine:

Creating test database for alias 'default'... System check identified no issues (0 silenced). ........ ---------------------------------------------------------------------- Ran 8 tests in 0.214s OK Destroying test database for alias 'default'...

Each dot is one passing test. An F marks a failure and an E marks an error, which means the test itself crashed. Read the failure message: it shows the expected value and the actual value.

Pytest alternative: The pytest-django plugin runs Django tests with pytest, which you used on Day 26. Both approaches are common; choose one and be consistent.

Lesson 8: What to Test

Test thisBecause
Model methods and propertiesBusiness rules live here, and they should never break silently
Access rules (drafts hidden, deletes need POST)Security problems are costly and easy to introduce
Form validation (valid and invalid data)Bad input is the most common source of bugs
Redirects after successUsers expect a predictable path after each action
Each important page loadsA crash on a key page is the most visible failure
Don't test Django itself: Trust that save() saves and that the admin works. Test the rules your project adds on top.

Common Mistakes on Day 13

  1. Hard-coding URLs: use reverse() so tests survive route changes.
  2. Testing only the happy path: include invalid input and access checks.
  3. Forgetting the database check after a POST: the page may say "saved" while nothing changed.
  4. Writing tests that depend on each other: each test should create the data it needs.
  5. Using the real database for tests: Django's test runner creates a separate one automatically, so don't override it.
  6. Ignoring failing tests: a red test that stays red teaches the team to ignore the suite.

Practicals

Use your mini-blog project. Write the tests in blog/tests.py.

Practical 1: Model Test

Write a test that publish() sets is_published to True. Use refresh_from_db() before checking the value.

Practical 2: List Page Tests

Write three tests for the list view: the page returns 200, a published post is shown, and a draft is hidden.

Practical 3: Create Tests

Write one test for a valid submission that checks the redirect and the count, and one for a short title that checks the error message and that nothing was saved.

Practical 4: Delete Test

Write a test that a POST deletes the post, and a second test that a GET to the delete address does not delete it. Run the suite and confirm both pass.

Practical 5: Break and Fix

Change the list view to show drafts too, run the tests, and read the failure. Revert the change and confirm the tests pass again.
