Building a JSON API

Estimated time: about 1.5 hours · JSON responses with JsonResponse, listing and fetching objects, creating from JSON with validation and status codes, handling errors as JSON, and when to use Django REST framework

Lesson 1: What Is an API?

So far your views return HTML pages for people. An API (application programming interface) returns data, usually as JSON, for programs to use. A mobile app, a JavaScript page, or another server can all read the same posts without scraping HTML.

Analogy: A website is a restaurant dining room, where the food is plated for you. An API is the kitchen window, where the same food is handed over in a standard container for any delivery service to pick up.

JSON is a plain text format of keys and values, such as {"title": "Model tips", "views": 40}. Almost every language reads it.

Lesson 2: Returning JSON with JsonResponse

Django's JsonResponse converts a dictionary to JSON and sets the content type for you:

# blog/api.py
from django.http import JsonResponse

def api_hello(request):
    return JsonResponse({"message": "Hello from the API", "version": 1})
{"message": "Hello from the API", "version": 1}
Lists need a wrapper: By default, JsonResponse refuses a top-level list for security reasons. Wrap lists in a dictionary, such as {"results": [...]}, which is also easier to extend later with pagination info.

Lesson 3: Converting Objects to Dictionaries

Model objects are not JSON, so write a small function that chooses which fields to expose. Keeping this list explicit prevents accidentally sharing private fields:

# blog/api.py
def post_to_dict(post):
    return {
        "id": post.pk,
        "title": post.title,
        "body": post.body,
        "author": post.author.name,
        "published": post.is_published,
        "created_at": post.created_at.isoformat(),
    }
Expose deliberately: Never return model_to_dict or __dict__ blindly. A new sensitive field added later, such as an internal note, would leak to everyone who calls the API.

isoformat() turns a date into a standard text form, such as 2026-10-21T07:14:00+05:30, which every language can parse.

Lesson 4: Listing and Fetching

# blog/api.py
from django.http import JsonResponse
from django.views.decorators.http import require_http_methods
from .models import Post

@require_http_methods(["GET"])
def api_post_list(request):
    posts = Post.objects.filter(is_published=True).select_related("author")
    return JsonResponse({"results": [post_to_dict(p) for p in posts]})

@require_http_methods(["GET"])
def api_post_detail(request, pk):
    try:
        post = Post.objects.select_related("author").get(pk=pk, is_published=True)
    except Post.DoesNotExist:
        return JsonResponse({"error": "Post not found"}, status=404)
    return JsonResponse(post_to_dict(post))
# blog/urls.py
path("api/posts/", api.api_post_list, name="api_post_list"),
path("api/posts/<int:pk>/", api.api_post_detail, name="api_post_detail"),

A request to the list address returns:

{"results": [{"id": 1, "title": "Model tips", "body": "Keep models small.", "author": "Asha", "published": true, "created_at": "2026-10-21T07:14:00+05:30"}]}
Don't use get_object_or_404 in APIs: It returns the HTML 404 page, which an API client can't parse. Catch DoesNotExist and return a JSON error, as shown above.

Lesson 5: Creating from JSON

A client sends JSON in the request body. Read it with json.loads, reuse the form from Day 6 to validate, and return 201 Created on success:

# blog/api.py
import json
from django.http import JsonResponse
from django.views.decorators.http import require_http_methods
from .forms import PostForm

@require_http_methods(["POST"])
def api_post_create(request):
    try:
        data = json.loads(request.body)
    except json.JSONDecodeError:
        return JsonResponse({"error": "Request body must be valid JSON"}, status=400)

    form = PostForm(data)
    if not form.is_valid():
        return JsonResponse({"errors": form.errors.get_json_data()}, status=400)

    post = form.save()
    return JsonResponse(post_to_dict(post), status=201)

A client that sends a short title receives:

{"errors": {"title": [{"message": "Title must be at least 5 characters.", "code": "invalid"}]}}

Lesson 6: CSRF and API Clients

On Day 6 you learned that Django rejects POST requests without a CSRF token. That protects browsers from forged requests. A JavaScript page on your own site can send the token. A separate program such as a mobile app or a script cannot, so it receives 403 errors.

from django.views.decorators.csrf import csrf_exempt

@csrf_exempt
@require_http_methods(["POST"])
def api_post_create(request):
    ...
Exempt only with another protection: csrf_exempt removes the browser protection, so an exempt endpoint must require something else, such as an API token in the Authorization header. Never exempt an endpoint that uses cookies to identify the user.

Real APIs usually use token authentication, where each client sends a secret token that the server checks on every request. Keep the browser-facing views protected by CSRF, and secure the API with tokens.

Lesson 7: Testing an API

The test client works for APIs too. Use response.json() to read the body as a dictionary:

import json
from django.test import TestCase
from django.urls import reverse

class PostApiTests(TestCase):
    def setUp(self):
        self.author = Author.objects.create(name="Asha", email="asha@example.com")

    def test_create_returns_201(self):
        response = self.client.post(
            reverse("api_post_create"),
            data=json.dumps({"author": self.author.pk, "title": "API made", "body": "Hi", "is_published": True}),
            content_type="application/json",
        )
        self.assertEqual(response.status_code, 201)
        self.assertEqual(response.json()["title"], "API made")

    def test_short_title_returns_400(self):
        response = self.client.post(
            reverse("api_post_create"),
            data=json.dumps({"author": self.author.pk, "title": "Hi", "body": "Hi"}),
            content_type="application/json",
        )
        self.assertEqual(response.status_code, 400)
        self.assertIn("title", response.json()["errors"])
Send JSON properly: Use json.dumps for the data and set content_type="application/json". Sending a plain dictionary would be encoded as form data, and the view would not read it as JSON.

Lesson 8: Django REST Framework

Writing every API view by hand works well for learning, but real projects usually use Django REST framework (DRF). It adds:

  • Serializers: convert models to JSON and validate input in one class, replacing post_to_dict.
  • Viewsets and routers: build list, detail, create, update, and delete endpoints from a few lines.
  • Authentication and permissions: token and session auth, plus the permission classes from Day 17.
  • A browsable API: a web page for trying each endpoint.

Common Mistakes on Day 23

  1. Returning a top-level list: wrap it in a dictionary.
  2. Exposing every model field: choose fields explicitly.
  3. Using get_object_or_404 in an API: return a JSON error instead.
  4. Forgetting status codes: return 201 for creation and 400 for bad input.
  5. Exempting CSRF without other protection: add token authentication first.
  6. Sending form-encoded data to a JSON endpoint: set the content type and encode with json.dumps.

Practicals

Use your mini-blog project. Test with the shell, the test client, or a tool such as curl.

Add the api_hello view with JsonResponse, and visit it in the browser. Confirm the response is JSON.

Practical 2: Read-Only Endpoints

Add the list and detail endpoints. Confirm that unpublished posts never appear, and that an unknown ID returns a 404 with a JSON error.

Practical 3: Create Endpoint

Add the create endpoint. Send a valid post with curl or the test client, and confirm you receive status 201 and the new data.

Practical 4: Error Responses

Send invalid JSON, then a post with a short title. Record each status code and error body.
