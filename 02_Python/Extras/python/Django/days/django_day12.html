Errors, Debugging, and Custom Error Pages

Estimated time: about 1.5 hours · Reading tracebacks, raising HTTP errors, custom 404 and 500 pages, logging, and debugging with breakpoints

Lesson 1: Errors Are Information

Every developer meets errors daily. A good error tells you what went wrong, where, and why. Django's job is to show that clearly during development and to hide the details from visitors in production.

Analogy: A warning light on a car dashboard. The light doesn't fix the engine, but it tells you where to look. Read the light, then go to the engine.

Two modes control what visitors see:

SettingDevelopment (DEBUG = True)Production (DEBUG = False)
Unhandled exceptionDetailed traceback with code and variablesGeneric 500 error page, details written to logs
Missing pageDetailed list of URL patterns that were triedYour custom 404 page, or a simple default
Static filesServed by runserverServed by a web server, after collectstatic
Never deploy with DEBUG = True: The detailed pages reveal your code, settings, and sometimes secret keys. Keep it on only while developing.

Lesson 2: Reading a Traceback

A traceback lists the chain of calls that led to an error. Read it from the bottom up:

Traceback (most recent call last): File "blog/views.py", line 12, in post_detail post = Post.objects.get(pk=post_id) ... blog.models.Post.DoesNotExist: Post matching query does not exist.
  1. The last line names the error type and message: Post.DoesNotExist.
  2. The line above it shows the code that raised it, here the get() call.
  3. The lines above that show how you got there: the view, then the request handling.

The fix for this error is to use get_object_or_404 (Day 4), which returns a 404 page instead of crashing. Knowing the error name tells you which tool to reach for.

ErrorUsual causeTypical fix
DoesNotExistget() finds no rowget_object_or_404, or filter().first()
MultipleObjectsReturnedget() matches several rowsMake the lookup more specific, or use filter()
NoReverseMatchA {% url %} name or argument is wrongCheck name= and the argument types in urls.py
TemplateDoesNotExistThe template path is wrongCheck the folder structure and TEMPLATES settings
DisallowedHostThe domain is not in ALLOWED_HOSTSAdd the host name to ALLOWED_HOSTS
OperationalError: no such tableMigrations were not runmakemigrations then migrate

Lesson 3: Raising HTTP Errors on Purpose

Sometimes an error is the correct response. A visitor asks for a post that is a draft, or a user tries to open someone else's page. Raise the matching exception to send the right status code:

# blog/views.py
from django.core.exceptions import PermissionDenied
from django.http import Http404
from .models import Post

def post_detail(request, pk):
    try:
        post = Post.objects.get(pk=pk)
    except Post.DoesNotExist:
        raise Http404("No such post")
    if not post.is_published and not request.user.is_staff:
        raise PermissionDenied
    return render(request, "blog/post_detail.html", {"post": post})
ExceptionStatusMeaning
Http404404The page does not exist
PermissionDenied403The page exists, but this visitor may not see it
SuspiciousOperation400The request looks malformed or tampered with
Choosing a status: Use 404 when you don't want to reveal that something exists. For a draft post, many sites return 404 to outsiders, so they can't discover hidden content.

Lesson 4: Custom Error Pages

Create these templates in your project's templates folder. Django uses them automatically when DEBUG = False:

templates/ ├── base.html ├── 404.html # page not found ├── 403.html # permission denied └── 500.html # server error
# templates/404.html
{% extends "base.html" %}
{% block title %}Page not found{% endblock %}
{% block content %}
  <h1>Page not found</h1>
  <p>The page you asked for does not exist. <a href="{% url 'post_list' %}">Browse the posts</a>.</p>
{% endblock %}
Keep 500.html simple: The server error page may be shown when the database or the template engine has failed. A 500 template must not depend on the database, and it cannot use base.html if that file is the source of the error. Keep it static, with plain HTML and no template tags beyond the basics.

To test your 404 page locally, set DEBUG = False and ALLOWED_HOSTS = ["127.0.0.1", "localhost"], restart, and visit a missing address. Set DEBUG back to True afterwards.

Lesson 5: Logging

Printing to the console disappears when the server stops. Django uses Python's logging module, which can write to the console, a file, or an error-tracking service:

# mysite/settings.py
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "handlers": {
        "console": {"class": "logging.StreamHandler"},
    },
    "loggers": {
        "blog": {"handlers": ["console"], "level": "INFO"},
    },
}
# blog/views.py
import logging
from django.shortcuts import get_object_or_404, render
from .models import Post

logger = logging.getLogger(__name__)

def post_detail(request, pk):
    post = get_object_or_404(Post, pk=pk)
    logger.info("Viewing post %s", post.pk)
    return render(request, "blog/post_detail.html", {"post": post})
Viewing post 1
LevelUse for
debug()Detailed information during development
info()Normal events, such as a post being viewed
warning()Something unexpected that the app handled
error()A failure that needs attention
exception()An error, with the full traceback included automatically
Use %s, not f-strings, in logging calls: Logging formats the message only if that level is enabled, so it skips the work when the message won't be shown.

Lesson 6: Debugging with Breakpoints

Print statements work, but a breakpoint lets you pause the code and inspect every variable. Python 3.7 and later provide breakpoint():

# blog/views.py
def post_detail(request, pk):
    post = get_object_or_404(Post, pk=pk)
    breakpoint()                 # execution pauses here
    return render(request, "blog/post_detail.html", {"post": post})

When the request reaches that line, the terminal shows a (Pdb) prompt. Useful commands:

CommandAction
p postPrint a variable
p post.titlePrint an attribute
nRun the next line
cContinue until the next breakpoint
qQuit the debugger
Remove breakpoints before committing: A forgotten breakpoint() pauses the server for every visitor on a live site. Search your code for it before each commit.

Lesson 7: Built-in Checks

Before you run the server, ask Django to check your project for common problems:

python manage.py check
python manage.py check --deploy
System check identified no issues (0 silenced).

The first command checks your models, URLs, and settings. The second checks production settings, such as DEBUG, SECRET_KEY, and HTTPS options, and lists warnings you should fix before going live.

Common Mistakes on Day 12

  1. Leaving DEBUG = True in production: it exposes code and settings to anyone who triggers an error.
  2. Catching every exception silently: use specific exceptions, and log the rest. A bare except: hides real bugs.
  3. Making the 500 page depend on the database: it fails exactly when you need it.
  4. Using f-strings in logging calls: use %s arguments so formatting is deferred.
  5. Forgetting to read the last line of the traceback: it names the error, which is the fastest clue.

Practicals

Use your mini-blog project.

Practical 1: Trigger and Read an Error

Visit /posts/999/ with a missing id and read the traceback or 404 page. Write down the exception name, then change the view to use get_object_or_404 and confirm the error disappears.

Practical 2: Custom 404

Create templates/404.html, set DEBUG = False with the correct ALLOWED_HOSTS, and visit a missing page. Confirm your page appears. Restore DEBUG = True afterwards.

Practical 3: Permission Check

Add the draft check from Lesson 3 to post_detail. Confirm that an anonymous visitor gets an error for a draft post, and that the published post still loads.

Practical 4: Logging

Add the logging configuration and a logger.info line to the detail view. View a post and confirm the message appears in the terminal.

Practical 5: Breakpoint

Add breakpoint() to the detail view, visit the page, use p post.title at the (Pdb) prompt, then continue with c. Remove the breakpoint afterwards.
