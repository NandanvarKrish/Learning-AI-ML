DAY 25 of 30

Virtual Environments

Estimated time: about 1.5 hours · Why isolation matters, venv, activating and deactivating, requirements files, reproducible installs

Lesson 1: The Problem Virtual Environments Solve

On Day 13 you installed packages globally, so every project on your computer shares them. That causes trouble. Project A needs requests version 2.28, while project B needs version 2.31. Upgrading one breaks the other.

Analogy: A virtual environment is like giving each project its own toolbox. The carpentry project keeps its own saws, and the plumbing project keeps its own wrenches. Nobody borrows tools from a box they don't own.

A virtual environment is a folder containing its own Python interpreter and its own set of installed packages. Each project gets one.

Lesson 2: Creating a Virtual Environment

Python includes the venv module, so you don't need to install anything extra. Run this command in your project folder:

# Windows, Mac, and Linux
python -m venv venv

The second venv is the folder name. It's a convention, but you can use any name. A folder called venv or .venv appears inside your project.

On some Linux systems: If you see an error about ensurepip, install the venv support package for your distribution, such as python3-venv, then try again.

Lesson 3: Activating and Deactivating

Activating the environment makes the terminal use its Python and pip, instead of the global ones.

SystemCommand to activate
Windows (PowerShell)venv\Scripts\Activate.ps1
Windows (Command Prompt)venv\Scripts\activate.bat
Mac and Linuxsource venv/bin/activate

When it works, the terminal prompt shows the environment name in brackets, such as (venv).

# Check which Python and pip are in use
which python        # Mac and Linux
where python        # Windows

# Deactivate when you finish
deactivate
Windows note: If PowerShell says running scripts is disabled, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once, then try activating again.

Lesson 4: Installing Packages Inside an Environment

With the environment active, pip installs packages into it only. Nothing changes for your other projects.

# With (venv) showing in the prompt
pip install requests
pip list
Package Version ---------- ------- pip 24.x requests 2.31.0

The pip list output shows only the packages in this environment, not your global ones. Your version numbers may differ.

Safe habit: Activate the environment before every pip install. If the prompt doesn't show (venv), you are installing globally.

Lesson 5: Recording and Reproducing Dependencies

A requirements.txt file lists your project's packages and versions. Anyone can recreate the environment from it, including your future self on a new computer.

# Save the current packages
pip freeze > requirements.txt

# On another computer, after creating and activating a new venv
pip install -r requirements.txt
Contents of requirements.txt: certifi==2024.2.2 charset-normalizer==3.3.2 idna==3.7 requests==2.31.0 urllib3==2.2.1
Use pip freeze carefully: It lists every installed package, including the dependencies of your dependencies. For small projects, many developers write just the top-level packages by hand. Either way, keep the file up to date.

Lesson 6: Keeping Your Project Clean

  • Don't commit the venv folder to version control such as Git. It is large and specific to one computer. Commit requirements.txt instead.
  • Create a new environment per project, so dependencies never clash.
  • Upgrade pip inside the environment with python -m pip install --upgrade pip.
  • Delete and recreate a broken environment rather than trying to repair it. Since requirements.txt exists, you lose nothing.

A simple .gitignore entry for Python projects looks like this:

venv/
__pycache__/
*.pyc

Lesson 7: Choosing a Python Version

You can create an environment with a specific interpreter. This matters when a project needs an older or newer Python.

# Mac and Linux, if you have Python 3.11 installed
python3.11 -m venv venv311

# Windows, using the Python launcher
py -3.11 -m venv venv311

Check the version after activating with python --version.

Lesson 8: A Full Workflow

Here's the complete routine for starting a new project. Follow it once, and you'll remember it.

mkdir expense_app
cd expense_app
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install requests
pip freeze > requirements.txt
python main.py
deactivate

When you return to the project later, just activate the environment, and you'll be working with the same packages as before.

Common Mistakes on Day 25

  1. Forgetting to activate: packages install globally, and the program may then use the wrong versions.
  2. Committing the venv folder: it bloats the repository and doesn't work on other machines.
  3. Mixing global and project packages: the cause of most "it works on my machine" problems.
  4. Not updating requirements.txt: after adding a package, record it, or others can't reproduce the setup.
  5. Using the wrong activate script: Windows and Mac/Linux use different commands.

Practicals

Try each one before looking at any hints. Use a folder you can delete afterwards.

Practical 1: First Environment

Create a folder called practice_env, create a virtual environment inside it, and activate it. Confirm the prompt shows the environment name.

Practical 2: Compare Environments

With the environment active, run pip list. Deactivate it and run pip list again. Note how the two lists differ.

Practical 3: Install and Record

Inside the active environment, install requests. Create requirements.txt with pip freeze and open the file to read it.

Practical 4: Rebuild Elsewhere

Create a second folder with a new environment. Copy requirements.txt into it, then run pip install -r requirements.txt. Confirm requests is installed there too.

Practical 5: Two Versions

In two different environments, install different versions of the same package, such as requests==2.28.0 in one and requests==2.31.0 in the other. Check each version with pip show requests.

Practical 6: Project Setup Script

Write the workflow from Lesson 8 as a short checklist in a text file called setup_steps.txt. Follow your own checklist from scratch on a new folder to test it.
