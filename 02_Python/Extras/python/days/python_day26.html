Testing with pytest

Estimated time: about 1.5 hours · Why tests matter, writing test functions, assert, fixtures, parametrize, pytest.raises

Lesson 1: Why Test?

A test is a small program that checks whether another piece of code behaves as expected. Tests catch bugs early, and they let you change code later without fear, because you can run the tests again and see what broke.

Analogy: Tests are like a building inspector. The inspector checks each part against the plan. You don't wait until the roof collapses to find out a beam was weak.

Python has a built-in assert statement, and the pytest library builds on it to make testing much easier to organise and read.

Lesson 2: Installing pytest

Create a virtual environment first, as you learned on Day 25, then install pytest inside it.

# With your environment active
pip install pytest
pytest --version
pytest 8.x.x

Your version number may differ, but the commands work the same way.

Lesson 3: The assert Statement

assert checks that a condition is True. If it is False, Python raises an AssertionError.

x = 5
assert x == 5          # passes silently
assert x > 10          # raises AssertionError
Traceback (most recent call last): ... AssertionError
Note: Python can skip asserts when run with optimisation flags, so don't use assert to validate user input. Use if and raise, as you learned on Day 12.

Lesson 4: Writing Your First Test

Put the code you want to test in one file, and the tests in another file whose name starts with test_. pytest finds test files and test functions automatically, and any function whose name starts with test_ is a test.

Create calculator.py:

# calculator.py
def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ValueError("Cannot divide by zero")
    return a / b

Create test_calculator.py in the same folder:

# test_calculator.py
from calculator import add, divide

def test_add_positive_numbers():
    assert add(2, 3) == 5

def test_add_negative_numbers():
    assert add(-2, -3) == -5

def test_divide():
    assert divide(10, 2) == 5

Run pytest from the folder:

pytest
============ test session starts ============ collected 3 items test_calculator.py ... [100%] ============ 3 passed in 0.02s ============

Each dot means one passed test. A failure shows an F, and pytest prints the details.

Lesson 5: Reading a Failing Test

When a test fails, pytest shows the values it compared, which helps you find the problem.

def test_add_wrong():
    assert add(2, 2) == 5
E assert 4 == 5 E + where 4 = add(2, 2) test_calculator.py:12: AssertionError

The line starting with E shows what was expected and what happened. Read it first, then look at the line number.

Lesson 6: Testing Exceptions with pytest.raises

Sometimes the correct behaviour is to raise an error. pytest.raises checks that the right exception is raised.

import pytest
from calculator import divide

def test_divide_by_zero_raises():
    with pytest.raises(ValueError):
        divide(10, 0)

def test_error_message():
    with pytest.raises(ValueError, match="Cannot divide"):
        divide(1, 0)

If divide(10, 0) does not raise ValueError, the test fails. The match argument also checks the message text, using a regex from Day 24.

Lesson 7: Testing Many Cases with parametrize

Instead of writing one test per case, use @pytest.mark.parametrize to run the same test with several inputs.

import pytest
from calculator import add

@pytest.mark.parametrize("a, b, expected", [
    (1, 1, 2),
    (0, 5, 5),
    (-3, 3, 0),
    (10, -4, 6),
])
def test_add_cases(a, b, expected):
    assert add(a, b) == expected
test_calculator.py .... [100%] 4 passed
Why this helps: Each row is a separate test. If one row fails, pytest tells you exactly which inputs caused it, and the others still run.

Lesson 8: Fixtures for Shared Setup

A fixture is a function that prepares something for tests, such as a sample list or a temporary file. Mark it with @pytest.fixture, then name it as a parameter in any test that needs it.

import pytest

@pytest.fixture
def sample_scores():
    return [70, 85, 90]

def test_average(sample_scores):
    assert sum(sample_scores) / len(sample_scores) == 81.66666666666667

def test_max(sample_scores):
    assert max(sample_scores) == 90

Fixtures avoid repeating setup code in every test. pytest runs the fixture fresh for each test that uses it, so tests don't affect each other.

Temporary files with tmp_path

pytest provides a built-in fixture called tmp_path, a temporary folder that is removed after the tests finish. It's ideal for testing file code from Day 11.

def save_note(path, text):
    with open(path, "w") as f:
        f.write(text)

def test_save_note(tmp_path):
    file = tmp_path / "note.txt"
    save_note(file, "hello")
    assert file.read_text() == "hello"
Good habit: Tests should never touch your real data files. tmp_path keeps them isolated.

Lesson 9: Testing Classes

You can test classes from Days 15 to 21 the same way. Create an object inside the test and check its methods.

# bank.py
class Account:
    def __init__(self, balance=0):
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("Insufficient funds")
        self.balance -= amount

# test_bank.py
import pytest
from bank import Account

def test_withdraw_reduces_balance():
    acc = Account(100)
    acc.withdraw(30)
    assert acc.balance == 70

def test_overdraw_raises():
    acc = Account(50)
    with pytest.raises(ValueError):
        acc.withdraw(80)

Each test creates a fresh object, so one test never changes another's starting data.

Common Mistakes on Day 26

  1. Forgetting the test_ prefix: pytest skips functions and files that don't start with test_.
  2. Testing too much in one function: keep each test focused on one behaviour, so failures are easy to understand.
  3. Using assert for input validation: asserts can be disabled, so validate input with if and raise.
  4. Sharing state between tests: create fresh objects or use fixtures, so tests can run in any order.
  5. Running pytest outside the environment: it may not find your project's packages. Activate first.
  6. Writing a test that always passes: check that a test can fail, by temporarily breaking the code.

FixturesPreparing database connections or sample data shared across dozens of tests
Continuous integrationRunning the full test suite automatically every time code is pushed
Regression testsMaking sure a fixed bug never comes back
