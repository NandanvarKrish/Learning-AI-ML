OOP & Error Handling

An architect draws one blueprint for a house, then builds as many actual houses from it as needed — that's Object-Oriented Programming. And every good building has a safety protocol for when something goes wrong on site — that's error handling. Together, they're how real, reliable software gets built.

Topic 01

What Object-Oriented Programming actually is

OOP is a way of organizing code around things — objects that bundle together data (what they know) and behavior (what they can do), instead of scattering variables and functions loosely.

Real-world analogy A blueprint for a house isn't a house — it's a plan describing rooms, dimensions, and wiring. Once you build from it, you get an actual house you can live in. You can build many houses from one blueprint, each with its own address and paint color, but all following the same plan. In Python, the blueprint is called a class, and each built house is an object (or instance). 
# the blueprint
class House:
    def __init__(self, color):
        self.color = color

# building actual houses from the blueprint
house1 = House("blue")
house2 = House("red")

print(house1.color)   # blue
print(house2.color)   # red — separate house, separate paint

Why bother with OOP

Bundling

Data and the actions that work on it stay together, instead of passing variables between loose functions.

Reuse

One blueprint, unlimited buildings — no rewriting the plan for every new house.

Modeling reality

Cars, users, orders, accounts — real-world things map naturally onto objects.

Extending safely

New blueprints can build on old ones (inheritance) without touching the original plan.

class = blueprintobject = built instanceself = this specific houseinheritance = family of blueprints
Topic 02

Classes and objects

A class defines what every object of that kind will have and be able to do. An object is one specific instance actually built from that class.

class Dog:
    def __init__(self, name, breed):
        self.name = name
        self.breed = breed

    def bark(self):
        return f"{self.name} says woof!"

# two separate dogs, built from the same blueprint
dog1 = Dog("Rex", "Labrador")
dog2 = Dog("Milo", "Beagle")

print(dog1.bark())    # Rex says woof!
print(dog2.breed)     # Beagle
Real-world analogy "Dog" the concept is the blueprint. Rex and Milo are two actual dogs built from that same concept — same general shape (name, breed, the ability to bark), but each carrying its own specific details.

What __init__ does

__init__ is the move-in checklist that runs automatically the moment a new object is built — it's where you fill in that object's specific details.

dog1 = Dog("Rex", "Labrador")
# the moment this line runs, __init__ fires:
#   self.name = "Rex"
#   self.breed = "Labrador"
Topic 03

Attributes, methods, and self

An attribute is a piece of data an object holds (name, breed). A method is an action it can perform (bark). self is how a method refers back to "this particular object, not some other one."

Real-world analogy If Rex and Milo can both bark, the "bark" instruction has to somehow know whose mouth to use. self is that pointer — when you call dog1.bark(), Python quietly hands the method "this is the dog you're working with," so it says "Rex says woof," not "Milo says woof." 
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance      # instance attribute — unique per object

    def deposit(self, amount):
        self.balance += amount      # self makes sure THIS account's balance changes
        return self.balance

acc = BankAccount("Maya", 100)
acc.deposit(50)
print(acc.balance)    # 150

Class attributes vs. instance attributes

class Dog:
    species = "Canis familiaris"   # class attribute — shared by every dog

    def __init__(self, name):
        self.name = name              # instance attribute — unique per dog

print(dog1.species)   # same for every Dog object, like a shared species label
print(dog1.name)      # unique to this one dog

Class attributes are like a fact printed on every blueprint copy ("all dogs are Canis familiaris"). Instance attributes are like the details filled in on one specific house ("this house is painted blue").

Topic 04

Inheritance

Inheritance lets a new blueprint start from an existing one and only add or change what's different — instead of redrawing the whole plan from scratch.

Real-world analogy A "Bungalow" blueprint and a "Two-Story House" blueprint might both start from a general "House" blueprint (foundation, walls, roof), each adding their own specifics on top. Neither has to redraw the foundation from zero. 
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound."

class Dog(Animal):              # Dog inherits from Animal
    def speak(self):             # overrides Animal's version
        return f"{self.name} barks."

class Cat(Animal):
    def speak(self):
        return f"{self.name} meows."

generic = Animal("Some Creature")
dog = Dog("Rex")
cat = Cat("Momo")

for creature in [generic, dog, cat]:
    print(creature.speak())
# Some Creature makes a sound.
# Rex barks.
# Momo meows.

Calling the parent's version with super()

class Puppy(Dog):
    def __init__(self, name, age_months):
        super().__init__(name)   # reuse Animal's setup instead of rewriting it
        self.age_months = age_months

super() is like saying "build the foundation the same way the parent blueprint already does it, then I'll add my extra details on top."

Topic 05

Encapsulation & polymorphism

Two more ideas that make objects safer and more flexible to work with.

Encapsulation — protecting the internals

Real-world analogy A house's wiring is inside the walls, not dangling in the living room — you interact with a light switch, not the bare wires. Encapsulation hides an object's messy internal details behind a clean, safe interface (its methods). 
class BankAccount:
    def __init__(self, balance):
        self.__balance = balance     # double underscore signals "internal, don't touch directly"

    def get_balance(self):
        return self.__balance      # controlled access through a method

    def withdraw(self, amount):
        if amount > self.__balance:
            return "Insufficient funds."
        self.__balance -= amount
        return self.__balance

The double underscore doesn't make it impossible to access, but it's a strong signal: "go through the light switch, don't grab the bare wire."

Polymorphism — same call, different behavior

Real-world analogy "Open" means something different for a door, a jar, and a book — each object interprets the same instruction in its own way. That's polymorphism: calling .speak() on a Dog and a Cat runs different code, even though the call looks identical. 
for creature in [Dog("Rex"), Cat("Momo")]:
    print(creature.speak())   # same method name, different result per object
Topic 06

What error handling actually is

Things go wrong on a job site — a delivery is late, a measurement is off. A good crew has a plan for handling that without the whole project collapsing. Error handling is that plan for your code.

Real-world analogy Imagine a construction site with no safety protocol — the moment one thing goes wrong (a dropped tool, a wrong measurement), the entire crew stops and the whole build halts. A site with a safety plan absorbs the problem, logs it, and keeps working. An exception is the "something went wrong" signal; handling it is having a plan ready instead of the whole program crashing. 
# without handling — the whole program crashes here
number = int(input("Enter a number: "))   # crashes if the user types "abc"
# with handling — the problem is caught, the program keeps going
try:
    number = int(input("Enter a number: "))
except ValueError:
    print("That wasn't a valid number — using 0 instead.")
    number = 0

Common built-in exceptions

ValueError

Right type, wrong content — like int("abc").

TypeError

Wrong type entirely — like adding a string and a number.

KeyError

Looking up a dictionary key that doesn't exist.

ZeroDivisionError

Dividing by zero — undefined, and Python refuses.

FileNotFoundError

Trying to open a file that isn't there.

IndexError

Reaching for a list position that doesn't exist.

Topic 07

try / except / else / finally

This is the full safety protocol structure: attempt the risky step, catch specific problems, celebrate if nothing went wrong, and always clean up at the end.

try:
    result = 10 / int(input("Divide 10 by: "))
except ZeroDivisionError:
    print("Can't divide by zero.")
except ValueError:
    print("That wasn't a number.")
else:
    print(f"Success: {result}")     # runs only if try had NO problems
finally:
    print("Attempt finished.")      # always runs — success or failure
Real-world analogy try is attempting the risky step. Each except is a specific contingency plan for a specific kind of problem — a different response for "wrong tool" versus "missing material." else is what happens when nothing went wrong at all. finally is the site cleanup that happens no matter what — successful build or not, you still lock up the tools at the end.

Catching multiple exception types together

try:
    risky_operation()
except (ValueError, TypeError) as e:
    print(f"Something went wrong: {e}")

Catching anything (use carefully)

try:
    risky_operation()
except Exception as e:
    print(f"Unexpected issue: {e}")

A bare except: or overly broad except Exception: is like a safety plan that says "if anything at all happens, just shrug" — it can hide real bugs. Catch the specific problems you actually expect wherever possible.

Topic 08

Raising exceptions & building your own

Sometimes your own code needs to raise the alarm on purpose — flagging a problem before it causes something worse downstream.

Raising a built-in exception

def set_age(age):
    if age < 0:
        raise ValueError("Age cannot be negative.")
    return age

set_age(-5)   # raises ValueError: Age cannot be negative.
Real-world analogy raise is a foreman spotting a problem and sounding the alarm deliberately, before a bad measurement gets built into the wall — better to stop early with a clear reason than let it cause a collapse later.

Custom exception classes

Just like you can design your own blueprint (class) for a house, you can design your own exception — a specific, named alarm for a specific kind of problem in your program.

class InsufficientFundsError(Exception):
    """Raised when a withdrawal exceeds the account balance."""
    pass

class BankAccount:
    def __init__(self, balance):
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise InsufficientFundsError(
                f"Tried to withdraw {amount}, only {self.balance} available."
            )
        self.balance -= amount
        return self.balance

acc = BankAccount(100)
try:
    acc.withdraw(500)
except InsufficientFundsError as e:
    print(f"Blocked: {e}")

Custom exceptions make your alarms specific and self-explanatory — InsufficientFundsError tells you exactly what went wrong, instead of a generic error that leaves you guessing.

Topic 09 · Build something real

Project: a safe bank account system

We'll build a small banking system with classes, inheritance, and custom exceptions — the same foundational shape behind any real banking app's account logic.

The brief Model a bank account as a class with safe deposit and withdrawal methods. Build a SavingsAccount that extends it with interest. Guard every risky operation with proper error handling, using custom exceptions for domain-specific problems.
1

Design the custom exceptions first

Decide what can specifically go wrong, and give each one a clear, named alarm.

class InsufficientFundsError(Exception):
    pass

class InvalidAmountError(Exception):
    pass
2

Build the base Account blueprint

Encapsulate the balance, and guard both deposit and withdraw with validation.

class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.__balance = balance

    def get_balance(self):
        return self.__balance

    def deposit(self, amount):
        if amount <= 0:
            raise InvalidAmountError("Deposit must be positive.")
        self.__balance += amount
        return self.__balance

    def withdraw(self, amount):
        if amount <= 0:
            raise InvalidAmountError("Withdrawal must be positive.")
        if amount > self.__balance:
            raise InsufficientFundsError(
                f"{self.owner} has only {self.__balance}, tried to withdraw {amount}."
            )
        self.__balance -= amount
        return self.__balance
3

Extend it with inheritance

A SavingsAccount is still an Account — it just adds interest behavior on top, reusing everything from the parent blueprint.

class SavingsAccount(Account):
    def __init__(self, owner, balance=0, rate=0.02):
        super().__init__(owner, balance)
        self.rate = rate

    def apply_interest(self):
        interest = self.get_balance() * self.rate
        self.deposit(interest)
        return self.get_balance()
4

Use try/except/else/finally around every risky call

Wrap the actual banking operations the way a teller would follow a safety checklist for every transaction.

acc = SavingsAccount("Maya", 200)

try:
    acc.withdraw(500)
except InsufficientFundsError as e:
    print(f"Transaction blocked: {e}")
except InvalidAmountError as e:
    print(f"Invalid request: {e}")
else:
    print("Withdrawal successful.")
finally:
    print(f"Current balance: {acc.get_balance()}")
5

Run the account through a realistic sequence

Deposit, apply interest, and attempt a safe withdrawal — showing the whole system working together.

acc.deposit(100)
acc.apply_interest()
print(f"Balance after interest: {acc.get_balance()}")

try:
    acc.withdraw(50)
except (InsufficientFundsError, InvalidAmountError) as e:
    print(f"Error: {e}")
else:
    print("Withdrawal went through cleanly.")
What you just practiced Class design, __init__ and self, encapsulation with a private balance, inheritance with super(), custom exception classes, and the full try / except / else / finally structure — all working together in one coherent, realistic system.
