Model Methods, Managers, and Signals

Estimated time: about 1.5 hours · Putting behaviour where the data lives: model methods and properties, Meta options, custom QuerySets and managers, constraints, and signals

Lesson 1: Fat Models, Thin Views

Views and templates should describe what the page shows. Rules about the data itself, such as "a published post needs a body" or "word count of an article", belong on the model. Then every view, form, admin page, and shell session follows the same rule.

Analogy: A model is the engine of a car, and views are the dashboard. If the engine rules are written on the dashboard, every new car needs them rewritten. Keep the rules in the engine.

This principle is often called "fat models, thin views". It keeps your logic in one place and easy to test.

Lesson 2: Model Methods

A method on a model can read and change its own data. Add a few useful ones to the Post model from the mini blog:

# blog/models.py
from django.db import models
from django.urls import reverse

class Post(models.Model):
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name="posts")
    title = models.CharField(max_length=200)
    body = models.TextField()
    created_at = models.DateTimeField(auto_now_add=True)
    is_published = models.BooleanField(default=False)

    def __str__(self):
        return self.title

    def publish(self):
        self.is_published = True
        self.save(update_fields=["is_published"])

    def get_absolute_url(self):
        return reverse("post_detail", args=[self.pk])

    @property
    def word_count(self):
        return len(self.body.split())

Use them like any other attribute or method:

>>> post = Post.objects.get(title="Model tips")
>>> post.word_count
>>> post.publish()
>>> post.is_published
>>> post.get_absolute_url()
3 True '/posts/1/'

The word count uses the sample body "Keep models small.", which has three words. The URL uses the primary key 1, so your number may differ.

KindWhen to use
Method (publish())An action that changes data or needs arguments
Property (@property word_count)A read-only value calculated from fields
get_absolute_url()The canonical address of one object, used by admin's "View on site" and by templates
Use update_fields: save(update_fields=[...]) writes only the named columns. This avoids overwriting changes that another request made to other fields at the same time.

Lesson 3: Custom QuerySets with Chaining

Filters such as "published posts" get repeated across views. A custom QuerySet lets you name them and chain them together:

# blog/models.py
class PostQuerySet(models.QuerySet):
    def published(self):
        return self.filter(is_published=True)

    def by_author(self, name):
        return self.filter(author__name=name)

class Post(models.Model):
    # ...fields from above...
    objects = PostQuerySet.as_manager()
>>> Post.objects.published().by_author("Asha").order_by("title")
<QuerySet [<Post: Model tips>, <Post: Views explained>]>

Because each method returns a QuerySet, you can chain as many as you need. as_manager() exposes these methods on Post.objects as well.

Naming tip: Name queryset methods after the business meaning, such as published(), rather than the field, such as filter_is_published(). Views then read like plain English.

Lesson 4: Custom Managers

A manager is the object behind Post.objects. You can add a second manager for a common view of the data, such as only published posts:

# blog/models.py
class PublishedManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().filter(is_published=True)

class Post(models.Model):
    # ...fields...
    objects = models.Manager()          # keep the default first
    published = PublishedManager()
>>> Post.published.all().order_by("title")
<QuerySet [<Post: Model tips>, <Post: Views explained>]>
Order matters: The first manager defined on a model becomes the default. Django uses the default for related lookups, admin pages, and some built-in operations. Put the plain objects manager first, so no records are hidden by accident.

For most projects, a custom QuerySet with as_manager() (Lesson 3) is more flexible than a custom manager. Use a custom manager when you need to change the base queryset for everyone.

Lesson 5: Meta Options

The inner Meta class controls how the model behaves across the project:

class Post(models.Model):
    # ...fields...

    class Meta:
        ordering = ["-created_at"]
        verbose_name = "article"
        verbose_name_plural = "articles"
        constraints = [
            models.UniqueConstraint(
                fields=["author", "title"],
                name="unique_title_per_author",
            ),
        ]
OptionEffect
orderingDefault order for every query on this model
verbose_name / verbose_name_pluralNames shown in the admin, such as "Articles" instead of "Posts"
constraintsRules enforced by the database, such as unique combinations
indexesSpeeds up searches on columns you filter often

A constraint is enforced by the database itself, so it holds even when code elsewhere forgets to check. Create a migration after adding one, as usual:

python manage.py makemigrations blog
python manage.py migrate
Constraint errors: Creating a duplicate title for the same author now raises IntegrityError. Forms check uniqueness for you, but shell code and imports need to handle the exception.

Lesson 6: Signals

A signal announces that something happened, such as a model being saved. Receivers listen for the signal and react. This lets you add behaviour without editing the model or the view that saved it.

# blog/signals.py
from django.db.models.signals import post_save
from django.dispatch import receiver
from .models import Post

@receiver(post_save, sender=Post)
def announce_new_post(sender, instance, created, **kwargs):
    if created and instance.is_published:
        print(f"New post published: {instance.title}")

Connect the receiver when the app starts, in apps.py:

# blog/apps.py
from django.apps import AppConfig

class BlogConfig(AppConfig):
    name = "blog"

    def ready(self):
        from . import signals  # noqa: F401
New post published: Hello Django

The output appears when a new published post is saved, for example from the shell or the admin.

Use signals with care: Signals hide the connection between actions. When a signal sends an email or changes other data, a later developer may not know it happens. Prefer explicit method calls for core logic, and keep signals for side effects such as logging, cache clearing, or notifications.

Common Mistakes on Day 10

  1. Putting business rules only in views: the same rule must then be repeated in the admin, forms, and shell.
  2. Defining a custom manager first: it becomes the default and can hide records.
  3. Forgetting to make a migration after adding a constraint: the database keeps its old rules.
  4. Using a signal for something the caller should control explicitly: the code becomes hard to follow.
  5. Calling save() without update_fields in a method that changes one field: it can overwrite concurrent changes.
