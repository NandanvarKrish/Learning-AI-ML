DJANGO DAY 22 of 30

Deployment Basics

Estimated time: about 1.5 hours · How a Django site runs in production: WSGI and Gunicorn, a reverse proxy, static files, running migrations on release, process management, and a launch checklist

Lesson 1: What Happens When a Site Goes Live

On your laptop, runserver handles everything. It is convenient but not built for real traffic or safety. A production site is a small team of programs, each with one job:

Visitor's browser │ HTTPS (port 443) ▼ Reverse proxy (Nginx or similar) ├── serves /static/ and /media/ files directly └── forwards everything else │ HTTP (internal) ▼ Application server (Gunicorn) │ runs several copies of your Django code ▼ Django project ──► Database (PostgreSQL)
Analogy: A restaurant has a host at the door (the reverse proxy), several kitchen staff working in parallel (the application server), and the recipe book and pantry (Django and the database). Each does one job well.

Django is the kitchen, not the front door. Its job is to produce responses; the surrounding programs handle connections, encryption, and static files.

Lesson 2: WSGI and Gunicorn

Django exposes a standard entry point called WSGI in mysite/wsgi.py, which you saw on Day 1. An application server such as Gunicorn loads that entry point and runs several worker processes, so multiple requests can run at once:

pip install gunicorn
gunicorn mysite.wsgi:application --bind 127.0.0.1:8000 --workers 3
[INFO] Starting gunicorn [INFO] Listening at: http://127.0.0.1:8000 (...) [INFO] Booting worker with pid: ... [INFO] Booting worker with pid: ... [INFO] Booting worker with pid: ...

A common starting point for the number of workers is about two per CPU core, plus one. Measure before changing it, because too many workers use memory without speeding anything up.

Do not use runserver in production: Django's own development server is not designed for security or load. Always put Gunicorn (or a similar server) behind a reverse proxy.

Lesson 3: The Reverse Proxy

A reverse proxy such as Nginx accepts connections from the internet, handles HTTPS, and passes the requests to Gunicorn. It is also the fastest way to serve static files:

# /etc/nginx/sites-available/mini-blog  (example)
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;        # redirect plain HTTP to HTTPS
}

server {
    listen 443 ssl;
    server_name example.com www.example.com;
    # ssl_certificate and ssl_certificate_key lines go here (from your certificate provider)

    location /static/ {
        alias /srv/mini-blog/staticfiles/;       # collectstatic output (Day 5)
    }

    location /media/ {
        alias /srv/mini-blog/media/;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;        # Gunicorn
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
Why the forwarded headers matter: Django sees only the connection from Nginx. The X-Forwarded-Proto header tells it the visitor used HTTPS. Set SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https") in production settings, so Django knows the request is secure.
Trust only your proxy: Set SECURE_PROXY_SSL_HEADER only when your proxy overwrites this header. Otherwise, a visitor could send the header themselves.

Lesson 4: Static Files in Production

Run collectstatic (Day 5) on every release, so the proxy has a complete folder to serve:

export DJANGO_SETTINGS_MODULE=mysite.settings.prod
python manage.py collectstatic --noinput
142 static files copied to '/srv/mini-blog/staticfiles'.

Two alternatives are common. WhiteNoise is a middleware that serves static files from Django itself, which suits small sites with no separate proxy for assets. A CDN (content delivery network) copies static files to servers near visitors, which suits large sites.

Media files are different: Uploads change at runtime and are not part of the release. Keep them on a persistent location, or cloud storage for larger sites, so a new deploy never wipes them.

Lesson 5: Releasing a New Version

Each release follows the same order, so the site never runs new code with an old database or missing static files:

  1. Get the new code, and install packages from requirements.txt.
  2. Run collectstatic to refresh the static files.
  3. Run migrate to update the database (Day 2).
  4. Restart Gunicorn so it loads the new code.
pip install -r requirements.txt
python manage.py collectstatic --noinput
python manage.py migrate --noinput
sudo systemctl restart mini-blog
Migrations come before the restart: If the new code expects a new column, it must exist before the new code runs. Also, make migrations backward-compatible when you can, because a rollback may run the old code against the new database.

Lesson 6: Keeping Gunicorn Running

On a Linux server, systemd starts Gunicorn at boot and restarts it after a crash. Create a service file:

# /etc/systemd/system/mini-blog.service  (example)
[Unit]
Description=Mini Blog Gunicorn service
After=network.target

[Service]
User=www-data
WorkingDirectory=/srv/mini-blog
EnvironmentFile=/etc/mini-blog.env
ExecStart=/srv/mini-blog/venv/bin/gunicorn mysite.wsgi:application --bind 127.0.0.1:8000 --workers 3
Restart=always

[Install]
WantedBy=multi-user.target

The EnvironmentFile line loads the secrets from Day 21 (such as DJANGO_SECRET_KEY) from a file that only the server can read. Enable and start it with:

sudo systemctl enable --now mini-blog
sudo systemctl status mini-blog
Other options: Platform-as-a-service hosts and containers handle the same jobs (running Gunicorn, restarting it, and injecting environment variables) with their own configuration. The concepts here carry over.

Lesson 7: Logs, Backups, and Rollback

PracticeWhy
Read logs regularly (journalctl -u mini-blog)Errors you ignore today become outages tomorrow
Back up the database on a scheduleMistakes, attacks, and hardware failures happen; a tested backup is the only recovery
Test restoring a backupAn untested backup may not work when you need it
Keep the previous release availableLets you roll back quickly if the new one fails

Backups are the last line of defence: A backup you have never restored is a hope, not a plan. Schedule a restore test on a separate server at least once.

Lesson 8: The Launch Checklist

Work through this list before the first public visit:

  • DEBUG = False and ALLOWED_HOSTS lists your real domains only.
  • The secret key comes from the environment, and is unique to production.
  • python manage.py check --deploy shows no warnings you haven't accepted.
  • HTTPS works, and plain HTTP redirects to it.
  • collectstatic has run, and static files load on every page.
  • Migrations have been applied, and the admin login works.
  • Email sends in production (test with a real address you own).
  • Custom 404 and 500 pages appear (Day 12).
  • A database backup has run and been restored successfully at least once.
  • Logs are readable, and someone is notified of errors.

Common Mistakes on Day 22

  1. Running runserver in production: use Gunicorn behind a reverse proxy.
  2. Forgetting collectstatic: styles and scripts go missing on the live site.
  3. Restarting before migrating: the new code runs against an old database.
  4. Trusting proxy headers from anyone: configure the proxy and SECURE_PROXY_SSL_HEADER together.
  5. Storing uploads in the release folder: a redeploy can delete them.
  6. Skipping backup restore tests: the first real restore is the wrong time to find out it fails.

Practicals

You can practise most of this locally, without a public server.

Practical 1: Run with Gunicorn

Install Gunicorn in your virtual environment, then run it with the prod settings and a placeholder secret key. Visit the site at 127.0.0.1:8000 and record the startup lines.

Practical 2: Static Files Check

Run collectstatic, then start Gunicorn. Note which static files you expect the proxy to serve, and explain why Gunicorn alone is not ideal for them.

Practical 3: Write a Service File

Write the systemd unit from Lesson 6 for your project, using your own paths. Check it with systemd-analyze verify if you have a Linux machine, or review it line by line otherwise.

Practical 4: Release Script

Write a short shell script that runs the four release steps in the correct order and stops on the first error (add set -e at the top).

Practical 5: Launch Checklist

Go through the checklist for mini-blog. Mark each item done or not done, and list the three items you would fix first.
