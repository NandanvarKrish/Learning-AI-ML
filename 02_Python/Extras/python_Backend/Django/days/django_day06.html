DJANGO DAY 6 of 30

Forms and User Input

Estimated time: about 1.5 hours · Form classes, ModelForm, handling GET and POST, validation, cleaned_data, CSRF protection, and redirect after POST

Lesson 1: Why Forms Matter

Almost every useful site receives input: sign-up forms, comments, search boxes, and checkout pages. Users make mistakes, and some enter malicious data. Django's form system handles the hard parts: displaying fields, checking values, showing errors, and protecting against attacks.

Analogy: A form is a bouncer at the door. It checks every guest's ticket (the data) against the rules before anyone gets inside the venue (your database).

Never trust data from the browser. Anyone can send any values, even ones your HTML doesn't offer. Django's forms validate on the server, which is where the real checking must happen.

Lesson 2: A Plain Form Class

Create blog/forms.py and describe the fields. Django builds the HTML inputs for you:

# blog/forms.py
from django import forms

class ContactForm(forms.Form):
    name = forms.CharField(max_length=50)
    email = forms.EmailField()
    message = forms.CharField(widget=forms.Textarea)

Test it in the shell before using it in a page. Passing a dictionary of data creates a bound form, which can be validated:

>>> from blog.forms import ContactForm
>>> f = ContactForm({"name": "Sam", "email": "bad", "message": "Hi"})
>>> f.is_valid()
False
>>> list(f.errors["email"])
['Enter a valid email address.']

>>> g = ContactForm({"name": "Sam", "email": "sam@example.com", "message": "Hi"})
>>> g.is_valid()
True
>>> g.cleaned_data["email"]
'sam@example.com'
False ['Enter a valid email address.'] True 'sam@example.com'
Field typeChecks
CharFieldText, with optional max_length and min_length
EmailFieldA valid email format
IntegerFieldA whole number, with optional min_value and max_value
BooleanFieldA checkbox
DateFieldA valid date
ChoiceFieldOne value from a list
Key idea: cleaned_data holds only the validated, converted values. Always use cleaned_data, never the raw request data.

Lesson 3: ModelForm

Most forms create or edit a model. A ModelForm builds the fields from the model, so you don't repeat yourself:

# blog/forms.py
from django import forms
from .models import Post

class PostForm(forms.ModelForm):
    class Meta:
        model = Post
        fields = ["author", "title", "body", "is_published"]

The fields list controls what appears in the form. Leave out fields the user shouldn't set, such as created_at, which is filled in automatically.

Watch the required fields: A post needs an author. If you leave author out of fields, saving will fail, because the database requires a value. Include it, or set it in the view before saving.

Lesson 4: Handling GET and POST in a View

A form page does two jobs: show an empty form (GET), and process submitted data (POST). Handle both in one view:

# blog/views.py
from django.shortcuts import redirect, render
from .forms import PostForm

def post_create(request):
    if request.method == "POST":
        form = PostForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect("post_list")
    else:
        form = PostForm()
    return render(request, "blog/post_form.html", {"form": form})

Add the route in blog/urls.py:

path("posts/new/", views.post_create, name="post_create"),

Here's the flow:

  1. GET: the view creates an empty form and shows it.
  2. POST: the view creates a form from the submitted data and checks it.
  3. If the data is valid, it saves and redirects. If not, the same page appears again with error messages.
Post/Redirect/Get: After a successful save, always redirect(). If you rendered a page instead, refreshing the browser would submit the form a second time and could create duplicate posts.

Lesson 5: The Template and CSRF Protection

# blog/templates/blog/post_form.html
{% extends "base.html" %}
{% block content %}
  <h1>New post</h1>
  <form method="post">
    {% csrf_token %}
    {{ form.as_p }}
    <button type="submit">Save</button>
  </form>
{% endblock %}

Two details matter here:

  • {% csrf_token %} adds a hidden token. Django checks it on every POST, which blocks attacks that trick a logged-in user's browser into submitting forms on another site (CSRF).
  • {{ form.as_p }} prints every field with its label, input, and error messages, each wrapped in a paragraph. Other options are as_table, as_ul, and as_div.
Common error: Forgetting {% csrf_token %} makes every submission fail with "CSRF verification failed" (HTTP 403). Always include it in POST forms.

When a field has an error, Django shows it automatically. For example, a title that is too short appears as:

<ul class="errorlist"><li>Title must be at least 5 characters.</li></ul>

Lesson 6: Custom Validation

Add rules beyond the field types with a clean_<fieldname> method. Raise ValidationError when a value is not acceptable:

# blog/forms.py
from django import forms
from .models import Post

class PostForm(forms.ModelForm):
    class Meta:
        model = Post
        fields = ["author", "title", "body", "is_published"]

    def clean_title(self):
        title = self.cleaned_data["title"].strip()
        if len(title) < 5:
            raise forms.ValidationError("Title must be at least 5 characters.")
        if title.isupper():
            raise forms.ValidationError("Please don't write the title in capitals only.")
        return title

Rules that involve several fields belong in clean():

    def clean(self):
        cleaned = super().clean()
        if cleaned.get("is_published") and not cleaned.get("body"):
            raise forms.ValidationError("A published post needs body text.")
        return cleaned
Order matters: Django runs each clean_<field> method first, then clean(). Always call super().clean() in clean() so the default checks still run.

Lesson 7: Editing an Existing Object

To edit a post, pass the existing object as instance. The form then fills in the current values and saves changes to that object instead of creating a new one:

# blog/views.py
from django.shortcuts import get_object_or_404, redirect, render
from .forms import PostForm
from .models import Post

def post_edit(request, post_id):
    post = get_object_or_404(Post, pk=post_id)
    if request.method == "POST":
        form = PostForm(request.POST, instance=post)
        if form.is_valid():
            form.save()
            return redirect("post_list")
    else:
        form = PostForm(instance=post)
    return render(request, "blog/post_form.html", {"form": form})

The same template works for creating and editing, because the form holds all the information it needs.

Common Mistakes on Day 6

  1. Using request.POST data directly: use form.cleaned_data after is_valid().
  2. Forgetting {% csrf_token %}: POST requests fail with a 403 error.
  3. Saving without calling is_valid(): invalid data can reach the database.
  4. Rendering instead of redirecting after success: refreshing causes duplicate submissions.
  5. Leaving required fields out of fields: the save fails with an integrity error.
  6. Forgetting instance= when editing: Django creates a new object instead of updating the existing one.
