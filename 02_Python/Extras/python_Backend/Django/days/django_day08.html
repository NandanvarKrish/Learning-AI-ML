Class-Based Views

Estimated time: about 1.5 hours · Generic views, as_view(), ListView, DetailView, CreateView, UpdateView, DeleteView, and customising them with get_queryset and get_context_data

Lesson 1: From Functions to Classes

On Day 7 you wrote five views for the mini blog. Each one repeated the same steps: fetch objects, render a template, handle a form, redirect. Django's class-based views (CBVs) package those steps so you configure a view instead of rewriting it.

Analogy: Writing a function view is like building a car from parts each time. A class-based view is a ready-made car where you choose the colour, engine, and seats. You still have full control, but you start from a working design.
StyleGood forTrade-off
Function-based viewCustom logic that doesn't fit a patternMore code for common tasks
Class-based viewStandard patterns: lists, details, forms, deletesYou need to learn which methods to override

Both styles are normal in real projects. Choose whichever makes the code shorter and clearer.

Lesson 2: The Basic Pattern

A class-based view is a class with a method for each HTTP verb (get, post, and so on). Generic views already implement those methods for common tasks, so you only set attributes:

# blog/views.py
from django.views.generic import ListView
from .models import Post

class PostListView(ListView):
    model = Post
    template_name = "blog/post_list.html"
    context_object_name = "posts"

In urls.py, call as_view(). It turns the class into a function that Django can call:

from .views import PostListView

urlpatterns = [
    path("posts/", PostListView.as_view(), name="post_list"),
]
Don't forget as_view(): Passing the class itself, without () or as_view(), causes a confusing error. Django needs the function that as_view() returns.

Lesson 3: The Five Core Generic Views

ViewDoesDefault templateDefault context name
ListViewShows many objectsapp/model_list.htmlobject_list and model_list
DetailViewShows one objectapp/model_detail.htmlobject and model
CreateViewShows and processes a form to createapp/model_form.htmlform
UpdateViewShows and processes a form to editapp/model_form.htmlform, object, and model
DeleteViewConfirms, then deletesapp/model_confirm_delete.htmlobject and model

The model name is lowercased in the context. For Post, the detail view provides both object and post. Setting context_object_name lets you choose a friendlier name.

Tip: When a view's template name is the default, you can leave out template_name entirely. Keeping it explicit, as in the mini blog, makes the code easier to read.

Lesson 4: Rewriting the Mini Blog

Here are the Day 7 function views rewritten as classes. The behaviour stays the same, and far less code is needed:

# blog/views.py
from django.urls import reverse, reverse_lazy
from django.views.generic import (
    CreateView, DeleteView, DetailView, ListView, UpdateView,
)
from .forms import PostForm
from .models import Post

class PostListView(ListView):
    model = Post
    template_name = "blog/post_list.html"
    context_object_name = "posts"

    def get_queryset(self):
        return Post.objects.filter(is_published=True)

class PostDetailView(DetailView):
    model = Post
    template_name = "blog/post_detail.html"
    context_object_name = "post"

    def get_queryset(self):
        return Post.objects.filter(is_published=True)

class PostCreateView(CreateView):
    model = Post
    form_class = PostForm
    template_name = "blog/post_form.html"
    success_url = reverse_lazy("post_list")

class PostUpdateView(UpdateView):
    model = Post
    form_class = PostForm
    template_name = "blog/post_form.html"

    def get_success_url(self):
        return reverse("post_detail", args=[self.object.pk])

class PostDeleteView(DeleteView):
    model = Post
    template_name = "blog/post_confirm_delete.html"
    success_url = reverse_lazy("post_list")

The URL patterns change only by adding .as_view() to each view:

# blog/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("posts/", views.PostListView.as_view(), name="post_list"),
    path("posts/new/", views.PostCreateView.as_view(), name="post_create"),
    path("posts/<int:pk>/", views.PostDetailView.as_view(), name="post_detail"),
    path("posts/<int:pk>/edit/", views.PostUpdateView.as_view(), name="post_edit"),
    path("posts/<int:pk>/delete/", views.PostDeleteView.as_view(), name="post_delete"),
]
Name change: Generic views look up objects by pk by default, so the URL parameter is now <int:pk> instead of <int:post_id>. Update the templates' {% url %} tags to pass the object's primary key.
Why reverse_lazy in some places? success_url is set when the class is loaded, before URLs are ready. reverse_lazy waits until the URL is needed. Inside a method like get_success_url, plain reverse works, because the method runs later.

Lesson 5: Customising with get_queryset and get_context_data

Two methods cover most customisation:

  • get_queryset() controls which objects the view can see. Put security and filtering rules here.
  • get_context_data() adds extra values for the template. Always call super() first so the defaults are kept.
class PostListView(ListView):
    model = Post
    template_name = "blog/post_list.html"
    context_object_name = "posts"
    paginate_by = 5

    def get_queryset(self):
        return Post.objects.filter(is_published=True).select_related("author")

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context["total_published"] = Post.objects.filter(is_published=True).count()
        return context
AdditionWhat it does
paginate_by = 5Splits results into pages of five. Pagination links appear through page_obj in the template.
select_related("author")Fetches each post's author in the same query, avoiding one extra query per post
total_publishedAn extra value the template can print, such as "12 published posts"
Performance note: select_related works for ForeignKey and one-to-one fields. For ManyToMany relations, use prefetch_related.

Lesson 6: Templates for Generic Views

The list template receives the same variable names as before, so the Day 7 template still works. Pagination adds a short block:

# blog/templates/blog/post_list.html (addition)
{% if is_paginated %}
  <nav>
    {% if page_obj.has_previous %}
      <a href="?page={{ page_obj.previous_page_number }}">Previous</a>
    {% endif %}
    Page {{ page_obj.number }} of {{ page_obj.paginator.num_pages }}
    {% if page_obj.has_next %}
      <a href="?page={{ page_obj.next_page_number }}">Next</a>
    {% endif %}
  </nav>
{% endif %}

For a list with 12 posts and paginate_by = 5, the page shows "Page 1 of 3" with a Next link.

Lesson 7: Mixins and Reuse

A mixin is a small class that adds one behaviour. You combine mixins with a view class, listing the mixins first:

from django.contrib.auth.mixins import LoginRequiredMixin

class PostCreateView(LoginRequiredMixin, CreateView):
    model = Post
    form_class = PostForm
    template_name = "blog/post_form.html"
    success_url = reverse_lazy("post_list")

This view now redirects anonymous visitors to the login page before the form appears. You'll build the login system on Day 16, so for now this is a preview of how mixins add behaviour without changing the core view.

Order matters: Put mixins before the generic view class in the bases list. Django checks them left to right, so a mixin placed after the view may never run.

Lesson 8: When to Use Each Style

  1. Use a generic view when the page fits a standard pattern, such as listing or editing one model.
  2. Use a function view when the logic is unusual, such as a page that combines data from several models in a special way.
  3. Override only what you need. If you find yourself rewriting most of a generic view, a function view is probably clearer.
Rule of thumb: Start with a generic view. Switch to a function view when the class starts fighting you.

Common Mistakes on Day 8

  1. Forgetting .as_view(): Django raises an error about the view being a class.
  2. Overriding get_queryset without the model: the view can't tell which table to use.
  3. Forgetting super() in get_context_data: the default context values disappear, and the template fails.
  4. Using reverse in a class attribute: use reverse_lazy so the URL is resolved later.
  5. Keeping the old post_id URL parameter: generic views expect pk by default.
