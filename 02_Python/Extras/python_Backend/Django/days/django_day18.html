DJANGO DAY 18 of 30

Sending Email

Estimated time: about 1.5 hours · Email settings, the console backend for development, send_mail, HTML emails from templates, sending on sign-up with signals, and testing with the outbox

Lesson 1: Why Email Matters

Email is how a site confirms a sign-up, resets a password, sends receipts, and announces new content. Django includes an email system that works the same way in every environment. Only the delivery method changes between development and production.

Analogy: Django's email module is like a mail room. Your code drops off a letter with the address and contents. The mail room either prints it on the spot for testing or hands it to the postal service in production.

Lesson 2: Email Settings

The email backend decides how messages are delivered. During development, use the console backend, which prints each email in the terminal instead of sending it:

# mysite/settings.py
EMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend"
DEFAULT_FROM_EMAIL = "Mini Blog <noreply@example.com>"

For production, use an SMTP server from your email provider. Keep the password out of your code by reading it from an environment variable:

# mysite/settings.py
import os

EMAIL_BACKEND = "django.core.mail.backends.smtp.EmailBackend"
EMAIL_HOST = "smtp.example.com"
EMAIL_PORT = 587
EMAIL_USE_TLS = True
EMAIL_HOST_USER = os.environ.get("EMAIL_HOST_USER", "")
EMAIL_HOST_PASSWORD = os.environ.get("EMAIL_HOST_PASSWORD", "")
DEFAULT_FROM_EMAIL = "Mini Blog <noreply@example.com>"
Never commit passwords: Read secrets from environment variables, as you did with the secret key on Day 1. Anyone with access to your repository would otherwise be able to send email as your site.

Lesson 3: Sending with send_mail

send_mail is the simplest way to send a plain text email:

>>> from django.core.mail import send_mail

>>> send_mail(
...     subject="Welcome to Mini Blog",
...     message="Hi Sam, thanks for signing up.",
...     from_email=None,                       # None uses DEFAULT_FROM_EMAIL
...     recipient_list=["sam@example.com"],
...     fail_silently=False,
... )
Content-Type: text/plain; charset="utf-8" MIME-Version: 1.0 Content-Transfer-Encoding: 7bit Subject: Welcome to Mini Blog From: Mini Blog <noreply@example.com> To: sam@example.com Date: ... Message-ID: <...> Hi Sam, thanks for signing up. ------------------------------------------------------------------------------- 1

The final 1 is the number of messages sent. The header values such as Date and Message-ID change each time.

ArgumentPurpose
subjectThe email heading
messageThe plain text body
from_emailThe sender; None uses DEFAULT_FROM_EMAIL
recipient_listA list of addresses that receive the email
fail_silentlyIf False, errors such as a failed connection raise an exception
Safety built in: Django refuses a subject containing a newline with a BadHeaderError. This blocks header injection, where an attacker slips extra recipients into a form field.

Lesson 4: HTML Emails from Templates

Real emails usually have a plain text version and an HTML version. Write the content in templates, and send both with EmailMultiAlternatives:

# blog/templates/emails/welcome.txt
Hi {{ user.username }},

Thanks for joining Mini Blog. You can start writing today.

# blog/templates/emails/welcome.html
<h1>Welcome, {{ user.username }}!</h1>
<p>Thanks for joining Mini Blog. <a href="{{ site_url }}">Start writing</a>.</p>
# blog/emails.py
from django.core.mail import EmailMultiAlternatives
from django.template.loader import render_to_string

def send_welcome_email(user):
    context = {"user": user, "site_url": "https://example.com/posts/"}
    text_body = render_to_string("emails/welcome.txt", context)
    html_body = render_to_string("emails/welcome.html", context)

    message = EmailMultiAlternatives(
        subject="Welcome to Mini Blog",
        body=text_body,
        to=[user.email],
    )
    message.attach_alternative(html_body, "text/html")
    message.send()
Why both versions? Some email apps show only plain text, and some spam filters score emails with only HTML more harshly. Sending both is the safer choice.

Keep email templates in a dedicated emails folder inside your templates, and keep the logic that builds them in emails.py. The view then calls one function, which keeps the view short.

Lesson 5: Sending When Something Happens

On Day 10 you used a signal to react when a post was saved. The same idea sends a welcome email when a new user is created:

# blog/signals.py
from django.conf import settings
from django.db.models.signals import post_save
from django.dispatch import receiver
from .emails import send_welcome_email

@receiver(post_save, sender=settings.AUTH_USER_MODEL)
def welcome_new_user(sender, instance, created, **kwargs):
    if created and instance.email:
        send_welcome_email(instance)
Slow email blocks the page: Sending email inside a request makes the visitor wait for the mail server. Real projects move sending into a background task, using a tool such as Celery or Django's task framework. For learning now, the direct call is fine.
Only send to real addresses: The check instance.email skips users with no address, which avoids errors in the email system.

Lesson 6: Testing Email Without Sending

During tests, Django replaces the real backend with an in-memory one. Every message is stored in mail.outbox, so you can check what would have been sent:

# blog/tests.py
from django.contrib.auth.models import User
from django.core import mail
from django.test import TestCase

class WelcomeEmailTests(TestCase):
    def test_welcome_email_sent_on_signup(self):
        User.objects.create_user(username="sam", email="sam@example.com", password="x-pass-123")

        self.assertEqual(len(mail.outbox), 1)
        self.assertEqual(mail.outbox[0].subject, "Welcome to Mini Blog")
        self.assertEqual(mail.outbox[0].to, ["sam@example.com"])

    def test_no_email_without_address(self):
        User.objects.create_user(username="nomail", email="", password="x-pass-123")
        self.assertEqual(len(mail.outbox), 0)
Check the outbox, not the terminal: The outbox is reset before each test, so emails from one test never appear in another. This is the same isolation you learned on Day 13.

Lesson 7: Good Email Practice

  • Ask consent first: send marketing email only to people who opted in. Transactional email, such as a password reset, may be sent without marketing consent.
  • Include an unsubscribe option in marketing emails, and honour it immediately.
  • Use a clear sender name and a real reply address, so people recognise your messages.
  • Never put secrets in email links without expiry: password-reset links should expire quickly and be used only once.
  • Log failures: with fail_silently=False, catch exceptions and log them (Day 12), so a broken mail server doesn't go unnoticed.

Common Mistakes on Day 18

  1. Hard-coding passwords: read them from environment variables.
  2. Forgetting the console backend in development: the mail server may reject test sends or deliver real messages to real people.
  3. Sending only HTML: include a plain text body as well.
  4. Sending from inside a slow request: move long-running sends into background tasks in larger projects.
  5. Assuming an email was delivered: send() only hands the message to the mail server; it does not confirm delivery.

Practicals

Use your mini-blog project.

Practical 1: Console Output

Set the console backend, then run send_mail from the shell. Find the email headers and body in the terminal output.

Practical 2: Plain and HTML Templates

Create the two welcome templates and the send_welcome_email function. Call it from the shell with an existing user and confirm both parts appear in the console output.

Practical 3: Welcome on Signup

Add the signal from Lesson 5 and register a new user through the signup page. Confirm the email appears in the terminal.

Practical 4: Test the Email

Write the two tests from Lesson 6 and run python manage.py test. Confirm both pass and that the console prints nothing during the tests.

Practical 5: Secure Settings

Move the email password into an environment variable, confirm your code reads it, and check that settings.py contains no real password.
