DJANGO DAY 1 of 30

Getting Started with Django

Estimated time: about 1.5 hours · What Django is, setup, projects vs apps, your first view and URL, and how a request travels through Django

Lesson 1: What Is Django?

Django is a Python web framework. A framework gives you the common parts of a web application already built: user accounts, database access, URL routing, form handling, security protections, and an admin panel. You write the parts that make your application unique.

Analogy: Building a house from bare bricks means deciding everything from plumbing to wiring. Django is a prefabricated house: the foundation, plumbing, and wiring are standard and tested, and you spend your time on the rooms and the design.

Django was built for busy news sites and has been used for a wide range of products since. It favours a principle called "batteries included": most things you need are in the box.

Part of DjangoWhat it handles
Models and ORMDefining database tables as Python classes
URLsMatching web addresses to your Python functions
ViewsThe code that handles a request and returns a response
TemplatesHTML files with placeholders filled in by Python data
AdminAn automatic management panel for your data
Auth and securityLogins, password hashing, CSRF and SQL injection protection

Lesson 2: How a Request Travels

When someone types an address into a browser, Django handles it in a predictable chain. Learn this chain now, because every later day adds one link to it.

Browser  →  URL pattern (urls.py)  →  View function (views.py)  →  Response (HTML, JSON, redirect)
                                          ↓
                               Models (models.py) ↔ Database
                               Templates (.html) for pages
Django calls this MTV: Model, Template, View. It is similar to the MVC pattern you may have seen elsewhere. The names differ, but the idea is the same: separate data, presentation, and logic.

Lesson 3: Setup with a Virtual Environment

Use the virtual environment habit from Day 25 for every Django project. Each project gets its own copy of Django, so upgrading one project never breaks another.

mkdir django-course
cd django-course
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install django
python -m django --version
5.2.1

Your version number may be newer. Any recent Django 5.x or later works for this course.

Check the environment: If (venv) is missing from your prompt, the environment isn't active. Run the activate command again before installing anything.

Lesson 4: Projects and Apps

Django has two levels of organisation:

  • Project: the whole website, with its settings and the main URL configuration.
  • App: a self-contained feature, such as a blog, a shop, or user accounts. A project contains one or more apps.
django-admin startproject mysite
cd mysite
python manage.py startapp blog
Analogy: The project is the whole shopping centre. Each app is one shop inside it, with its own rooms and staff, and the centre's settings decide which shops are open.

After these commands your folder looks like this:

mysite/ ├── manage.py # command-line helper for this project ├── mysite/ # the project package │ ├── settings.py # configuration: apps, database, security │ ├── urls.py # the main URL map │ ├── asgi.py / wsgi.py # deployment entry points └── blog/ # the app you created ├── models.py # database tables ├── views.py # request handlers ├── admin.py # admin panel setup ├── apps.py ├── tests.py └── migrations/ # history of database changes

Register the new app in mysite/settings.py so Django knows about it:

# mysite/settings.py
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "blog",   # our new app
]

Lesson 5: Your First View and URL

A view is a Python function that receives a request and returns a response. A URL pattern connects a web address to that view.

Write the view in blog/views.py:

# blog/views.py
from django.http import HttpResponse

def home(request):
    return HttpResponse("Hello, Django!")

def greet(request, name):
    return HttpResponse(f"Hello, {name}!")

Create blog/urls.py to map addresses to those views:

# blog/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("", views.home, name="home"),
    path("greet//", views.greet, name="greet"),
]

Then include the app's URLs in the project's main URL map:

# mysite/urls.py
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("blog.urls")),
]

Start the development server:

python manage.py runserver
Watching for file changes with StatReloader Performing system checks... System check identified no issues (0 silenced). Starting development server at http://127.0.0.1:8000/ Quit the server with CTRL-BREAK.

The first time you start the server, you may also see a warning about unapplied migrations. That is normal for a new project. You'll handle migrations on Day 2.

Visit the addresses in your browser:

AddressPage shown
http://127.0.0.1:8000/Hello, Django!
http://127.0.0.1:8000/greet/Sam/Hello, Sam!
The <str:name> part is a path converter. It captures text from the address and passes it to the view as the name argument. Other converters include int, slug, and uuid.

Lesson 6: The Settings File

Most project-wide behaviour lives in settings.py. You'll meet these settings often:

SettingPurpose
DEBUGWhen True, Django shows detailed error pages. It must be False in production.
INSTALLED_APPSThe list of apps Django loads
DATABASESDatabase connection details. SQLite is the default.
ALLOWED_HOSTSWhich domain names may serve the site
SECRET_KEYA secret used for security features. Never commit it to Git.
Security: The SECRET_KEY in a new project is generated for you. Keep it private, and load it from an environment variable once you deploy. This ties to the .gitignore lesson from Day 29.

Common Mistakes on Day 1

  1. Forgetting to activate the virtual environment: Django installs into the wrong place, or django-admin is not found.
  2. Running startproject twice in the same folder: you end up with nested folders named the same. Check your location with pwd or cd first.
  3. Not adding the app to INSTALLED_APPS: Django ignores the app's models, templates, and admin settings.
  4. Forgetting include() in the project URLs: the app's URLs are never reached, and you see a 404 page.
  5. Stopping the server in the wrong terminal: keep runserver in its own terminal while you edit code.

Practicals

Build everything in one project, mysite. Restart the server if a change doesn't appear.

Practical 1: Set Up Your Environment

Create the virtual environment, install Django, and confirm the version with python -m django --version. Take a screenshot or copy the output to your notes.

Practical 2: Create the Project and App

Run startproject mysite and startapp blog. Register blog in INSTALLED_APPS. Then start the server and confirm the default welcome page appears at http://127.0.0.1:8000/.

Practical 3: Your Own Page

Change the home view to return a short HTML string with a heading and a paragraph about yourself, such as "<h1>Welcome</h1><p>Learning Django</p>". Refresh the browser.

Practical 4: A Second Route

Add a view called about at the address about/. It should return a sentence describing the app. Test it in the browser.

Practical 5: A Route with Two Values

Create a route add/<int:a>/<int:b>/ whose view returns the sum, such as /add/3/4/ showing 7. Think about why int is useful here, and what happens at /add/x/4/.
