API Authentication and Permissions

Estimated time: about 1.5 hours · Token authentication, login endpoints, default settings, object-level permissions, throttling, and testing protected APIs

Lesson 1: Who Is Calling?

Yesterday's API let anyone create and change posts. Before you can allow only some clients to write, the API must know who is calling. That step is authentication. Deciding what that person may do is permission, which you met on Day 25.

Analogy: Authentication is checking a visitor's ID at the door. Permission is the list of rooms that ID opens.

Browsers normally use a session cookie (Day 11). Mobile apps and scripts usually can't keep a cookie jar in the same way, so APIs often use a token: a long random string the client sends with every request.

Lesson 2: Enabling Token Authentication

DRF ships a token model. Add it to the installed apps, then run migrations:

# settings.py
INSTALLED_APPS = [
    # ...
    "rest_framework",
    "rest_framework.authtoken",
    "blog",
]
python manage.py migrate

Then tell DRF which authentication classes to accept, project-wide:

REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.TokenAuthentication",
        "rest_framework.authentication.SessionAuthentication",
    ],
    "DEFAULT_PERMISSION_CLASSES": [
        "rest_framework.permissions.IsAuthenticatedOrReadOnly",
    ],
    "DEFAULT_PAGINATION_CLASS": "rest_framework.pagination.PageNumberPagination",
    "PAGE_SIZE": 5,
}
Setting a safe default: IsAuthenticatedOrReadOnly as the project default means a new viewset is protected unless you deliberately loosen it. Forgetting to set permissions then fails safe.
Order matters: DRF tries the classes in order. With TokenAuthentication first, a missing or bad token gives 401 Unauthorized. If SessionAuthentication is first, the same request gives 403 Forbidden. Both mean "refused", but clients rely on the code, so choose deliberately.

Lesson 3: Issuing a Token

DRF provides a view that checks a username and password and returns a token. Add it to the URLs:

# blog/urls.py
from rest_framework.authtoken.views import obtain_auth_token

urlpatterns = [
    path("api/", include(router.urls)),
    path("api/token/", obtain_auth_token, name="api-token"),
]

A client sends its credentials once and stores the result:

curl -X POST http://127.0.0.1:8000/api/token/ \
     -d "username=asha&password=x-pass-123"
{"token": "9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b"}

Every later request carries the token in the Authorization header, with the word Token before it:

curl http://127.0.0.1:8000/api/posts/ \
     -H "Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b"
Treat tokens like passwords: Anyone holding a token can act as its user. Send it only over HTTPS (Day 22), never put it in a URL, and never commit it to Git.

Lesson 4: Making the Token Creation Explicit

The token is created once per user. Token.objects.get_or_create returns the existing token, or makes one if it's missing. You can also create tokens yourself, for example when a user signs up:

from rest_framework.authtoken.models import Token

user = User.objects.create_user(username="ravi", password="a-strong-pass-789")
token, created = Token.objects.get_or_create(user=user)
print(created, token.key)
True 5b1e0c3a7d9f... (the key is different every time)

To invalidate a client, delete its token. The next request with that token gets a 401:

Token.objects.filter(user=user).delete()
Logout for APIs: Deleting the token is the API version of logging out. A "logout" endpoint can call the same line for the signed-in user.

Lesson 5: Checking the Caller Inside Views

After authentication, request.user holds the user, or AnonymousUser if nobody is signed in. Check it when you need logic beyond the simple permission classes:

from rest_framework.views import APIView
from rest_framework.response import Response

class WhoAmI(APIView):
    def get(self, request):
        if not request.user.is_authenticated:
            return Response({"user": None})
        return Response({"user": request.user.username,
                         "is_staff": request.user.is_staff})

Register it in urls.py as path("api/me/", WhoAmI.as_view()). Note that APIView with get is read-only here; the default permission still applies to the request.

Lesson 6: Object-Level Permissions

Permissions like IsAuthenticatedOrReadOnly answer "may this user call this method at all?". They don't answer "may this user change this post?". For that, write a custom permission with has_object_permission:

# blog/permissions.py
from rest_framework import permissions

class IsAuthorOrReadOnly(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:   # GET, HEAD, OPTIONS
            return True
        return obj.author.user == request.user

Use it on the viewset. Writes to a post now succeed only for its author:

class PostViewSet(viewsets.ModelViewSet):
    serializer_class = PostSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly, IsAuthorOrReadOnly]
    # ...get_queryset and perform_create from Day 25...

Both classes must allow the request. The first checks sign-in; the second checks ownership.

Watch the flow: has_object_permission runs only when DRF fetches a single object (update, partial update, delete, and custom detail actions). The list and create methods call has_permission only. Put the ownership check where it's needed.
Ownership comes from Day 16 and 17: obj.author.user follows the Author.user OneToOneField you built on Day 16, so ownership uses the same link as the rest of the site.

Lesson 7: Throttling

Throttling limits how often a client may call the API. It protects against brute-force logins and runaway scripts. Set rates in settings:

REST_FRAMEWORK = {
    # ...authentication and permission settings from Lesson 2...
    "DEFAULT_THROTTLE_CLASSES": [
        "rest_framework.throttling.AnonRateThrottle",
        "rest_framework.throttling.UserRateThrottle",
    ],
    "DEFAULT_THROTTLE_RATES": {
        "anon": "50/day",
        "user": "1000/day",
    },
}

When the limit is reached, DRF returns 429 Too Many Requests. Anonymous visitors are counted by IP address, signed-in users by their account.

Cache required: Throttling stores counts in Django's cache (Day 20). The default local-memory cache works for development. In production with several server processes, use a shared cache such as Redis.

Lesson 8: Testing Protected Endpoints

Test the three paths every protected API needs: anonymous, wrong user, and correct user. APIClient can send the token header directly:

from django.contrib.auth.models import User
from rest_framework.authtoken.models import Token
from rest_framework.test import APITestCase
from rest_framework import status
from django.urls import reverse
from blog.models import Author, Post

class PostPermissionTests(APITestCase):
    @classmethod
    def setUpTestData(cls):
        cls.asha_user = User.objects.create_user("asha", password="x-pass-123")
        cls.ravi_user = User.objects.create_user("ravi", password="y-pass-456")
        cls.asha = Author.objects.create(name="Asha", email="asha@example.com", user=cls.asha_user)
        cls.post = Post.objects.create(title="Hello", body="...", author=cls.asha, is_published=True)
        cls.asha_token = Token.objects.create(user=cls.asha_user)
        cls.ravi_token = Token.objects.create(user=cls.ravi_user)

    def test_anonymous_cannot_edit(self):
        url = reverse("post-detail", args=[self.post.pk])
        response = self.client.patch(url, {"title": "Hacked"}, format="json")
        self.assertIn(response.status_code, (401, 403))

    def test_other_user_cannot_edit(self):
        self.client.credentials(HTTP_AUTHORIZATION=f"Token {self.ravi_token.key}")
        url = reverse("post-detail", args=[self.post.pk])
        response = self.client.patch(url, {"title": "Hacked"}, format="json")
        self.assertEqual(response.status_code, status.HTTP_403_FORBIDDEN)

    def test_author_can_edit(self):
        self.client.credentials(HTTP_AUTHORIZATION=f"Token {self.asha_token.key}")
        url = reverse("post-detail", args=[self.post.pk])
        response = self.client.patch(url, {"title": "Updated"}, format="json")
        self.assertEqual(response.status_code, status.HTTP_200_OK)
        self.post.refresh_from_db()
        self.assertEqual(self.post.title, "Updated")
Clean up credentials: self.client.credentials() with no arguments removes the header. Use it between phases of one test so one user's token doesn't leak into the next check.

Common Mistakes on Day 26

  1. Forgetting rest_framework.authtoken in INSTALLED_APPS: the token table doesn't exist, and token login fails.
  2. Sending the token without the word Token: the header must be Authorization: Token <key>.
  3. Relying on has_permission alone for ownership: add has_object_permission for single-object writes.
  4. Passing tokens in URLs: query strings are logged by servers and proxies.
  5. Expecting throttling without a cache: counts are stored in the cache, so the cache must work.
  6. Testing only the success path: check anonymous and wrong-user responses too.

Practicals

Use your mini-blog project with the viewset from Day 25.

Practical 1: Enable Tokens

Add rest_framework.authtoken, run migrate, and add the api/token/ route. Request a token for a test user with curl or the browsable API.

Practical 2: Call with a Token

Create a post with the token header. Then call the same endpoint without the header and note the status code.

Practical 3: Ownership

Write IsAuthorOrReadOnly. Log in as two users and confirm only the author can change a post. Confirm both can read it.

Practical 4: Throttle

Set the anon rate to 5/minute. Send six anonymous requests in a loop and confirm the sixth returns 429.

Practical 5: Tests

Write the three tests from Lesson 8 and run python manage.py test. Fix any failures before moving on.
