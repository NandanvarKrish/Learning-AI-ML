Git Basics

Estimated time: about 1.5 hours · Why version control, repositories, add and commit, history, branches, merging, remotes, .gitignore, and Git from Python

Lesson 1: Why Version Control?

Every programmer eventually faces files named final.py, final_v2.py, and final_REALLY_final.py. Git solves this. It records snapshots of your project over time, so you can see what changed, when, and why, and return to any earlier version.

Analogy: Git is like a video recorder for your project. Each commit is a saved frame. You can rewind to any frame, compare two frames, or start a side timeline (a branch) to try an idea without touching the main one.

Git runs on your own computer. It is a tool; GitHub, GitLab, and Bitbucket are websites that host Git repositories so teams can share them.

Lesson 2: Setup and Your First Repository

Install Git from git-scm.com, then tell it who you are. This name appears on every commit.

git config --global user.name "Sam"
git config --global user.email "you@example.com"
git --version
git version 2.43.0

The version number on your machine may differ, which is fine. Now create a project folder and turn it into a repository:

mkdir hello-git
cd hello-git
git init
Initialized empty Git repository in /home/you/hello-git/.git/

git init creates a hidden .git folder. That folder holds the entire history. Delete it and you lose the history, but not your current files.

Lesson 3: The Three Stages: Working, Staged, Committed

Git has three places a change can live:

StageMeaningCommand that moves it forward
Working directoryThe files you editgit add
Staging areaChanges chosen for the next commitgit commit
RepositorySaved snapshots in history(already saved)

Staging lets you pick exactly which changes belong together in one commit.

echo 'print("Hello, Git")' > app.py
git status
On branch main No commits yet Untracked files: app.py
git add app.py
git commit -m "Add greeting script"
[main (root-commit) a1b2c3d] Add greeting script 1 file changed, 1 insertion(+) create mode 100644 app.py
Note: The short code like a1b2c3d is a commit ID. Yours will be different. Git computes it from the content, so it is unique to that snapshot.

Write commit messages in the imperative, such as "Add login form" or "Fix off-by-one in loop". Explain why when it isn't obvious.

Lesson 4: Looking at History and Changes

git log --oneline
a1b2c3d (HEAD -> main) Add greeting script
git diff            # unstaged changes
git diff --staged   # staged changes, ready to commit
git show HEAD       # the last commit in full

The table below covers the commands you will use most:

CommandWhat it does
git statusShows what has changed and what is staged
git log --onelineLists commits compactly
git diffShows line-by-line changes
git restore file.pyThrows away unstaged edits to a file
git restore --staged file.pyUnstages a file without losing its edits
Careful: git restore discards edits that were never committed. Those changes cannot be recovered afterwards. Check git status first.

Lesson 5: Branches

A branch is a movable pointer to a commit. Creating a branch lets you develop a feature without disturbing main.

git switch -c add-login     # create and switch to a new branch
# ... edit files, then:
git add .
git commit -m "Add login form"
git switch main            # go back to main
Switched to branch 'main'
Analogy: Branches are like drafts of an essay. You can rewrite a whole section in draft two, and the original stays untouched until you decide to adopt the changes.

Older tutorials use git checkout -b and git checkout. Both still work; switch and restore are clearer names for the same actions.

Lesson 6: Merging and Conflicts

Merging brings the commits from one branch into another.

git switch main
git merge add-login
Updating a1b2c3d..e4f5a6b Fast-forward login.py | 4 ++++ 1 file changed, 4 insertions(+)

A fast-forward happens when main has no new commits, so Git just moves the pointer. If both branches changed the same lines, Git reports a conflict and marks the file like this:

<<<<<<< HEAD
print("Welcome")
=======
print("Hello")
>>>>>>> add-login

Edit the file so it contains the correct final text, delete the marker lines, then run git add on the file and git commit. Conflicts look frightening the first time but are routine.

Lesson 7: Remotes: Sharing with Others

A remote is another copy of the repository, usually on GitHub. You send your commits to it with push and fetch others' commits with pull.

git remote add origin https://github.com/your-name/hello-git.git
git push -u origin main
git pull
CommandMeaning
originThe conventional name for the main remote
git push -u origin mainUpload main and link it to the remote branch
git pullFetch remote changes and merge them into your branch
git clone URLDownload a whole repository, including history
Tip: Run git pull before you start work, so you build on the latest code and avoid conflicts later.

Lesson 8: .gitignore: Keeping Files Out

Some files should never be committed: virtual environments, cache folders, secrets such as API keys, and large generated files. List them in a file named .gitignore:

venv/
__pycache__/
*.pyc
.env
contacts.csv
library.db
Security: If you commit a password or API key, deleting it in a later commit does not remove it from history. Rotate the secret immediately, and never put secrets in tracked files.

Files already tracked are not affected by .gitignore. Remove them from tracking with git rm --cached filename.

Lesson 9: Using Git from Python

Python's subprocess module (introduced on Day 27) can run Git commands and read their output. This is handy for scripts that check many repositories.

import subprocess

def git(*args):
    result = subprocess.run(
        ["git", *args],
        capture_output=True,
        text=True,
        check=True,
    )
    return result.stdout.strip()

print(git("branch", "--show-current"))
print(git("status", "--short") or "Working tree clean")
main Working tree clean

check=True raises CalledProcessError when Git fails, which fits the exception handling from Day 12. The sample output assumes you are on main with no changes; yours depends on your repository.

Common Mistakes on Day 29

  1. Forgetting git add: new or changed files are not included in the commit until they are staged.
  2. Vague messages: "stuff" or "fix" tells future readers nothing. Describe the change.
  3. Committing secrets or virtual environments: use .gitignore from the start.
  4. Working on main for everything: use a branch for each feature so main stays stable.
  5. Ignoring git status: it tells you what Git sees before you commit.

Practicals

Work in a new folder called git-practice. Run git status after every step so you see the stages change.

Practical 1: First Commit

Initialise a repository, create notes.txt with two lines of text, stage it, and commit with a clear message. Check the result with git log --oneline.

Practical 2: See a Diff

Add a third line to notes.txt. Run git diff to see the change, then stage and commit it with a new message.

Practical 3: Branch and Merge

Create a branch called experiment, add a file there, commit it, switch back to main, and merge. Explain in one sentence whether the merge was a fast-forward.

Practical 4: Ignore a File

Create a file named secret.env, add it to .gitignore, and confirm with git status that Git no longer lists it.

Practical 5: Python Helper

Write a script check_repo.py using the git() helper from Lesson 9. It should print the current branch and the last commit message, using git log -1 --pretty=%s.
