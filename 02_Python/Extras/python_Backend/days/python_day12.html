Errors and Exceptions

Estimated time: about 1.5 hours · Reading tracebacks, try, except, else, finally, raising and custom exceptions

Lesson 1: Errors Are Normal

Every programmer meets errors daily. An error is not a sign that you're bad at coding. It's Python telling you exactly what it couldn't do. Your job is to read the message, find the cause, and decide whether to fix the code or handle the situation gracefully.

Analogy: A smoke alarm doesn't mean the house is broken. It tells you something needs attention. Exceptions work the same way: they signal a problem at a specific point in the program.

Lesson 2: Three Kinds of Errors

TypeWhen it happensExample
Syntax errorBefore the program runs, when the code breaks Python's grammarif x = 5: (missing ==)
Runtime error (exception)While the program runs, when something goes wrong10 / 0
Logic errorThe program runs without crashing but gives the wrong resultUsing + where you meant *

Syntax errors must be fixed before the code can run at all. Exceptions can be caught and handled. Logic errors are the hardest, because Python does not report them. You find them with tests and careful thinking.

Lesson 3: Reading a Traceback

When an unhandled exception happens, Python prints a traceback. It looks intimidating, but you can read it in a fixed order.

def average(nums):
    return sum(nums) / len(nums)

print(average([]))
Traceback (most recent call last): File "stats.py", line 4, in <module> print(average([])) File "stats.py", line 2, in average return sum(nums) / len(nums) ZeroDivisionError: division by zero
How to read it:
  1. Start at the last line. It names the exception type and message: ZeroDivisionError.
  2. Look at the line above it to see the exact code that failed.
  3. Read upward through the File lines to see how the program reached that point.

The most useful habit: fix the exception named on the last line, and check the line number it points to.

Lesson 4: Common Built-in Exceptions

ExceptionTypical cause
ValueErrorRight type, wrong value, e.g. int("abc")
TypeErrorWrong type for an operation, e.g. "5" + 3
ZeroDivisionErrorDividing by zero
IndexErrorIndex beyond the list or string length
KeyErrorMissing key in a dictionary
FileNotFoundErrorFile does not exist (Day 11)
NameErrorUsing a variable that has not been defined
AttributeErrorCalling a method that doesn't exist on an object, e.g. "abc".push()
Careful: ValueError and TypeError look similar, but the difference matters. int("abc") is a ValueError because the type (str) is right but the value isn't a number. int([1]) is a TypeError because the type itself is wrong.

Lesson 5: try and except

Wrap risky code in a try block. If an exception happens, Python jumps to the matching except block instead of crashing.

try:
    number = int(input("Enter a number: "))
    print("Double:", number * 2)
except ValueError:
    print("That was not a whole number.")

print("Program continues")
Enter a number: abc That was not a whole number. Program continues

Catching several exceptions

def safe_divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        return None
    except TypeError:
        return None

print(safe_divide(10, 2))     # 5.0
print(safe_divide(10, 0))     # None
print(safe_divide(10, "x"))   # None
5.0 None None

Getting the exception details

try:
    value = int("abc")
except ValueError as error:
    print("Problem:", error)
Problem: invalid literal for int() with base 10: 'abc'
Avoid bare except: except: with no type catches everything, including KeyboardInterrupt when you press Ctrl+C. Name the exceptions you expect. Use except Exception only at the top level of a program, where you want a last-resort message.

Lesson 6: else and finally

else runs only if the try block succeeded. finally always runs, whether or not an error happened. Use it for cleanup.

def read_number(text):
    try:
        number = int(text)
    except ValueError:
        print("Invalid input")
    else:
        print("Valid number:", number)
    finally:
        print("Check finished")

read_number("42")
read_number("abc")
Valid number: 42 Check finished Invalid input Check finished
Tip: Keep the try block small. Put only the risky line inside it, so you catch exactly the error you expect and nothing else.

For files, the with statement from Day 11 already handles cleanup, so finally is most useful for other resources such as network connections.

Lesson 7: Raising Exceptions

You can trigger an error yourself with raise. This is useful when your function receives data that is technically valid Python but wrong for your program.

def set_age(age):
    if age < 0 or age > 130:
        raise ValueError("Age must be between 0 and 130")
    return age

try:
    set_age(200)
except ValueError as e:
    print("Error:", e)
Error: Age must be between 0 and 130

Raising early, near the bad input, gives a clear message. Without it, the bad value might cause a confusing error much later.

Lesson 8: Custom Exceptions

For your own program, you can define an exception class. Inherit from Exception, and you'll learn classes properly in Week 3.

class InsufficientFunds(Exception):
    pass

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFunds(f"Balance {balance} is less than {amount}")
    return balance - amount

try:
    withdraw(100, 500)
except InsufficientFunds as e:
    print("Transaction declined:", e)
Transaction declined: Balance 100 is less than 500

Custom exceptions let calling code catch exactly the problem it cares about.

Common Mistakes on Day 12

  1. Bare except: hides bugs and catches Ctrl+C. Name the exception.
  2. Too much code inside try: an unrelated error may be caught by accident.
  3. Silent failure: except: pass hides problems. At least print or log the error.
  4. Reading only the top of a traceback: the last line says what went wrong.
  5. Confusing ValueError and TypeError: check whether the type or the value is the problem.

Practical 6: Read a Traceback
