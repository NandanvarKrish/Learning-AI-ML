The Control Panel & The Assembly Line:
@property, Comprehensions & Generators

A good control panel lets you turn a dial and have the machine quietly check and adjust things behind the scenes — that's @property. An assembly line stamps out a whole batch of parts in one pass — that's a comprehension. And a lazy conveyor belt that hands you one part only when you ask for the next one — that's a generator.

What you'll walk away with: why @property exists, Pythonic getters/setters, computed and validated attributes, list/set/dict comprehensions (including nested and conditional ones), what generators are, yield, generator expressions, lazy evaluation and memory efficiency, a full real-world build (a streaming data processor), and a 15-question quiz.

Topic 01

Why @property exists

Sometimes you want an attribute to look and feel like plain data (obj.value), but actually run a small check or calculation behind the scenes every time it's read or changed.

Real-world analogy A thermostat dial looks like a simple control — you turn it to 72. But behind the panel, it's actually running a small program: checking the number is in a safe range, converting it to the furnace's internal units, maybe logging the change. You never see that machinery; you just turn the dial. @property lets a Python attribute work exactly like that dial — simple to use, but backed by real logic.

The problem it solves

# plain attribute — anyone can set it to anything, including nonsense
class Thermostat:
    def __init__(self, temp):
        self.temp = temp

t = Thermostat(70)
t.temp = -500   # nothing stops this — an impossible temperature is silently accepted

The fix, with a property

class Thermostat:
    def __init__(self, temp):
        self._temp = temp        # stored privately, single underscore = "internal"

    @property
    def temp(self):
        return self._temp     # the "dial reading" — looks like a normal attribute

    @temp.setter
    def temp(self, value):
        if value < -40 or value > 120:
            raise ValueError("Temperature out of safe range.")
        self._temp = value

t = Thermostat(70)
t.temp = 75          # looks like plain assignment, but runs the check
t.temp = -500        # raises ValueError — the dial refuses an unsafe setting
@property = getter@x.setter = setterlooks like data, acts like a methodvalidation on assignment
Topic 02

Getters and setters, the Pythonic way

Other languages often require explicit getTemp() / setTemp() methods everywhere. Python lets you start with a plain attribute and upgrade to a property later — without changing how anyone else uses your class.

Real-world analogy If the control panel starts as a bare wire and later gets a proper dial installed, the person operating it shouldn't have to learn a new gesture — turning the dial should feel the same before and after. Properties let you swap plain storage for real logic without breaking any code that already does obj.value = 10. 
class Circle:
    def __init__(self, radius):
        self.radius = radius

    @property
    def area(self):
        return 3.14159 * self.radius ** 2

c = Circle(4)
print(c.area)     # 50.26544 — called with NO parentheses, like a plain attribute
c.radius = 10       # change the radius...
print(c.area)     # ...and area recalculates automatically on next read: 314.159

Notice c.area is read with no parentheses, even though it's really running a calculation — that's the whole point. It behaves like a value, not a method call.

Read-only properties

class Circle:
    def __init__(self, radius):
        self.radius = radius

    @property
    def area(self):
        return 3.14159 * self.radius ** 2

c = Circle(4)
c.area = 100   # AttributeError — no setter defined, so "area" can't be assigned directly

Without a matching @area.setter, the dial simply has no input side — you can read it, but you can't turn it. That's a deliberate design choice for values that should only ever be calculated, never set directly.

Topic 03

Computed properties & validation

Properties shine in two situations: deriving a value from other attributes, and enforcing rules the moment something is assigned.

A computed property

class Employee:
    def __init__(self, first, last):
        self.first = first
        self.last = last

    @property
    def full_name(self):
        return f"{self.first} {self.last}"

e = Employee("Maya", "Rao")
print(e.full_name)    # Maya Rao — never stored directly, always derived fresh

There's no self.full_name = ... anywhere — it's computed live every time it's read, so it can never drift out of sync with first and last.

A validating setter

class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price     # goes through the setter below immediately

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError("Price cannot be negative.")
        self._price = value

item = Product("Mug", 9.99)
item.price = -5   # raises ValueError immediately — bad data is rejected at the door
Real-world analogy A validating setter is a security guard at the panel's input slot — every value that tries to get in is checked before it's accepted, so nothing invalid ever makes it into storage in the first place.
Topic 04

Comprehensions, quick recap

A comprehension is a compact assembly line: feed it raw material and a rule, and it stamps out a finished collection in one line — no manual loop needed.

Real-world analogy Instead of a worker picking up each part, checking it, and placing it on a shelf one at a time (a manual for-loop), a comprehension is the automated stamping machine: raw parts go in one end, finished parts come out the other, following one fixed rule. 
# list comprehension
squares = [n**2 for n in range(1, 6)]
# [1, 4, 9, 16, 25]

# set comprehension — duplicates automatically dropped
unique_lengths = {len(w) for w in ["fig", "kiwi", "pear"]}
# {3, 4}

# dict comprehension
squared_map = {n: n**2 for n in range(1, 4)}
# {1: 1, 2: 4, 3: 9}

The general shape

[ expression for item in iterable if condition ]

Read it left to right as: "give me expression, for every item in iterable, but only keep it if condition is true." Swap the brackets for {} or {: } to get a set or dict instead of a list.

Topic 05

Nested & conditional comprehensions

Comprehensions can filter with if, branch with if/else, and even loop inside a loop — still in one line, though readability starts to matter more here.

Filtering with if

evens = [n for n in range(10) if n % 2 == 0]
# [0, 2, 4, 6, 8] — the "if" here is a filter: skip anything that fails it

Branching with if/else

labels = ["even" if n % 2 == 0 else "odd" for n in range(5)]
# ['even', 'odd', 'even', 'odd', 'even']
# note: this if/else sits BEFORE the "for" — it picks a value, it doesn't filter
Real-world analogy An if after the loop is a quality-control gate — reject anything that doesn't pass, nothing comes out for it. An if/else before the loop is a stamping choice — every part gets stamped with one of two labels, nothing is rejected.

Nested loops inside a comprehension

# flatten a grid of rows into one flat list
grid = [[1, 2], [3, 4], [5, 6]]
flat = [num for row in grid for num in row]
# [1, 2, 3, 4, 5, 6] — reads like: for each row, for each num in that row

Once a comprehension needs more than one for and one if, it's often clearer to write it as a regular loop instead — a comprehension should save effort, not cost readability.

Topic 06

What generators actually are

A list builds every item up front and holds them all in memory at once. A generator produces items one at a time, only when asked — and forgets each one once it's handed over.

Real-world analogy A comprehension is a factory that stamps out an entire batch of parts before handing you the whole crate — all of it sitting in a warehouse at once. A generator is a conveyor belt: it hands you one part only when you reach for the next one, and never stockpiles the whole batch. If you only ever need the first three parts, the conveyor belt never bothers making the other 999,997. 
# a list — builds and stores ALL 10 million numbers immediately
big_list = [n for n in range(10_000_000)]

# a generator — produces numbers one at a time, on demand, using far less memory
big_gen = (n for n in range(10_000_000))

Why this matters in practice

Memory

A generator over a huge dataset can use a tiny, constant amount of memory instead of loading everything at once.

Laziness

Values are computed only when actually requested — useful for infinite or very large sequences.

One pass only

Once you've walked the conveyor belt to the end, it's empty — you can't rewind and read it again.

Pipelines

Generators chain well — one lazy step feeding the next, processing huge data streams efficiently.

Topic 07

yield, in depth

yield is what turns an ordinary function into a generator function — instead of returning once and ending, it hands back a value and pauses, ready to continue exactly where it left off.

def countdown(n):
    while n > 0:
        yield n     # hand back this value, then PAUSE here
        n -= 1

for num in countdown(3):
    print(num)
# 3
# 2
# 1
Real-world analogy return is a worker finishing the whole job and walking away for good. yield is a worker handing you one finished part, then freezing exactly where they stood — the moment you ask for the next one, they pick up mid-motion and keep going, remembering everything they were doing.

Calling a generator function doesn't run it yet

gen = countdown(3)     # nothing has run yet — this just creates the generator object
next(gen)             # 3 — runs up to the first yield
next(gen)             # 2 — resumes right after the last yield
next(gen)             # 1
next(gen)             # raises StopIteration — the conveyor belt is empty

A for loop over a generator automatically calls next() for you and quietly stops when it sees StopIteration — you rarely need to call next() by hand outside of learning how it works.

A generator that models something real

def read_large_file(path):
    with open(path, "r") as f:
        for line in f:
            yield line.strip()    # one line at a time, never the whole file in memory

for line in read_large_file("huge_log.txt"):
    if "ERROR" in line:
        print(line)
Topic 08

Generator expressions & laziness

Just like list comprehensions have a compact syntax, generators have their own one-liner form — swap the square brackets for parentheses.

# list comprehension — builds the whole list immediately
squares_list = [n**2 for n in range(1_000_000)]

# generator expression — builds nothing yet, just describes how to make each value
squares_gen = (n**2 for n in range(1_000_000))

next(squares_gen)   # 0 — computed only now, the instant it's asked for
next(squares_gen)   # 1
Real-world analogy The square-bracket version is ordering the entire year's production run delivered to your warehouse today. The parenthesis version is a standing order: "make one whenever I ask" — nothing is produced, stored, or paid for until it's actually requested.

Feeding a generator directly into a function

total = sum(n**2 for n in range(1_000_000))
# no square brackets needed here — this generator expression streams
# values straight into sum() one at a time, without ever building a full list

When to choose which

  • Use a list/comprehension when you need to loop over the data more than once, check its length, or index into it.
  • Use a generator when you're processing something huge or possibly infinite, and only need to walk through it once, front to back.
Topic 09 · Build something real

Project: a streaming sales report

We'll build a small system that processes a large sales log without ever loading the whole thing into memory, using a validated @property, comprehensions for quick summaries, and a generator pipeline for the heavy lifting — the same shape real log-processing and analytics tools use.

The brief Model a Sale with a validated price property. Stream sales from a huge file lazily with a generator. Filter and transform that stream with more generators. Use a comprehension only for the small, final summary — never for the full raw stream.
1

Model a Sale with a guarded property

The amount should never be negative — enforce that the moment it's set, not after the fact.

class Sale:
    def __init__(self, item, amount):
        self.item = item
        self.amount = amount     # goes straight through the setter below

    @property
    def amount(self):
        return self._amount

    @amount.setter
    def amount(self, value):
        if value < 0:
            raise ValueError(f"Sale amount cannot be negative: {value}")
        self._amount = value
2

Stream sales from a file, one line at a time

A generator function — never loads the whole log into memory, however large it is.

def read_sales(path):
    with open(path, "r") as f:
        for line in f:
            item, amount_str = line.strip().split(",")
            yield Sale(item, float(amount_str))
3

Filter the stream lazily with another generator

Chain a second generator on top — still nothing has actually run yet at this point.

def big_sales(sales, threshold=50):
    for sale in sales:
        if sale.amount >= threshold:
            yield sale

sales_stream = read_sales("sales_log.csv")
notable = big_sales(sales_stream, threshold=100)
4

Only pull what's needed — the first few, or a running total

Nothing is computed until you actually ask, one at a time or via a built-in like sum().

import itertools

# peek at just the first 3 notable sales without processing the whole file
for sale in itertools.islice(notable, 3):
    print(f"{sale.item}: {sale.amount}")

# or stream the whole thing into a total, still one sale at a time
total = sum(sale.amount for sale in big_sales(read_sales("sales_log.csv")))
5

Use a comprehension only for a small final summary

Once you've reduced the stream down to something small, a comprehension is the right tool again.

top_items = ["Laptop", "Monitor", "Keyboard"]
price_lookup = {item: len(item) * 10 for item in top_items}
# {'Laptop': 60, 'Monitor': 70, 'Keyboard': 80} — a small, finished result, built all at once
What you just practiced A validating @property guarding bad data at the door, a generator pipeline (read_sales → big_sales) that never loads the full file into memory, lazy consumption with islice and sum(), and a comprehension used correctly — for a small, already-reduced final result, not the raw stream.
